## 问题描述

### A. 范围事实与 PRD 冲突：托管化已落地，PRD 仍写「顺延 v0.3」

**既成事实**（commit `b5ae3b6`）：`deploy/systemd/niuma-ai-worker@.service` 与 `niuma-ai-http@.service` 模板 unit + 幂等部署脚本已提交，unit 含 `Restart=on-failure`、`TimeoutStopSec=280`。

**PRD §4 现写**：

> **服务托管化**（systemd / launchd）——顺延 v0.3。v0.2 的 worker 是**无托管、崩溃不自动拉起**的进程……因此 **v0.2 只能在人工看护下灰度，不得进入无人值守运行**。

**实际状态介于两者之间**（DevOps 设计 R2 中②已精确指出）：

| 能力 | v0.2 实际 |
|---|---|
| 进程崩溃后自动拉起 | ✅ 已具备（`Restart=on-failure` 看进程退出码） |
| **worker 协程死亡后自动重启** | ❌ **不具备**——协程死了进程仍在（正是 §4.1 `_on_worker_done` 处理的场景），systemd 看不到退出码，什么都不会做 |
| 消费 `dead` 状态的健康检查 | ❌ 未纳入（healthcheck timer 在 `deploy/README.md` 中明确列为「尚未纳入」） |

于是 `dead` 状态下的真实链路是：worker 已死 → `/health` 返回 503 → **没有任何东西在读这个 503** → 靠人工 curl 才能发现。

### B. PM 设计 R2 附条件（高）：AC-5.7「三层须配一致值」与设计冲突，错在 PRD

设计 §4.8（R2 订正）为**逐层放大**：应用层 260s ≤ uvicorn `--timeout-graceful-shutdown` ≥260s < systemd `TimeoutStopSec` 280s，并给出不能相等的理由——**若应用层与托管层都配 260s，当 worker 恰好用满 260s 完成最后一次写回时 systemd 在同一时刻 SIGKILL，写回事务可能在 COMMIT 之前被杀**，留下 `l1_status='processing'` 残留锁等 1800s 回收。

而 PRD AC-5.7 现写「**三层须配一致值**」（`v0.2-prd.md:171`）。

**责任在 PM**：CN-003 变更 3.4 承接 DevOps R3 高②时，逐字搬用了其「三层配一致」的措辞。DevOps 本意是「三层必须协调、不能各自为政」，「一致」的字面被读成了「数值相等」——**而验收标准的字面就是实现依据**。

**后果非文字问题**：照 PRD 字面配三个相等值会**完全符合 AC-5.7 的验收**，却在真实停机时踩上述竞态；而该竞态只在「恰好用满宽限期」时触发，**自测几乎必不复现**。

### C. DevOps 设计 R2 附条件（高）：数据库操作没有任何时间上限

设计对**处理阶段**的时间控制很严谨（`ItemBudget` + `slice_for()` + `L1_MIN_SEGMENT_MS`，240s 封顶）。但 **claim 与写回两个数据库事务不在任何预算内，且全文没有任何超时配置**——`connect_timeout` / `statement_timeout` / `lock_timeout` 在设计 §2.6 配置表与 §4.10 连接池设计中**均零命中**。

后果：

- §4.8 的宽限期算式（应用层 260s = 240s 预算 + **20s 收尾余量**）失去保证——收尾余量要覆盖「写回事务及其重试」，而写回时间无界。
- §4.6 写回重试的「≤2s」断言同样失去依据。

**这与 PM 设计 R2 低②是同一处的两面**：PM 指出「不变式输入应含写回重试余量」，DevOps 指出「那个余量本身就是无界的」——后者是根因。

DevOps 给出的自洽取值：`statement_timeout=8s`、`lock_timeout=5s` → 最坏 `2 × (8+1) = 18s < 20s` 余量，**算式自洽且无需改动已定的 260/280**。（若按常见的 `statement_timeout=30s`，最坏 62s 远超余量，届时要么调大宽限期、要么调小超时。）

## 处理方式

### 变更 1（A 项，Owner 2026-07-28 拍板）：托管化**部分纳入** v0.2

**PRD §4 的托管化条目由「本迭代不做」拆分**——

**移入「本迭代做」**：

> - **服务托管化（进程级）**：systemd 模板 unit + 幂等部署脚本，**进程崩溃后自动拉起**（`Restart=on-failure`）、`TimeoutStopSec` 与 AC-5.7 的三层时限协同。
>   - 验收：① unit 已部署且 `systemctl` 可正常 start/stop/status；② 手动 kill worker **进程**后，systemd 在配置的重试策略内自动拉起；③ `TimeoutStopSec` 取值满足 AC-5.7 的逐层放大关系。

**保留在「本迭代不做（顺延 v0.3）」并改写**：

> - **健康检查驱动的重启（worker 协程级）**——顺延 v0.3。
>   **v0.2 的真实能力边界（据实写明，防止误期待）**：`Restart=on-failure` 只看**进程退出码**；而 worker 协程死亡时**进程仍然存活**（设计 §4.1 `_on_worker_done` 正是处理这一场景），systemd 看不到任何退出码，**不会做任何事**。消费 `dead` 状态的 healthcheck timer 尚未纳入（`deploy/README.md` 明确列为「尚未纳入」）。
>   因此 `dead` 状态下的真实链路是：worker 已死 → `/health` 返回 503 → **没有任何东西在读这个 503** → **靠人工发现**。
>   **灰度期约束（替代原「不得无人值守」）**：v0.2 **可以**在 systemd 托管下运行（进程崩溃有兜底），但**仍须人工看护 worker 存活**——因为 `dead` 状态无自动消费方。部署就绪检查须按此口径判定：**unit 存在 ≠ worker 存活有自动兜底**。

### 变更 2（B 项，PM 附条件）：AC-5.7 订正为逐层放大

AC-5.7 的「三层须配一致值」**改写为**：

> - **三层须逐层放大，且不得取同一数值**：**应用层 `L1_SHUTDOWN_GRACE_MS` ≤ ASGI 层 `--timeout-graceful-shutdown` < 托管层 systemd `TimeoutStopSec`**（设计 §4.8 落定为 260s / ≥260s / 280s）。
>   - **为什么不能相等**：三者语义不同——应用层是「worker 收到停机信号后最多用多久收尾」，托管层是「从 SIGTERM 到 SIGKILL 的墙钟」。若应用层与托管层同为 260s，当 worker **恰好用满** 260s 完成最后一次写回时，systemd 在同一时刻 SIGKILL——**写回事务可能在 COMMIT 之前被杀**，留下 `l1_status='processing'` 的残留锁等 1800s 回收。这正是整条优雅停机链要防的事，却会因为「三个数字写成一样」而发生；且该竞态**只在恰好用满宽限期时触发，自测几乎必不复现**。
>   - **强制点在部署脚本，不在应用启动校验**：应用进程**读不到自身的 systemd 配置**，启动门禁只能校验应用侧的两个量（`L1_SHUTDOWN_GRACE_MS ≥ N × L1_ITEM_BUDGET_MS`）。三层关系的校验须落在部署脚本（设计 §4.8 已落定）。
>   > **订正说明**：原「三层须配一致值」由 CN-003 变更 3.4 逐字搬用 DevOps R3 高②的措辞而来，其本意为「三层必须协调、不能各自为政」，字面被读成「数值相等」。**表述责任在 PM**，DevOps 已在设计 R2 认领原措辞的歧义来源。

### 变更 3（C 项 + PM 低②合并）：新增 DB 操作超时上限，AC-3.6 不变式输入据此收敛

**新增 AC-4.7（数据库操作超时上限）**：

> 1. 数据库操作须设时间上限，**不得依赖默认无限等待**：`connect_timeout`（新增配置 `AI_DB_CONNECT_TIMEOUT_MS`）、`statement_timeout`、`lock_timeout` 三项须在连接池初始化时显式设置。
> 2. **取值须与 AC-5.7 的收尾余量自洽**：`(写回重试次数 + 1) × (statement_timeout + 重试间隔) ≤ AC-5.7 的收尾余量`。按设计当前取值（重试 2 次 / 间隔 1s / 收尾余量 20s），**`statement_timeout=8s`、`lock_timeout=5s`** 满足自洽（最坏 `2 × (8+1) = 18s < 20s`），且无需改动已定的 260/280。
> 3. 验证方式：配置校验中断言上述不等式；构造一次持锁冲突，断言在 `lock_timeout` 内失败而非无限等待。
> 4. **写回事务本身是毫秒级的**，上述超时只对「等锁」这类异常路径起封顶作用，对正常路径无影响。

**AC-3.6 的不变式输入相应收敛为**：

> `N × (单条 wall-clock 预算 + AC-4.7 保证的 DB 操作上界) < 1800s`
>
> 原式 `N × 单条预算 < 1800s` 未含 DB 操作时间，而写回重试明确在预算之外（设计 §4.6）。当前取值下 `1 × (240 + 18) = 258s`，相对 1800s 有 7 倍余量。**AC-3.6 被声明为正确性约束，其输入就该与实际最坏值一致**——否则 N 上调时会再次出现「式子算得过、实际不够」的同型问题（正是 CN-004 A 项刚修好的那类）。

### 变更 4（DevOps 中②）：AC-9.3 三态映射表补 v0.2 能力限定

AC-9.3 的状态码映射表中，`dead` 行的「托管层应有反应」列**补一句限定**：

> `dead` → HTTP 非 200 → 托管层应有反应：重启。**⚠️ v0.2 无自动消费方**——`Restart=on-failure` 只看进程退出码，worker 协程死亡时进程仍存活；消费该 503 的 healthcheck timer 顺延 v0.3。**v0.2 的 `dead` 靠人工或外部监控发现**，表中「重启」描述的是 v0.3 落地后的目标状态。

### 变更 5（DevOps 中③）：AC-6.3 日志落盘按 journal 订正

AC-6.3 的「v0.2 灰度期由 DevOps 指定落盘路径并人工轮转」**改写为**：

> 日志统一输出到 **stdout**，由托管层收集——**v0.2 起 systemd unit 使用 `StandardOutput=journal`，journald 自带轮转与配额**，无需指定落盘路径、无需人工轮转；**应用内不实现轮转**。
> > 原表述源自托管化顺延时期的 `nohup` 预设，托管化落地后已不适用（按原文会去配一套不需要的日志轮转）。应用侧行为不变（照样写 stdout）。

### 变更 6（PM 低③）：AC-6.1 字段清单补 `budget_remaining_ms`

AC-6.1 的日志字段中**新增**：

> `budget_remaining_ms` —— 该步骤结束时的剩余预算。**用于灰度期定位「预算被谁吃掉」**：`error_kind=budget_exhausted` 只能告知「预算耗尽了」，逐步的剩余预算才能定位是哪一段吃掉的，从而判断该调 `KB_TIMEOUT_MS` / `WEB_SEARCH_TIMEOUT_MS` 还是总预算。
