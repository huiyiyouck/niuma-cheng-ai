xiaobao Architect **主动撤回其上轮对 C-1 的答复并认账**：

其追到底的取数链路证明：`L1Input.domain_tags` **从来不是 L0 的产物**，而是**信息源级的静态领域标签**，真源在 `sources.domain_tags`（jsonb）：

```
sources.domain_tags (schema.ts:67)
  → l1-processor.ts:243      SELECT s.domain_tags
  → l1-processor.ts:257-278  归一化为 string[] → L1Input.domainTags
  → ai-hub.ts:45             → HTTP 请求体
```

`l0_label` 的真实语义也澄清了：一套规划好的枚举（`direct_display` / `normal_candidate` / `high_priority_candidate` / `needs_context_candidate` / 各类跳过原因 / NULL），但表达的是**「是否值得送 AI + 优先级 + 是否需补上下文」的处理决策，与领域分类无关**——ai 侧的判断方向被确认正确。

**ai 实测只看到 `direct_display` 一个值的原因**：L0 链路在两库都没成功跑过（xiaobao 侧 `l0_classify | failed | 8`，8 条全失败 0 条成功），加上生产 `ENABLE_AI_PROCESSING` 默认关闭、条目全走 `direct` 路径。那 8 条 L0 失败是 xiaobao 已登记的自身问题。

**结论**：`sources.domain_tags` 的 GRANT 已由 xiaobao DevOps 执行（契约已升 v1.5），**ai 与 HTTP 模式在该字段上完全等价——不是「近似」，更不是「恒空」**。CN-004 变更 1 建立在已被撤回的前提上，**整条作废**。

### 订正 1：变更 1 的「完全等价」→「取数路径等价，但冒烟数据下值仍为空」

**实机事实**（ai DevOps 2026-07-28 复验）：`sources` 全部 4 行中 **2 行 `domain_tags` 是 array（如 `["AI"]`）、2 行是 object `{}`**（列上无类型约束）；而**5 条待冒烟条目 JOIN 出的 source 全部是 `{}`**。

因此 xiaobao Architect「拿到该列后与 HTTP 模式完全等价」的结论**在当前测试数据上不成立**，PM 在变更 1 中逐字采纳该表述同样说早了。据实收紧为：

- ✅ **「取数路径等价」成立** —— DB 模式与 HTTP 模式读的是**同一列同一份数据**，差异的**成因**（此前误认为 `l0_label`）确已消除。
- ❌ **「值一定非空」不成立** —— 值取决于各 source 的配置；冒烟数据下**实际仍为空**。**联调时若期待它非空会误判。**
- ⚠️ **新增一条实现约束（必须保留）**：`{}` 是 object 不是 array，**若适配层按数组直接构造 `L1Input` 会触发 pydantic 校验失败 → 按设计 §4.4 归为 `MappingError(client_error)` → 不可重试直接 `final_failed`，5 条冒烟全部报废**。入向映射**须做 jsonb 类型判定**（仅 `isinstance(raw, list)` 时取用，否则 `[]`）。设计 §3.3 的归一化已覆盖该形态、无需改代码，但**必须写明**——否则实现时若「优化」成 `raw or []` 之类的写法就会踩上去。

**变更 1 的撤回动作本身仍然成立**（AC-8.2 原差异条与 CN-004 变更 1 仍应撤回）——因为差异的**成因**已消除；剩下的是**数据覆盖问题**，性质不同、处置也不同（见下）。

**新增待跟进（已请 xiaobao 确认）**：① `sources.domain_tags` 的**预期类型**（`{}` 是脏数据还是合法形态）；② 请其在测试库补几条 `domain_tags` 非空 source 下的待处理条目——**否则「有值」这条路径直到生产才会第一次被执行**。

### 订正 2：变更 2 的「多实例并发验证仍在 ai 侧待做」已完成，前置解除

**实机事实**（ai DevOps 2026-07-28 复验）：两会话同时 claim **拿到不同行**（`ee471923…` / `5b0e6f71…`），`SKIP LOCKED` 生效、**并发不重复领取**；越权 `UPDATE tasks SET type` 仍 `permission denied`；全程 `ROLLBACK`、队列未消耗（仍 5 条）。

即 **C-6 已完整闭合**——xiaobao DevOps 验的是权限侧（单会话可行性），**ai DevOps 补齐了并发侧**。据此：

- **列级 GRANT 足以支撑行锁**，xiaobao 预留的「改授 `tasks` 表级 UPDATE」**不必执行**。
- **PRD §4 的「v0.3 上多 worker 实例前必须先解决 C-6」前置可解除**（原因是 C-6 已解决，不是要求被放弃）。
- 变更 2 中「多实例并发验证仍在 ai 侧待做」「请贵方不要标为已彻底解决」两句**已过期**，PM 已在 coordination 回帖更正。
- **fallback 写法仍保留为备用**（不再是「因为 C-6 未闭合」，而是作为权限变更后的退路），其三条限定同样保留。
