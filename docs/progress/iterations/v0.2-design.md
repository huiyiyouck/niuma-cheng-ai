## 1. 概述

### 1.1 本设计要解决的问题

把 news-l1 的集成模式从「HTTP 同步调用」扩展为「数据库契约边界异步解耦」，且**不让 ai 被 xiaobao 的库 schema 绑死**。三条硬约束来自 PRD §1：并行而非替换、数据源协议隔离、schema 权属不越界；第四条是 R2 追加的 async 地基先行。

### 1.2 设计准则（Owner 2026-07-27 重申）

**按最健全的方式设计，而不是最省力的方式——高可用、高可靠、高复用。** 这是 PRD §0 准则在设计阶段的延续。本文档中凡出现多方案取舍，均按这三维裁定，并在 §7 逐条记录被放弃的省力方案与放弃理由。三维在本设计中的具体落点：

| 维度 | 本设计的落点 |
|------|------------|
| **高可用** | 三态探活（§4.9）+ worker task 异常不静默（§4.1）+ 优雅停机（§4.8）+ 启动自愈（§4.8）+ 单条 wall-clock 预算防止单条卡死拖垮整个 worker（§4.5） |
| **高可靠** | 三段式事务（§4.6）+ 写回幂等（`ON CONFLICT`）+ 退避真源唯一（读写 `tasks.run_after`）+ claim 原子性双写法（§3.4）+ 隔离级别显式断言 + **批量 N=1**（§4.3，单点故障影响面从 N 条降到 1 条） |
| **高复用** | 协议按职责分层（映射 / 拉取，§3.1-3.2）+ 源类型适配器注册表（§3.3，新增 source type 只加一个注册项）+ 处理核心零数据源概念（AC-2.2 静态判据）+ 第二调用方只需实现 `L1Mapper` |

## 2. 数据模型

> 本节的类型全部落在 `sources/base.py` 与 `worker/`，均为**进程内类型**，不是跨服务契约（跨服务契约是 `news-l1` HTTP v1 与 `news-l1-db` v1.4，两者本迭代均不改）。

### 2.1 SourceRecord — 数据源交给映射层的原始记录

> 数据源无关的中间表示。DB 数据源填它，HTTP 数据源不产生它（HTTP 的入向是恒等映射，见 §3.1）。

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `raw_item_id` | `UUID` | 必填 | `raw_items.id` |
| `source_type` | `str` | 必填 | `sources.type`，映射分发键（`x_twitter` / `rss` / `jin10_flash`） |
| `source_identity` | `str` | 必填 | `sources.identity` → `L1Input.source_identity` |
| `source_config` | `dict` | 默认 `{}` | `sources.config`，当前未消费，预留 |
| `content` | `dict` | 默认 `{}` | `raw_items.content` jsonb 原文 |
| `source_item_url` | `str \| None` | 可空 | `raw_items.source_item_url`，**规范化前**的原值 |
| `source_domain_tags` | `list[str]` | 默认 `[]` | **`sources.domain_tags`（jsonb）—— `L1Input.domain_tags` 的真源**（契约 v1.5 / C-14 订正，GRANT 已执行） |
| `l0_label` | `str \| None` | 可空 | `raw_items.l0_label`。**是 L0 处理决策标记，不是领域分类**（v1.5 订正）；v0.2 **不消费**，仅保留字段备 v0.3 评估 |
| `published_at` | `datetime \| None` | 可空 | `raw_items.published_at`，写回时回填（AC-4.6） |

### 2.2 ClaimedItem — claim 事务的产出

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `task_id` | `UUID` | 必填 | `tasks.id` |
| `record` | `SourceRecord` | 必填 | 同事务内读出，处理期间不再回查数据库 |
| `attempt` | `int` | 必填 | claim 后的值（已 +1） |
| `max_attempts` | `int` | 必填 | 读 `tasks.max_attempts`，**禁止硬编码**（AC-5.1） |

| `claimed_at` | `float` | 必填 | `time.monotonic()`，预算计时起点（**不用 wall clock，避免系统时钟跳变**） |

### 2.3 WriteBackPayload — 出向映射的产物

> `L1Output` → `processed_news` 列的映射结果。**这是唯一带列名的进程内类型，定义在 `sources/db/` 内**，处理核心不感知。

| 字段 | 类型 | 取值 | 依据 |
|------|------|------|------|
| `raw_item_id` | `UUID` | `ClaimedItem.record.raw_item_id` | AC-4.6 |
| `title` / `summary` / `analysis` | `str` / `str` / `str \| None` | `L1Output` 同名字段；`analysis` 为 `None` 时写 SQL `NULL`（**不写空串**） | AC-4.6、Q-3 |
| `translation` / `context` / `score_dimensions` | `jsonb` | `L1Output` 同名字段序列化 | AC-4.6 |
| `tags_v2` | `jsonb` | `{domain, entity, event, content_type, processing}` | AC-4.6、C-10 |
| `language` | `str` | 固定 `'zh'` | AC-4.6、C-7 |
| `published_at` | `datetime \| None` | `SourceRecord.published_at` | AC-4.6（双保险，归属声明见 PRD） |
| — | — | **`score_total` 与 `id` 不出现在本类型中** | AC-4.6、O-1 |

> **实现约束**：`score_total` 不得出现在 `INSERT` 列清单与 `DO UPDATE SET` 子句里——不是「写 NULL」，是**根本不提及**，否则 `ON CONFLICT DO UPDATE` 会把 xiaobao 已算好的值覆盖成 NULL。

### 2.4 ItemBudget — 单条 wall-clock 预算（AC-3.8）

| 字段 | 类型 | 说明 |
|------|------|------|
| `total_ms` | `int` | `L1_ITEM_BUDGET_MS`，见 §2.6 |
| `started` | `float` | `time.monotonic()` |
| `remaining_ms()` | `-> int` | `max(0, total_ms - elapsed)` |
| `exhausted()` | `-> bool` | `remaining_ms() <= 0` |
| `slice_for(段上限_ms)` | `-> int` | `min(段上限, remaining_ms())`；**若结果 < `MIN_SEGMENT_MS`（默认 1000）则返回 `0`**（R2 补，Developer 问题 4）；返回 `0` 表示该段必须跳过 |

`slice_for` 是本设计对「预算覆盖 pipeline 全程，而非各段独立超时之和」（AC-3.8.1）的实现手段——每个 IO 节点在发起调用前用它换取本段可用时间，而不是读各自的配置常量。

> **为什么需要最小段阈值**（R2 补）：若只判 `exhausted()`（`remaining <= 0`），当 `remaining = 300ms` 时该段不会被跳过，而是**用 300ms 去发起一次必然超时的调用**——超时按 AC-7.2 属「调用故障」，会产出 `degraded:kb_search_failed`。于是一条因预算耗尽而降级的记录看起来像 xiaobao 的 KB 服务挂了，**污染的正是本设计最看重的观测面**。加最小阈值后，「预算不足以支撑本段」统一走 `degraded:{tool}_budget_exhausted` + `error_kind=budget_exhausted`（CN-004 新增枚举），与真实工具故障彻底分开。

### 2.5 WorkerState — 三态机与在途进度（AC-9.3）

| 字段 | 类型 | 说明 |
|------|------|------|
| `state` | `Literal["running","stopping","dead"]` | 三态，映射见 §3.6 |
| `dead_reason` | `str \| None` | 仅 `dead` 时非空，脱敏后的异常摘要 |
| `last_poll_at` | `datetime \| None` | 每轮 claim 查询完成时更新（**无论是否取到条目**） |
| `in_flight` | `int` | 当前处理中的条目数（v0.2 恒为 0 或 1） |
| `current_item_started_at` | `datetime \| None` | 当前条目开始处理的时刻 |
| `consecutive_empty_polls` | `int` | 连续空轮次数，取到条目即归零。见下方「空转可观测性」 |
| `lock_token` | `str` | `{worker_id}#{run_token}`，见下 |

**空转可观测性（据 DevOps 实机发现 A 补）**：DevOps 2026-07-28 实机核出 `tasks` 中 `l1_ai_process` 类型记录数为 **0**——5 条预置 `raw_items` 没有对应 task 行，按 AC-3.1 的 claim 条件**永远领不到**。这暴露了一个设计层面的观测盲区：按 C-5 结论 ai **不做孤儿探测**（不扫 `raw_items`），因此「队列真的空」与「队列有货但没有 task」在 ai 侧表现完全相同——worker 正常空转、`/health` 200、`last_poll_at` 正常刷新，运维看不出任何异常。

处置（不违反「不做孤儿探测」——只报告自身状态，不查 `raw_items`）：worker 每轮记录 `consecutive_empty_polls`，达到阈值（`L1_EMPTY_POLL_WARN`，默认 **20** 轮 ≈ 5 分钟）时打一条 WARN 日志并在 `/health` 暴露该计数。运维据此可判断「ai 侧一直没活干」，再由 PM/DevOps 与 xiaobao 侧核对队列——把一个静默状态变成可见信号，成本仅一个计数器。

---

**`lock_token`（O-10 落定）**：格式 `{worker_id}#{run_token}`。
- `worker_id`：**稳定身份**，取 `AI_WORKER_ID` 配置，默认 `socket.gethostname()`。同一部署位置跨重启不变。
- `run_token`：**本次进程运行标识**，取进程启动时刻的 `time.time_ns()` 十六进制短串。每次启动都不同。
- 写入 `tasks.locked_by`（`text` 列，长度充裕）。

三种匹配语义因此可以精确区分，直接支撑 AC-5.6 的自愈口径：

| 库中 `locked_by` | 含义 | 处置 |
|---|---|---|
| `worker_id` 相同 **且** `run_token` 相同 | 当前进程持有 | 不动 |
| `worker_id` 相同 **但** `run_token` 不同 | **我上次进程留下的残留锁** | 启动时自愈回收（不越权） |
| `worker_id` 不同 | 他人的锁 | **一律不碰**，交 xiaobao 1800s 回收 |

> 若只用 `hostname:pid` 会误判（pid 会复用）；若把启动时间揉进 `worker_id` 则自愈永远匹配不到自己上次的锁——分成稳定段与运行段是这条 AC 能同时满足「能自愈」与「多实例安全」的前提。

| `KB_TIMEOUT_MS` / `WEB_SEARCH_TIMEOUT_MS` | `15000` / `20000` | `> L1_MIN_SEGMENT_MS` | 工具段上限（§4.5），由 v0.1 透传的 180s 收紧而来 |
| `L1_WRITEBACK_RETRY` / `L1_WRITEBACK_RETRY_DELAY_MS` | `2` / `1000` | `≥0` / `≥0` | 写回事务的瞬时故障有限重试（§4.6，R2 补） |

**配置校验是启动门禁**（AC-3.6「配置校验中拒绝超限取值」）：上表带不等式的约束在进程启动时一次性校验，任一不满足即**拒绝启动**并打印算式，不允许 WARN 后继续——它们是正确性约束，不是调优建议。

**`DB_OP_BOUND` 的定义（R2 定稿前补，AC-4.7）**：单条处理链路上数据库操作的最坏耗时上界

```text
DB_OP_BOUND = (L1_WRITEBACK_RETRY + 1) × (AI_DB_STATEMENT_TIMEOUT_MS + L1_WRITEBACK_RETRY_DELAY_MS)
            = (2 + 1) × (8000 + 1000)  ... 保守口径
当前取值下按 DevOps 给出的自洽算式：2 × (8s + 1s) = 18s ≤ §4.8 的 20s 收尾余量 ✔
```

须同时满足两条不等式，二者都进启动门禁：

| # | 不等式 | 当前取值 |
|---|--------|---------|
| 1 | `DB_OP_BOUND ≤` §4.8 的收尾余量（`L1_SHUTDOWN_GRACE_MS − N × L1_ITEM_BUDGET_MS`） | `18s ≤ 20s` ✔ |
| 2 | `N × (L1_ITEM_BUDGET_MS + DB_OP_BOUND) < 1800s × 0.6` | `1 × 258s = 258s < 1080s` ✔（7 倍余量） |

> **为什么必须补这一项**（DevOps R2 问题 1，我接受该判断）：`ItemBudget` 只覆盖**处理阶段**，claim 与写回两个事务在所有预算之外。§4.6 原写的「重试总耗时（≤2s）」**只在每次重试立即失败时成立**——而重试的触发条件里 `deadlock_detected` / `serialization_failure` 本质就是**锁等待**，无 `lock_timeout` 时 PostgreSQL 会无限等。这不是理论风险：写回三表时，xiaobao 的 1800s 卡死回收可能正在 UPDATE 同一行 `tasks`，两侧对同一行的写竞争是这套契约的固有面。**我给处理阶段设了 240s 封顶，却默认了「数据库操作总是快的」——这是设计的一处真实算式漏项。**

> `L1_SHUTDOWN_GRACE_MS` 默认 260000（≈ 4.3 分钟）= `1 × 240000` + 20s 收尾余量，同时满足 `< 1800000`。三层一致性（应用 / ASGI / 托管）见 §4.8。

### 3.1 `L1Mapper` — 映射协议（两种模式均真实实现）

```python
# src/agent_hub/sources/base.py
from typing import Protocol, Any
from agent_hub.schemas import L1Input, L1Output

class L1Mapper(Protocol):
    """数据来源 ↔ 处理核心 的双向映射。第二个调用方接入时，这是唯一需要实现的协议。"""

    def to_l1_input(self, record: Any) -> L1Input:
        """源记录 → 处理输入。允许恒等映射（见 AC-2.1 CN-003 澄清）。
        失败须抛 MappingError(kind='client_error')——不可重试（AC-2.5）。"""

    def from_l1_output(self, output: L1Output, ctx: Any) -> Any:
        """处理输出 → 落地表示。DB 侧产出 WriteBackPayload，HTTP 侧产出 RunResponse。
        失败须抛 MappingError(kind='server_error')——可重试（AC-2.5）。"""
```

| 实现 | `to_l1_input` | `from_l1_output` |
|------|---------------|------------------|
| `HttpL1Mapper`（`sources/http_source.py`） | **恒等**：入参已是 FastAPI 反序列化好的 `L1Input`，原样返回。这是真实实现，明确表达「HTTP 数据源入向无需转换」（AC-2.1 CN-003 澄清） | 包装为 `RunResponse`（含 `run_id` / `status` / `elapsed_ms` / `tool_summary`），**有实质逻辑** |
| `DbL1Mapper`（`sources/db/source.py`） | `SourceRecord` → `L1Input`，按 `source_type` 分发到适配器（§3.3） | `L1Output` → `WriteBackPayload`（§2.3） |

**`MappingError`**（`sources/base.py`）：`kind: Literal["client_error","server_error"]` + 脱敏 `message`。入向失败不可重试直接最终失败、出向失败可重试——这是 AC-2.5 的载体。

### 3.2 `PullSource` — 拉取型数据源协议（仅 pull 型实现）

```python
class PullSource(Protocol):
    """主动拉取型数据源。HTTP 模式不实现、也不假装实现（AC-2.1）。"""

    async def fetch_batch(self, n: int) -> list[ClaimedItem]:
        """原子领取至多 n 条并置为处理中。无可领条目时返回 []（不是异常，AC-3.4）。"""

    async def commit_success(self, item: ClaimedItem, payload: WriteBackPayload) -> None:
        """单事务写回结果 + 推进状态 + 释放锁（AC-4.3/4.4）。"""

    async def mark_failed(self, item: ClaimedItem, *, error_kind: str,
                          message: str, retryable: bool) -> None:
        """单事务标记失败 + 退避 + 释放锁（AC-5.3/5.4）。retryable 与 attempt/max_attempts
        共同决定落 retryable_failed 还是 final_failed。"""

    async def release(self, item: ClaimedItem) -> None:
        """主动释放一个「已 claim、未开始处理」的条目（停机路径，R2 补）。
        单事务退回 queued + 清锁，且【不动 attempt、不写 last_error】——它既非成功也非失败。"""

    async def reclaim_own_stale_locks(self) -> int:
        """启动自愈：仅回收 worker_id 相同、run_token 不同的残留锁（AC-5.6）。返回回收条数。"""
```

> **`release` 为什么不能复用 `mark_failed(retryable=True)`**（R2 补，Developer 问题 1）：正常停机时释放一个还没开始处理的条目，若走失败路径会污染 `attempt` 与 `last_error_kind`——一次正常停机在 xiaobao 侧看起来像一次处理失败，且白白消耗一次重试配额。N=1 时该分支几乎不触发（`items` 只有一条），但 `L1_CLAIM_BATCH_SIZE` 是可配项，N>1 且停机时必然走到，且 §4.2 主循环已经调用了它——协议缺这个方法，实现会直接撞 `AttributeError`。

> 五个方法**全部真实实现于 `DbPullSource`**，HTTP 侧不出现该协议。这就是「按职责分层、不按模式对称」（O-2 落定）的形态：HTTP 模式只有 `L1Mapper`，DB 模式有 `L1Mapper` + `PullSource`。

#### `domain_tags` 映射规则（**R2 定稿后据 C-14 重写**，契约 v1.5）

**真源是 `sources.domain_tags`，不是 `raw_items.l0_label`。** 取到它之后，DB 模式与 HTTP 模式**读的是同一列同一份数据，取数路径等价**——但**值本身取决于各 source 的配置，不等于「一定非空」**（见下方实机订正）。

xiaobao Architect 于 2026-07-28 撤回其 v1.3 的错误结论并追出了 HTTP 模式的完整取数链路：

```text
sources.domain_tags (jsonb, schema.ts:67)
  → l1-processor.ts:243      SELECT s.domain_tags
  → l1-processor.ts:257-278  归一化为 string[] → L1Input.domainTags
  → ai-hub.ts:45             domain_tags: input.domainTags → HTTP 请求体
```

即 **`L1Input.domain_tags` 从来不是 L0 的产物，而是信息源级的静态领域标签**；`l0_label` 是「是否值得送 AI + 优先级 + 是否需补上下文」的处理决策标记，两者语义无关。`GRANT SELECT (domain_tags, attention_level) ON sources` 已由 xiaobao DevOps 在 test + prod 双库执行并 verify。

```python
# sources/db/adapters.py
def map_domain_tags(raw) -> list[str]:
    """sources.domain_tags(jsonb) → list[str]。与 xiaobao l1-processor.ts:257-278 的归一化对齐。"""
    if not isinstance(raw, list):
        return []                                   # NULL / 非数组 → 无标签
    return [s.strip() for s in raw if isinstance(s, str) and s.strip()]
```

| `sources.domain_tags` 实际值 | `domain_tags` | 理由 |
|---|---|---|
| `["AI", "芯片"]` | `["AI", "芯片"]` | 正常路径，与 HTTP 模式等价 |
| **`{}`（jsonb object）** | `[]` | **实机确认存在该形态**——`sources` 4 行中 2 行是 `{}`；`isinstance({}, list)` 为假故自然落到 `[]`。**这条不是理论分支**，见下 |
| `NULL` / 其他非数组 / `[]` | `[]` | 该源未配领域标签 |
| 数组内含空串 / 非字符串元素 | 过滤掉该元素 | `['']` 是真值，会穿过 `news_l1.py:206` 的 `or None` 并把空标签传给 KB 检索（Developer R3 问题 5 的同型风险，来源换了但风险不变） |

> **实机订正（2026-07-28，ai DevOps 复验）—— 「完全等价」这个说法当时下早了。** 实测 `sources` 全部 4 行中 **2 行 `domain_tags` 是 array（如 `["AI"]`）、2 行是 object `{}`**（列上无类型约束）；而 **5 条待冒烟条目 JOIN 出的 source 全部是 `{}`**。两个后果：① **冒烟阶段 `domain_tags` 实际仍为空**——「取数路径等价」成立，「值非空」不成立，联调时若期待它非空会误判；② `{}` 是 object 不是 array，**若适配层按数组直接构造 `L1Input` 会触发 pydantic 校验失败 → 按 §4.4 归为 `MappingError(client_error)` → 不可重试直接 `final_failed`，5 条冒烟全部报废**。

### 3.4 claim SQL（两种写法，实证后二选一）

> **C-6 已完整闭合（2026-07-28），采用写法 A。** 两侧各验一半：xiaobao DevOps 验**权限侧**（以 `ai_worker` 实测 `FOR UPDATE SKIP LOCKED` + claim 写入返回 `UPDATE 1`，列级 GRANT 支撑行锁、`FOR UPDATE` 不需要表级 UPDATE 权限）；**ai DevOps 补齐并发侧**（两会话同时 claim 拿到**不同行** `ee471923…` / `5b0e6f71…`，`SKIP LOCKED` 生效、并发不重复；越权 `UPDATE tasks SET type` 仍 `permission denied`；全程 `ROLLBACK`、队列未消耗）。
> **因此：xiaobao 预留的「改授 `tasks` 表级 UPDATE」不必执行；PRD §4 的「v0.3 多实例前必须先解决 C-6」前置可解除**（原因是它已被解决，不是要求被放弃）。**写法 B 仍保留为备用**——不再因为「C-6 未闭合」，而是作为将来权限变更后的退路，其三条限定同样保留。
> §8 测试 6 的定位随之调整：从「待做的前置验证」变为**实现阶段的回归确认**（对真实 PG 跑，确认代码实现与实机验证一致）。

**写法 A（首选，✅ C-6 实证通过，本迭代采用）**

```sql
-- 事务内步骤 1：选行并加锁
SELECT id, raw_item_id, attempt, max_attempts
FROM tasks
WHERE type = 'l1_ai_process'
  AND status = 'queued'
  AND run_after <= now()
  AND raw_item_id IS NOT NULL
ORDER BY priority DESC, run_after ASC      -- 走 ix_tasks_queue；priority 数值大=优先（C-11 已确认）
LIMIT %(n)s
FOR UPDATE SKIP LOCKED;

-- 步骤 2：置为处理中
UPDATE tasks
SET status='running', attempt = attempt + 1,   -- ★ 枚举取 C-2 契约值；见 §7.2 的 6j 风险
    locked_by = %(lock_token)s, locked_at = now(), updated_at = now()
WHERE id = ANY(%(ids)s);
```

> **`status` 取值的一处待确认（6j）**：契约 C-2 给的枚举是 `running`，而 xiaobao 的 C-6 实证 SQL 写的是 `processing`，且 `tasks` **无 CHECK 约束**（写错不报错）。**本设计按契约取 `running`**；已请对方确认后端实际读哪个值。冒烟时须重点核对「对方状态是否随之推进」——这类不一致不会有任何报错，只表现为对方状态不动。

**写法 B（备用，本迭代不采用；保留作 v0.3 权限收紧时的退路）**

```sql
UPDATE tasks
SET status='running', attempt = attempt + 1,
    locked_by = %(lock_token)s, locked_at = now(), updated_at = now()
WHERE id IN (
  SELECT id FROM tasks
  WHERE type = 'l1_ai_process' AND status = 'queued'
    AND run_after <= now() AND raw_item_id IS NOT NULL
  ORDER BY priority DESC, run_after ASC
  LIMIT %(n)s
)
AND status = 'queued'                       -- 关键：并发下后到者在此被排除
RETURNING id, raw_item_id, attempt, max_attempts;
```

**写法 B 的三条限定（AC-3.7 CN-003）必须在实现中体现**：
1. 并发下后到者**本轮拿空批**（`RETURNING` 0 行），不是拿到其他行 → 属正常情况，按「无可领条目」处理，**不得记为错误**。
2. **只在 `READ COMMITTED` 下正确**（依赖 EvalPlanQual 重新求值）。§4.10 的连接池必须显式断言隔离级别。
3. 多实例下并发语义与 `SKIP LOCKED` **不等价**——此限定对写法 B 本身依然成立（后到者拿空批 ⇒ 吞吐不随实例数增长）。**但它已不再是 v0.3 多实例的阻塞前置**：C-6 已完整闭合（见上），v0.3 多实例直接用写法 A 即可，无需先解决 C-6。

**两种写法之后的共同步骤（同一事务内）**：

```sql
-- 步骤 3：读取处理所需的全部数据（此后处理期间不再回查数据库）
SELECT ri.id, ri.content, ri.published_at, ri.source_item_url, ri.l0_label,
```

### 3.6 `/health` 契约（AC-9.3 三重探活）

| `worker_state` | HTTP 状态码 | 语义 | 托管层应有反应 |

| `stopping` | **200** | 收到停机信号、正在收尾 | **等待**（配合 `TimeoutStopSec`），不得重启 |
| `dead` | **503** | worker 协程已异常退出 | 重启 —— **⚠️ v0.2 无自动消费方**，见下 |

> **`dead` 在 v0.2 靠人工发现**（R2 定稿前补，DevOps R2 问题 2）：systemd 的 `Restart=on-failure` 只看**进程退出码**，而 worker 协程死亡时进程仍存活（这正是 §4.1 `_on_worker_done` 处理的场景），systemd 不会有任何动作；消费该 503 的 healthcheck timer 顺延 v0.3。因此上表「重启」描述的是 **v0.3 落地后的目标状态**，v0.2 的真实链路是「worker 已死 → `/health` 503 → 没有任何东西在读它 → 靠人工 curl 或外部监控发现」。这与 PRD §4「只能人工看护灰度、不得无人值守」是同一个已知取舍——**写在这里是为了让灰度期运维知道自己必须主动看**。

响应体：

| 字段 | 类型 | 说明 |
|---|---|---|
| `status` | `str` | `ok` / `stopping` / `dead` |
| `service` | `str` | `niuma-cheng-ai`（保持 v0.1 形状，兼容既有冒烟） |
| `mode` | `str` | `http` / `db` |
| `worker_state` | `str \| null` | HTTP 模式为 `null`（无 worker） |
| `last_poll_at` | `str \| null` | ISO8601 |
| `in_flight` | `int` | 在途条目数 |
| `current_item_started_at` | `str \| null` | ISO8601 |
| `consecutive_empty_polls` | `int` | 连续空轮次数；持续增长说明 ai 侧一直没领到活（见 §2.5「空转可观测性」） |
| `self_heal_failed` | `bool` | 启动自愈是否失败（R2 补，DevOps 问题 3）。为真表示有本进程上次残留的锁未被提前回收，将由 xiaobao 1800s 兜底 |
| `stale_tolerance_ms` | `int` | `N × L1_ITEM_BUDGET_MS + L1_POLL_INTERVAL_MS`，**由服务端算好给运维**，避免两侧各算一遍算错 |

**判读顺序（R2 补，DevOps 问题 4）——必须先看 `worker_state`，再看时间戳：**

| `worker_state` | `last_poll_at` 陈旧如何判读 |
|---|---|
| `running` | **`stale_tolerance_ms` 仅在此态下适用**；超出即异常 |
| `stopping` | **陈旧属预期**——收尾期间 worker 不再 poll，`last_poll_at` 最长陈旧至宽限期（260s，已超 255s 阈值）。此时**不得按阈值判死** |
| `dead` | 直接由 HTTP 503 表达，不必看时间戳 |

> 这条同时是 v0.3 healthcheck timer 的实现前提：若探针只看 `last_poll_at` 与 `stale_tolerance_ms` 而不先看状态，会在优雅停机窗口内把正常收尾的进程判为异常——与 §4.8 的三层时限问题是同一类错误的两种表现。
| `dead_reason` | `str \| null` | 脱敏摘要 |

**HTTP 模式必须在 ≤2s 内返回，DB 模式在单条处理进行中（≥60s）时同样必须 ≤2s 返回**（AC-9.3 抗阻塞）——这是 async 改造彻底性的运行时闸门。

## 4. 核心流程

### 4.1 进程启动与 worker 托管（AC-1、AC-9.3）

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = load_and_validate_config()        # 不变式不满足 → 直接拒绝启动
    app.state.worker = WorkerState(lock_token=make_lock_token(settings))

    if settings.run_mode == "db":
        pool = await create_pool(settings)       # §4.10
        source = DbPullSource(pool, settings)

        try:                                     # ★ 自愈失败不得阻止服务启动（R2 订正）
            n = await source.reclaim_own_stale_locks()   # 启动自愈（AC-5.6）
            log.info("self_heal_done", reclaimed=n)
        except Exception as exc:
            log.error("self_heal_failed", error_kind=classify(exc), error=redact(exc))
            app.state.worker.self_heal_failed = True     # 进 /health，运维可见

        task = asyncio.create_task(worker_loop(source, app.state.worker, settings))
        task.add_done_callback(partial(_on_worker_done, app.state.worker))   # ★ 关键
        app.state.worker_task = task

    yield                                        # ← 服务运行中

    if settings.run_mode == "db":
        app.state.worker.request_stop()          # → stopping
        await _await_worker(task, settings.shutdown_grace_ms)   # §4.8
        await pool.close()
```

**`_on_worker_done` 是 AC-9.3「worker 生死」的实现核心**：

```python
def _on_worker_done(state: WorkerState, task: asyncio.Task) -> None:
    if task.cancelled():
        state.mark_dead("cancelled"); return
    exc = task.exception()                       # ★ 必须取出，否则异常被静默吞掉
    if exc is not None:
        log.error("worker_loop_crashed", error_kind=classify(exc), error=redact(exc))
        state.mark_dead(redact(exc))
    else:
        state.mark_stopped()                     # 正常退出（停机路径）
```

> 不调 `task.exception()` 时，`asyncio` 只会在 task 被 gc 且异常从未取出时于 stderr 打一行 `Task exception was never retrieved`——进程、HTTP、`mode` 全部正常，`/health` 会完整地报告「健康」，托管层永远不会重启它。这正是 Architect R3 问题 4 指出的失效模式，`add_done_callback` + `task.exception()` 是它的直接解法。

> **自愈失败为什么不能 fail-fast**（R2 订正，DevOps 问题 3）：`reclaim_own_stale_locks()` 抛异常会让 lifespan 启动失败 → 进程退出 → systemd `Restart=on-failure` 拉起 → 再失败 → `StartLimitBurst` 后置 failed，**服务完全不可用**。而自愈失败的实际后果很轻：只是上次进程的残留锁没被提前回收，xiaobao 侧 1800s 卡死回收会兜底（自愈本就只是**加速自己那部分**）。为一个加速项失败而拒绝提供服务，取舍是反的——尤其自愈失败最可能的原因正是 DB 短暂抖动，那时更该让服务起来重试。

**HTTP 模式**：不创建 worker task，不建连接池，`worker_state` 为 `null`，端点行为与 v0.1 等价（AC-1.1）。

### 4.2 worker 主循环（`worker/loop.py`）

```text
while state.state == "running":
    items = await source.fetch_batch(N)          # §4.3
    state.touch_poll(claimed=len(items))         # 更新 last_poll_at 与 consecutive_empty_polls
    if not items:
        if state.consecutive_empty_polls == EMPTY_POLL_WARN:   # 只在跨过阈值时打一次，不刷屏
            log.warning("queue_idle", consecutive_empty_polls=..., minutes=...)
        await sleep_interruptible(poll_interval) # 可被停机信号立即打断
        continue
    for item in items:
        if state.state != "running":             # 停机时不再开始新条目
            await source.release(item); continue
        await process_one(source, item, state)   # §4.4~4.7
```

**取到条目后不 sleep，立即进入下一轮 claim** —— 队列有积压时不浪费轮询间隔；只有空队列才等待。这是 N=1 不损失吞吐的前提（ADR-0004）。

### 4.3 claim（AC-3，含 O-3 落定的 N）

流程即 §3.4 的四个步骤，全部在**一个短事务**内完成（毫秒级），提交后立即释放连接回池。

**O-3 落定：`L1_CLAIM_BATCH_SIZE = 1`**（推翻 PRD 的暂定值 8，PRD AC-3.6 已授权 O-3 重算）。完整论证见 [ADR-0004](../../knowledge/decisions/0004-item-wall-clock-budget-and-batch-size.md)，结论摘要：

- **v0.2 批内串行（PRD §4 明确），N > 1 不带来任何吞吐收益**——8 条串行处理的总时间与逐条 claim 8 次完全相同，多出的只是 7 次毫秒级 SELECT（相对 240s 的单条处理不足 0.01%）。
- **N > 1 把风险放大 N 倍**：批内最后一条的持锁时长 ≈ `N × 单条预算`；且 worker 若在处理第 1 条时崩溃，**其余 N-1 条根本没被处理却同样被锁 30 分钟**。
- 代入不变式：`N=1` 时 `1 × 240s = 240s`，相对 1800s 卡死阈值有 **7.5 倍余量**；`N=8` 时 `1920s > 1800s`，**用本设计的预算值直接违反 AC-3.6**。
- 配置项保留且校验不变式，v0.3 批内并发落地后可上调——**不是把能力删掉，是把默认值放在正确的位置**。

### 4.4 入向映射（AC-2.4、AC-8.2）

`SourceRecord` → `L1Input`：按 `source_type` 查注册表取适配器（§3.3）→ 组装 `raw_content`（含规范化 URL）→ 填 `domain_tags`（空值兜底 `[]`）→ 预取字段置空。任一必填缺失或类型不符 → 抛 `MappingError(kind="client_error")` → §4.7 按**不可重试**处理。

### 4.5 处理与 deadline 传递（AC-3.8）

处理阶段调用 `await run_task("news-l1", run_id, l1_input, client=..., tools=..., budget=budget)`——`run_task` 签名新增一个 `budget` 参数（**这是数据源无关的量，不违反 AC-2.2**）。

`ItemBudget` 随 `L1State` 流经各节点，每个 IO 节点发起调用前换取本段时间：

| 节点 | 段上限 | 实际使用 |
|---|---|---|
| `kb_search` | `KB_TIMEOUT_MS`（新增，默认 `15000`） | `budget.slice_for(15000)` |
| `link_read` | 8000（沿用 v0.1） | `budget.slice_for(8000)` |
| `web_search` | `WEB_SEARCH_TIMEOUT_MS`（新增，默认 `20000`） | `budget.slice_for(20000)` |
| `llm_process` | 剩余全部 | **`complete_json(messages, timeout_ms=budget.remaining_ms())`**（R2 订正，见下） |

- 任一节点进入时 **`budget.slice_for(段上限) == 0`**（含 `remaining` 低于 `L1_MIN_SEGMENT_MS` 的情形）→ **跳过该节点**，记 `degraded:{tool}_budget_exhausted` + `error_kind=budget_exhausted`，继续后续流程（部分可用语义不变）。
- `llm_process` 进入时预算已耗尽 → 无法产出结果 → 整条放弃：**`error_kind=budget_exhausted`**（CN-004 新增枚举，与「某次外部调用自身超时」的 `timeout` 区分开），走 §4.7 可重试路径。
- 三个工具的段上限**显著小于 v0.1 的 180s**：v0.1 把 `options.timeout_ms`（默认 180s）直接透传给 kb/web，是单条最坏 548s 的主因（CN-003 A 项）。收紧后各段之和（15+8+20=43s）仅占预算 18%，把绝大部分预算留给 LLM 及其 fallback 链。
  > **范围声明（R2 补，PM 范围核查）**：段上限收紧改的是**超时参数**，不是评分 / 标签 / 摘要 / 翻译的算法逻辑，**不属于 PRD §4「不做主链路算法变更」的红线**；且它是 AC-3.8 预算机制的必要构成（不收紧则单条上限无从保证）。此处显式声明，避免实现或验收时被误判为触碰红线。

**LLM 预算的传递路径（R2 订正，Developer 问题 3）**：走 `complete_json` 的**按次入参**，不是 `ChainedAIClient` 的构造参数。

- `budget_ms` 是 `ChainedAIClient.__init__` 的构造参数（`client.py:88-93`），而 `ItemBudget.remaining_ms()` **每条都不同**——走构造参数就要么每条重建 client（`build_ai_client()` 每次重读配置、重装 provider 链），要么把它改成可变属性，两者都是多余改造。
- `client.py:99` 本就是 `budget = timeout_ms if self._budget_ms is None else min(self._budget_ms, timeout_ms)`——**按次传入的 `timeout_ms` 就是这条链的总预算**。
- **v0.1 的「链共享预算」语义本就正确实现了**（`client.py:101-111`：每个 provider 前算 `remaining = budget - elapsed`，`remaining <= 0` 记 `budget_exhausted` 并 break，`call_timeout = min(provider.timeout_ms or remaining, remaining)`）。因此 AC-3.8 注中的「v0.1 未传」应精确理解为：**构造参数 `budget_ms` 从未被使用**（`build_ai_client()` 不传，`client.py:215`），而 `complete_json` 的 `timeout_ms` 一直在传（`news_l1.py:333` 传 `inp.options.timeout_ms`，默认 180s）。
- **所以本迭代在这一处只需一行改动**：把 `news_l1.py:333` 的入参从 `inp.options.timeout_ms` 换成 `budget.remaining_ms()`。链内递减分配无需任何改动。

### 4.6 写回事务（AC-4，O-6 落定）

单事务内三步，顺序固定：

```sql
BEGIN;  -- READ COMMITTED
INSERT INTO processed_news (raw_item_id, title, summary, translation, context,
                            analysis, score_dimensions, tags_v2, language, published_at)
VALUES (...)
ON CONFLICT (raw_item_id) DO UPDATE SET
  title=EXCLUDED.title, summary=EXCLUDED.summary, translation=EXCLUDED.translation,
  context=EXCLUDED.context, analysis=EXCLUDED.analysis,
  score_dimensions=EXCLUDED.score_dimensions, tags_v2=EXCLUDED.tags_v2,
  language=EXCLUDED.language, published_at=EXCLUDED.published_at;
  -- ★ score_total 与 id 不出现在任何位置

UPDATE raw_items SET l1_status='completed', l1_processed_at=now()
WHERE id = %(raw_item_id)s;                    -- l1_attempt 已在 claim 事务递增，此处不再动

UPDATE tasks SET status='succeeded', locked_by=NULL, locked_at=NULL,
                 updated_at=now() WHERE id = %(task_id)s;
COMMIT;
```

**三段式的边界（O-6 落定）**：claim 短事务（§4.3）→ 处理**无事务、无连接**（§4.5）→ 写回短事务（本节）。LLM 调用绝不持有数据库事务或连接。

**写回失败的有限重试（R2 补，Developer 问题 6）**：写回事务失败时重试 `L1_WRITEBACK_RETRY` 次（默认 2，间隔 1s），**仅对可重试的 PG 错误类**（连接错误 / `deadlock_detected` / `serialization_failure`）；确定性错误（约束冲突、权限拒绝）不重试。全部失败后再落到「保持 `running`/`processing`、由启动自愈或 xiaobao 1800s 兜底」的既有路径。

> **为什么必须重试**：此时这条结果已经花掉了 **240s 预算 + 一次完整 LLM 调用（含费用）**，而写回事务本身是毫秒级的——因为一次可能只持续几毫秒的连接抖动就整个丢弃，并且让该条目再占用队列 30 分钟，与 §1.2 的「高可靠」准则不一致。DB 写回失败绝大多数是瞬时故障，重试成功率高而成本可忽略。
> **重试须在 `ItemBudget` 之外**：结果已经产出，不再受单条预算约束；但重试总耗时要计入 §4.8 的停机宽限期余量。
> **重试耗时的上界由参数推导，不是常数**（R2 定稿前订正，DevOps R2 问题 1）：原写「≤2s」**只在每次重试立即失败时成立**，而 `deadlock_detected` / `serialization_failure` 本质是锁等待、无 `lock_timeout` 时会无限等。上界为 `DB_OP_BOUND`（§2.6），当前取值 **18s ≤ 20s 收尾余量**，由启动门禁强制。

### 4.7 失败、退避与最终失败（AC-5）

| 情形 | `retryable` | `tasks` | `raw_items` |
|---|---|---|---|
| 入向映射失败（`client_error`） | 否 | `status='failed'` | `l1_status='final_failed'` + `l1_error` |
| 出向映射失败（`server_error`） | 是 | 见下 | 见下 |
| 预算耗尽（`budget_exhausted`）/ LLM 全 provider 失败 / 工具层不可用 | 是 | 见下 | 见下 |
| **主动释放（停机路径，非失败）** | — | `status='queued'`，**`attempt` 不动、`last_error` 不写** | `l1_status='queued'`，清锁 | 
| DB 写回失败（重试耗尽后） | 事务回滚，条目保持 `running`/`processing`，由**下一次启动自愈**或 xiaobao 1800s 回收 | — | — |

> **「主动释放」必须与失败路径分开**（R2 补，Developer 问题 1）：它对应 §3.2 的 `release()`，语义是「停机时把一个还没开始处理的条目原样退回队列」——既不是成功也不是失败。走 `mark_failed(retryable=True)` 会污染 `attempt` 与 `last_error_kind`，使一次正常停机在 xiaobao 侧看起来像一次处理失败，并白白消耗一次重试配额。

可重试且 `attempt < max_attempts`：

```sql
UPDATE tasks SET status='queued',
                 run_after = now() + %(backoff)s,     -- 退避真源，禁止 ai 自算公式之外的推导
                 last_error = %(redacted)s, last_error_kind = %(kind)s,
                 locked_by = NULL, locked_at = NULL, updated_at = now()
WHERE id = %(task_id)s;
UPDATE raw_items SET l1_status='retryable_failed', l1_error=%(redacted)s
WHERE id = %(raw_item_id)s;                    -- l1_attempt 已在 claim 事务递增，此处不再动
```

**退避取值**：`BACKOFF = [60s, 300s, 900s]`；`attempt` 超出数组长度时**取末值 900s**（AC-5.2 CN-003，因 `tasks.max_attempts` schema 默认为 5 而数组长度为 3）。索引用 `BACKOFF[min(attempt, len(BACKOFF)) - 1]`，禁止取 0、禁止越界崩溃。

`attempt >= max_attempts`：`tasks.status='failed'`、`raw_items.l1_status='final_failed'` + `l1_processed_at=now()`。

### 4.8 优雅停机与启动自愈（AC-5.6、AC-5.7）

**停机**：SIGTERM → `state.request_stop()`（→ `stopping`，`/health` 仍 200）→ 循环不再开始新条目 → 当前条目跑完并正常写回 → task 退出 → uvicorn 关闭。

- 宽限期 `L1_SHUTDOWN_GRACE_MS ≥ N × L1_ITEM_BUDGET_MS`（默认 260s ≥ 240s）。
- **三层逐层放大，不是数值相等**（R2 订正，DevOps 问题 1）：

  ```text
  应用层 grace (260s)  ≤  uvicorn --timeout-graceful-shutdown (≥260s)  <  systemd TimeoutStopSec (280s)
  ```

  | 层 | 语义 | 取值 |
  |---|---|---|
  | 应用层 `L1_SHUTDOWN_GRACE_MS` | worker 收到停机信号后**最多用多久收尾**（跑完当前条目 + 写回事务及其重试） | 260s |
  | ASGI 层 `--timeout-graceful-shutdown` | uvicorn 等待在途请求与 lifespan 收尾的上限 | ≥ 260s |
  | 托管层 systemd `TimeoutStopSec` | 从发出 SIGTERM 到**发出 SIGKILL** 的墙钟 | **280s**（= 应用层 + 20s 收尾余量） |

  > **为什么不能取同一个值**：三者语义不同。若应用层与托管层都配 260s，当 worker 恰好用满 260s 完成最后一次写回时，systemd 在同一时刻 SIGKILL——**写回事务可能在 COMMIT 之前被杀**，留下 `l1_status='processing'` 的残留锁等 1800s 回收。这正是整条优雅停机链要防的事，却会因为「三个数字写成一样」而发生。
  > 原 R1 的「三层配一致值」表述源自 DevOps R3 高②，其本意是「三层必须协调、不能各自为政」，字面被读成了数值相等——**DevOps 已认领该表述责任**，本轮据其建议订正为逐层放大。DevOps 已提交的 unit（`niuma-ai-worker@.service`）按 `TimeoutStopSec=280` 写，与本节一致。

- **三层一致性的强制点在部署脚本，不在应用启动校验**（R2 补，DevOps 问题 2）：§2.6 的启动门禁只能校验**应用侧**的两个量（`L1_SHUTDOWN_GRACE_MS ≥ N × L1_ITEM_BUDGET_MS`），**应用进程读不到自身的 systemd 配置**。漂移路径是真实存在且全程无报错的——运维把 `N` 调到合法上限 4 → 应用侧要求 `grace ≥ 960s`、改配置、校验通过、启动成功；而 unit 里的 `TimeoutStopSec` 仍是常量 280s → worker 以为有 960s 收尾，systemd 在 280s 时 SIGKILL，**残留锁照旧且比不配更隐蔽（应用侧所有校验都是绿的）**。
  > 因此 `deploy/deploy.sh` 须校验「运行目录 `.env` 的 `L1_SHUTDOWN_GRACE_MS` + 余量 ≤ unit 的 `TimeoutStopSec`」，不满足则拒绝部署（DevOps 已于 commit `2ce32cd` 落地）。**本设计记录这条依赖，以免后续维护者误以为应用侧校验已经兜住。**
- **`asyncio.CancelledError` 不得被吞**（CN-003 记入 O-8）：改造中任何节点的 `except Exception` 都不得改成 `except BaseException` 或裸 `except:`，否则协程不响应取消、优雅停机静默失效。建议加一条 lint/grep 断言。

**启动自愈**（在 worker 启动前执行，§4.1）：

```sql
UPDATE tasks SET status='queued', run_after=now(), locked_by=NULL, locked_at=NULL,
                 updated_at=now()
WHERE type='l1_ai_process' AND status='running'
  AND locked_by LIKE %(worker_id_prefix)s   -- '{worker_id}#%'
  AND locked_by <> %(current_lock_token)s   -- 排除当前进程（启动时必然无匹配，防御性保留）
RETURNING id, raw_item_id;
-- 对回收到的 raw_item_id 同事务写 l1_status='retryable_failed'
```

**只匹配 `worker_id` 前缀相同、`run_token` 不同的锁**——他人的锁一律不碰（AC-5.6）。

### 4.9 探活（AC-9.3）

`/health` 处理函数**不做任何 IO、不取连接池连接**，纯读内存中的 `WorkerState`，因此天然满足 ≤2s。DB 模式下它与 worker 协程共享同一 event loop——**如果 async 改造有遗漏（某个同步 IO 阻塞了 loop），这个端点会超时**。这正是 AC-9.3 把它设为验收项的原因：它是 async 彻底性的运行时闸门，不是普通的健康检查。

### 4.10 连接池与隔离级别（O-6 / O-9 落定）

- **驱动：`psycopg3`（async）**（O-9 落定，理由见 PRD §7 与 ADR-0003 附注）。
- 连接池 `psycopg_pool.AsyncConnectionPool`，`min_size=1` / `max_size=3`（v0.2 单实例串行，同一时刻最多 1 个事务在跑，留 2 个余量给 `/health` 之外的偶发并发与重连）。
- **连接必须随事务获取与释放，不得跨 `await` 长持**（O-6）：所有数据库访问写成 `async with pool.connection() as conn: async with conn.transaction(): …`，处理阶段不持有连接。
- **隔离级别显式断言**：池初始化时设置并断言 `READ COMMITTED`（写法 B 的正确性前提，AC-3.7 限定②）。启动时执行一次 `SHOW transaction_isolation` 校验，不符即拒绝启动——这条依赖是隐式的、一旦被破坏表现为偶发报错，必须在启动期暴露。
- **数据库操作超时上限（AC-4.7，R2 定稿前补）**：与隔离级别断言**在同一处执行**（池的连接初始化回调，天然复用现有代码位置）——

  ```python
  async def _configure(conn):                      # AsyncConnectionPool(configure=_configure)
      await conn.execute(f"SET lock_timeout = '{cfg.lock_timeout_ms}ms'")
      await conn.execute(f"SET statement_timeout = '{cfg.statement_timeout_ms}ms'")
      # 同处断言隔离级别：SHOW transaction_isolation → 必须是 read committed
  ```

  `connect_timeout` 由 `AI_DB_CONNECT_TIMEOUT_MS` 经连接串参数传入。三项取值与 §2.6 的两条不等式绑定，由启动门禁强制。**这三项只对异常路径（连不上 / 等锁 / 长查询）封顶，对毫秒级的正常路径无影响。**
- 口令**只从环境变量按字段读取**，不拼 DSN 字符串常驻内存；连接异常在记录前重写为不含连接串的消息（AC-6.2）。

### 4.11 三工具的「空结果 / 调用故障 / 预算跳过」三分（AC-7，R2 补）

> PM R1 问题 1 指出 AC-7 在 R1 全文零落点。它必须在设计阶段定，因为**它与本设计新增的 deadline 机制落在同一段代码里**——`news_l1.py:150`（link_read）/ `:179`（web_search）/ `:213`（kb_search）三处同构的 `if result.ok and result.items:` 判断，正是 §4.5 预算跳过要改的那三行。两件事若分两次改，同一段分支逻辑要动两次，且极易把三种情形混进同一个 `else`——**而 AC-7 的全部要点正是把它们分开**。

三处判断统一重写为**三分支**（v0.1 的两分支是缺陷所在）：

| 情形 | 判定条件 | `degradations` | `tool_summary` | 日志 |
|---|---|---|---|---|
| **成功且有结果** | `result.ok and result.items` | 不进 | +1 | `status=hit`，`items=n` |
| **空结果**（调用成功但无匹配） | `result.ok and not result.items` | **不进**（不产生 `degraded:` 标签） | **+1**（发起即计数口径不变） | `status=empty` |
| **调用故障** | `not result.ok`（非 200 / 超时 / 连接错误） | 进 `degraded:{tool}_failed` | +1 | `status=failed` + `error_kind` |
| **预算跳过**（§4.5） | 进入节点前 `budget.slice_for(段上限) == 0` | 进 `degraded:{tool}_budget_exhausted` | **不计**（未发起调用） | `status=skipped` + `error_kind=budget_exhausted` |

> **预算跳过时 `tool_budget_used` 同样不递增**（R2 定稿前补，Developer R2 问题 4）：v0.1 中 `tool_summary` 与 `tool_budget_used` 在同一个 updates 字典里一起递增（`news_l1.py:209-212`），而 `tool_budget_used` 控制的是 `options.max_tool_calls`（默认 4）配额、经 `_budget_ok`（`news_l1.py:290`）参与后续节点的路由判定。按同样的「未发起调用」逻辑它也不该递增——否则一次预算跳过会白白吃掉一次工具调用配额，连带影响后面节点该不该走。**两个计数器在四种情形下的口径必须一致。**

**为什么这在 DB 模式下比 v0.1 重要得多**：AC-8.2 已写明预取上下文消失、KB 由预取转主动检索（`tool_summary.kb_search` 从 0 变常态 ≥1），再叠加发现 B（`domain_tags` 实际恒为 `[]`）使 KB 查询命中率进一步下降——**空结果会从 v0.1 的边缘情形变成 DB 模式的常态**。若仍按「空结果 = 故障」记 `degradations`，产出里会出现大量 `degraded:kb_search_failed` 噪声，而 §1.2 的「高可用」正是建立在日志与降级信号的区分度之上：**满屏 `degraded:` 却无法判断哪些是真故障，等于没有观测面**。

> `tools/kb.py:72` 返回 `ToolResult(ok=True, items=[])` 本就是正确语义，**缺陷不在工具层而在 graph 层的三处判断**（AC-7.3 已点明）。三处须一并修，不可只修 kb。

### 4.12 结构化日志（AC-6 全六条，R2 补）

> PM R1 问题 2 指出 R1 只落了 AC-6.2 / 6.4 两条。`obs/logging.py` 在模块地图标 NEW 但正文无展开——而 US-6 与 §1.2 都把日志当作 worker 模式的**主要观测面**。

**注入方式（AC-6.4）**：logger 随 `L1State` 或依赖注入传入，`graphs/` 内**不得直接 import 全局 logger**——否则与 AC-2 的依赖方向产生耦合，且不可测试、不可替换。

**统一字段（AC-6.1）**：每条日志为一行 JSON，输出到 **stdout**（AC-6.3，由托管层收集——**v0.2 起 systemd unit 使用 `StandardOutput=journal`，journald 自带轮转与配额**，无需指定落盘路径、无需人工轮转；**应用内不实现轮转**）。

> R1/R2 原写的「由 DevOps 指定落盘路径并人工轮转」源自托管化顺延时期的 `nohup` 预设，托管化于 2026-07-28 落地后已不适用（按原文会去配一套不需要的日志轮转）。应用侧行为不变——照样只写 stdout。（R2 定稿前订正，DevOps R2 问题 3）

| 字段 | 说明 |
|---|---|
| `run_id` | 本次处理标识，贯穿一条的全部日志 |
| `raw_item_id` / `task_id` | DB 模式的条目标识；HTTP 模式为 `null` |
| `step` | `claim` / `map_in` / `kb_search` / `link_read` / `web_search` / `llm_process` / `normalize` / `map_out` / `writeback` / `release` |
| `status` | `ok` / `hit` / `empty` / `skipped` / `failed` |
| `duration_ms` | 本步骤耗时 |
| `budget_remaining_ms` | 该步骤结束时的剩余预算（**本设计新增，便于灰度期定位预算被谁吃掉**） |
| `error_kind` | 失败时必填，取 CN-004 后的八类枚举：`client_error` / `server_error` / `timeout` / `rate_limited` / `auth_error` / `db_error` / `mapping_error` / `budget_exhausted` |
| `error_message` | 脱敏摘要 |

**降级与 provider 事实须冗余一份（AC-6.6）**：`tags_v2.processing` 是 C-10 定案后**唯一**承载 `engine` / `llm:{provider}` / `degraded:{reason}` 的结构化字段，PRD 特意要求日志再记一份作为第二条线索。因此 `llm_process` 与三个工具节点结束时，除写入 `tags.processing` 外还须各记一条日志，含实际使用的 provider、是否走了 fallback、以及全部 `degraded:` 原因（含本设计新增的 `{tool}_budget_exhausted`）。

**脱敏（AC-6.2 / 6.5）**：日志不得含 API key、数据库口令、完整 `raw_content`。数据库连接/查询异常**必须在记录前重写**为不含连接串与口令的消息——最常见的泄漏路径不是主动打印，而是驱动异常带出 DSN。

> **`budget_exhausted` 与 `timeout` 必须分开记**（CN-004 变更 3）：前者指向各段上限分配（该调 `KB_TIMEOUT_MS` / `WEB_SEARCH_TIMEOUT_MS` / 总预算），后者指向 provider 侧（该调 provider 或查 fallback 链）。两者混记会让灰度期无法判断该调哪一个。

### 4.13 KB 检索的鉴权方式（R2 定稿后新增 —— Architect 拍板项）

> xiaobao DevOps 于 2026-07-28 澄清鉴权现状后，把选择权交给「架构/Owner」。此处给出结论。

**背景**：DB 模式下 KB 由「调用方预取」转为「ai 主动检索」（AC-8.2），唯一通道是回调 xiaobao 的 `POST /v1/kb-search`。该端点走全局 `adminGuard`，鉴权 = **`ADMIN_TOKEN` 或 IP 白名单**（二者满足其一即放行）；**后端不存在 `KB_ADMIN_TOKEN` 这个 env**（v0.1 代码里那个变量名是 ai 侧的一厢情愿）。

**结论：采用方案 A —— 同机直连、不使用任何 token。**

- `KB_SEARCH_URL` 指向 **`http://127.0.0.1:8001`（test）/ `:8000`（prod）** 的 `/v1/kb-search`；remote IP 命中对方 `adminAllowedIps=127.0.0.1` 即放行。
- **不配置 `KB_ADMIN_TOKEN`**。`tools/kb.py:38-40` 的现有逻辑是「该 env 为空则不发 `x-admin-token` 头」，**零代码改动即兼容**。
- **明令禁止**：不得向 ai 下发 xiaobao 的全权 `ADMIN_TOKEN`——那等于授予其所有 admin 写接口权限（改源 / 删空间 / 同步规则），严重违反最小权限。这一点与 DevOps 的判断一致，此处固化为设计约束。

**取舍理由**（按 §1.2 准则）：

| 维度 | 方案 A（同机直连，采用） | 方案 B（下发 token） |
|---|---|---|
| 最小权限 | **不引入任何凭据，泄漏面为零** | 唯一可用的是全权 token，越权严重 |
| 改动成本 | 零（对方无需改代码，ai 无需配置） | 需 xiaobao Developer 新增独立只读 KB token |
| 与现状契合 | 同机部署已是既定事实（§5 待办 1 已落地） | 为不存在的分机场景提前付代价 |

**部署约束（须写入部署就绪检查）**：本方案的**唯一前提是 ai 与 xiaobao 同机**。若将来分机部署，IP 白名单失效、KB 检索会**全部失败**（表现为 `degraded:kb_search_failed`，不影响主流程但持续降级）。届时的正确解法是请 xiaobao Developer 加**独立只读 KB token**，**不是**复用全权 `ADMIN_TOKEN`。已登记 §7.2 残留风险。

## 6. 迁移和兼容性

### 6.1 async 地基改造的切分与回归（O-8 落定，P0）

**切分顺序：自底向上、每层可独立回归。** 不采用「一次性全改」，也不采用「按功能纵切」——前者一旦回归失败无法二分定位，后者会让同一个协议在半途处于同步/异步混用状态。

| 步 | 范围 | 完成判据 |
|---|---|---|
| **0** | **录制黄金样本**（改造前，AC-9.4） | 四类路径快照落盘并纳入版本控制，见 §6.2 |
| 1 | 工具层：`tools/{kb,link_reader,web_search}.py` 三个出网点改 `AsyncClient`；`NewsTools` 协议 4 方法改 `async def`；`DefaultNewsTools` 同步跟进 | `test_news_l1_tools` 改 `pytest-asyncio` 后全绿 **+ 黄金样本四类逐字段比对通过** |
| 2 | LLM 层：`llm/client.py` 出网点改 `AsyncClient`，`AIClient.complete_json` 改 async（**`timeout_ms` 按次入参语义不变**，见 §4.5 订正） | `test_llm_client` 全绿 + provider fallback 链行为不变 **+ 黄金样本四类逐字段比对通过**（尤其样本 ④） |
| 3 | graph 层：4 个 IO 节点改 `async def`，`ingest_context` / `normalize_output` **保持同步**（无 IO 且毫秒级，O-8 判据）；`tasks.py:64` `invoke → ainvoke`；**并入 §4.11 的 AC-7 三分支修复与 §4.5 的 deadline 传递**（同一段代码只动一次） | 黄金样本四类**逐字段比对通过** + AC-7 三分支测试通过。**本步唯一允许的行为变更是 AC-7 三分支**（见 §6.2 边界声明），其余任何字段差异按回归处理 |
| 4 | 入口层：`main.py` 端点改 `async def`；`run_task` 改 async **并新增 `budget` 入参** | AC-9.5 并发验收（N≥3 并发，总耗时 < 1.5× 单条）**+ 黄金样本四类逐字段比对通过** |
| 5 | 新增数据源层与 worker（本迭代主体，非改造） | AC-2 静态 + 动态判据 |

**每步结束都跑黄金样本比对**——回归定位成本因此是 O(1) 而非 O(全量改动)。R1 的表格只在步 3 要求比对，与正文承诺不符（Developer 问题 7），R2 已把该判据补进步 1 / 2 / 4：**步 1、2 的行为漂移若要到步 3 才暴露，二分范围就白白扩大了两层**。

### 6.2 黄金样本（AC-9.4，CN-003 变更 2）

四类路径，每类固定 `L1Input` + 固定 mock LLM 响应，输出 `L1Output` JSON 快照落 `tests/golden/`：

| # | 路径 | 关键断言 |
|---|---|---|
| ① | 全工具命中的正常路径 | 全字段逐一比对 |
| ② | 工具全失败的降级路径 | 部分可用 = `succeeded`；`tags.processing` 的 `degraded:` 标记完全一致 |
| ③ | LLM 返回非法 JSON 的解析容错 | `llm/json.py` 容错分支产出一致 |
| ④ | LLM 超时触发 provider fallback | **`error_kind` 与降级标记一致**——同步下抛 `httpx.TimeoutException`，async 下若用 `asyncio.wait_for` 包裹则抛 `asyncio.TimeoutError`，按类型分派的 `except` 会漏接 |

> 针对 ④ 的实现约束：`ChainedAIClient` 的异常分类须**同时**认 `httpx.TimeoutException` 与 `asyncio.TimeoutError` 为 `timeout` kind。这是本次 async 改造中最容易静默变化的一处。

**黄金样本与 AC-7 的边界（R2 定稿前补，Developer R2 问题 1）**：

**四类黄金样本均不得包含「工具调用成功但无结果」（`ok=True, items=[]`）的场景。**

原因：步 3 同时做两件目标相反的事——async 改造要求**行为不变**（判据是黄金样本逐字段比对），而并入的 §4.11 AC-7 三分支修复是**有意改变行为**（空结果不再进 `degradations`，而 `degradations` 经 `normalize_output_node:371` 落进 `tags.processing`，正是样本 ② 的关键断言字段）。只要样本里出现一个空结果场景，比对必然失败——**而那是预期的正确变更，不是回归**。届时实现会话面对一个红色的黄金样本，无法判断该改代码还是该改样本，这正是回归基线最怕的状态。

- 空结果场景由 **§8 测试 17 独立覆盖**，其期望值是**改造后**的新语义。
- **§6.1 步 3 的唯一例外**：本步允许的行为变更**只有** AC-7 三分支，其余任何字段差异一律按回归处理。

> 现有 fake 的返回语义使风险实际较低（`NullTools`（`test_news_l1.py:67-74`）与 `FakeTools`（`test_news_l1_tools.py:33-44`）默认均返回 `ok=False`，是**故障**语义而非空结果），但那是巧合不是保证——`FakeTools` 支持传入 `ToolResult(ok=True, items=[])`，录样本的人为了「覆盖更全」很容易主动加进去。故此处写成硬约束。

### 6.3 对外兼容性

- **`news-l1` HTTP v1 契约不变**：`L1Input` / `L1Output` / `RunResponse` 字段与语义零改动；HTTP 模式行为与 v0.1 等价（含并发行为，AC-9.5）。
- **`news-l1-db` v1.4 不改**：ai 只读授权列、只写授权字段，不建表改表。
- **`/health` 响应体是增量扩展**：v0.1 的 `status` / `service` 两个键保留原位原值语义，新增键不影响既有冒烟脚本。
- **回滚是双侧协同动作**（AC-1.5）：先 xiaobao 切回集成模式、后 ai 切 `RUN_MODE=http` 重启。ai 单方回滚会导致队列静默积压。

## 7. 风险和取舍

### 7.1 关键决策与被放弃的省力方案

> 按 §1.2 准则，每条都记录「更省力的做法是什么、为什么不选」。

| # | 决策 | 更省力的做法 | 为什么不选 |
|---|------|-------------|-----------|
| 1 | 协议**按职责分层**（映射 / 拉取） | 一个四操作协议，HTTP 侧空实现 | HTTP 侧会出现 2~3 个空方法，AC-2.2 能被空实现通过；且「第二调用方要实现什么」变得不清楚（ADR-0003） |
| 2 | 源类型**适配器注册表** | 在 `DbL1Mapper` 里写 `if source_type == …` 三分支 | 新增 source type 要改核心映射类；注册表下只加一个文件 + 一行注册（高复用） |
| 3 | **`N = 1`** | 沿用 PRD 暂定的 `N ≤ 8` | 串行下 N>1 零吞吐收益、却把持锁时长与崩溃影响面放大 N 倍，且 `8 × 240s > 1800s` 直接违反 AC-3.6（ADR-0004） |
| 4 | **deadline 传递**（`slice_for`） | 各段各自配一个更小的超时常量 | 各段独立超时之和仍会累加，无法保证单条上限——正是 CN-003 A 项指出的根因 |
| 5 | `lock_token` **两段式**（稳定身份 + 运行标识） | 直接用 `hostname:pid` | pid 会复用导致误判；且单段标识无法同时满足「能自愈自己上次的锁」与「多实例互不误伤」 |
| 6 | 连接**随事务获取释放** | worker 循环外层开一个连接贯穿整批 | 240s 长持会同时踩 `idle_in_transaction_session_timeout` 与连接池饥饿，三段式设计等于作废 |
| 7 | async **自底向上分层改造** | 一次性全改 | 回归失败时无法二分定位；黄金样本的价值需要「每步可比对」才能兑现 |
| 8 | claim 后**一次性读全**处理所需数据 | 处理过程中按需回查 | 回查会在处理期间持有连接，破坏三段式；且数据在处理中途变化会引入不一致 |
| 9 | **写回失败有限重试**（R2 补，Developer 问题 6） | 失败即放弃，等 1800s 回收 | 此时已花掉 240s 预算 + 一次完整 LLM 调用（含费用），而写回事务是毫秒级、失败多为瞬时故障（连接回收 / 死锁 / 抖动）。为省一个 `for` 循环丢弃已产出的结果，并让条目再占队列 30 分钟，与 §1.2「高可靠」不一致 |
| 10 | **`release` 独立于失败路径**（R2 补，Developer 问题 1） | 停机时复用 `mark_failed(retryable=True)` | 会污染 `attempt` 与 `last_error_kind`：一次正常停机在 xiaobao 侧看起来像一次处理失败，且白白消耗一次重试配额 |
| 11 | **三层停机时限逐层放大**（R2 订正，DevOps 问题 1） | 三层配同一个数值（R1 原写法） | 语义不同的三个量取相等值，边界上必然竞态——worker 恰好用满宽限期完成写回时被 systemd 同刻 SIGKILL，COMMIT 前被杀留下残留锁，正是整条停机链要防的事 |
| 12 | **`slice_for` 设最小段阈值**（R2 补，Developer 问题 4） | 只判 `remaining <= 0` | 残值 300ms 时会发起一次必然超时的调用，并被 AC-7.2 记成「工具故障」——预算耗尽被误报为 xiaobao 服务挂了，污染的正是本设计最看重的观测面 |

**问题：**

1. **高｜`PullSource` 协议缺 `release` 方法，而 §4.2 主循环调用了它——实现会话照文档写会直接撞 `AttributeError`。**
   §3.2 的 `PullSource` 只定义四个方法（`fetch_batch` / `commit_success` / `mark_failed` / `reclaim_own_stale_locks`，行 239/242/245/250）；§4.2 的主循环写：
   ```text
   if state.state != "running":
       await source.release(item); continue      # ← 行 474，协议中无此方法
   ```
   N=1 时该分支几乎不触发（`items` 只有一条，进入 for 前刚判过 state），但 `L1_CLAIM_BATCH_SIZE` 是可配项，N>1 且停机时必然走到。
   更要紧的是**语义未定义**：停机时释放一个「已 claim、未开始处理」的条目，正确处置应是把 `tasks.status` 退回 `queued`、`raw_items.l1_status` 退回 `queued`、清锁——它既不是失败（不该 `attempt` 计入、不该写 `last_error`），也不是成功。复用 `mark_failed(retryable=True)` 会污染 `attempt` 与 `last_error_kind`，让一次正常停机看起来像一次处理失败，且白白消耗一次重试配额。
   建议：在 §3.2 补第五个方法 `async def release(self, item: ClaimedItem) -> None`（单事务退回 `queued` + 清锁 + **不动 `attempt`**），并在 §4.7 的失败表里补一行「主动释放（停机）」与失败路径区分开。

2. **中｜`run_task` 的签名，§1.3 说「签名不变」，§4.5 说「新增一个 `budget` 参数」——文档自相矛盾。**
   §1.3 模块地图第 53 行：`tasks.py  MOD  run_task 改 async（invoke → ainvoke）；签名不变`；§4.5 第 497 行：「`run_task` 签名新增一个 `budget` 参数」。两处对同一个函数的说法相反。我同意 §4.5 的实质判断（`budget` 是数据源无关的量，不违反 AC-2.2），建议订正 §1.3 的表述为「改 async + 新增 `budget` 入参」，否则实现会话按模块地图写完再看 §4.5 会返工。

3. **中｜LLM 预算的传递路径写反了方向，会把实现引向一次不必要的改造——实际比设计描述的更简单。**
   §4.5 写「`budget.remaining_ms()`，**实传给 `ChainedAIClient(budget_ms=…)`**（v0.1 未传）」。核对代码后，这个描述会误导：
   - `budget_ms` 是 `ChainedAIClient.__init__` 的**构造参数**（`client.py:88-93`），而 `ItemBudget.remaining_ms()` **每条都不同**。走构造参数就意味着每条都要重建 client（`build_ai_client()` 每次重读配置、重装 provider 链），或把它改成可变属性——两者都是多余改造。
   - 现有 `complete_json(messages, timeout_ms)` 已经支持按次传入，且 `client.py:99` 就是 `budget = timeout_ms if self._budget_ms is None else min(self._budget_ms, timeout_ms)`——**按次传的 `timeout_ms` 本来就是链的总预算**。
   - 更重要的是：**v0.1 的「链共享预算」语义本就正确实现了**（`client.py:101-111`：每个 provider 前算 `remaining = budget - elapsed`，`remaining <= 0` 时记 `budget_exhausted` 并 break，`call_timeout = min(provider.timeout_ms or remaining, remaining)`）。所以 AC-3.8 注的「v0.1 未传」应精确为「`budget_ms` **构造参数**从未被使用（`build_ai_client()` 不传，`client.py:215`），但 `complete_json` 的 `timeout_ms` 一直在传（`news_l1.py:333` 传 `inp.options.timeout_ms`，默认 180s）」。
   - 因此本迭代要做的只是把 `news_l1.py:333` 的入参从 `inp.options.timeout_ms` 换成 `budget.remaining_ms()`——**一行**，链内递减分配无需任何改动。
   建议 §4.5 改写为走 `complete_json(timeout_ms=budget.remaining_ms())`，并在表格「实际使用」列同步。这条不改也能做对，但按现文字实现会多绕一圈。

4. **中｜`slice_for` 返回极小残值时会发起一次必然超时的调用，并被 AC-7 记成「工具故障」——预算耗尽被误报为工具不可用。**
   §2.4 定义 `slice_for(段上限) = min(段上限, remaining_ms())`，§4.5 的跳过闸门只有 `budget.exhausted()`（即 `remaining <= 0`）。于是当 `remaining = 300ms` 时：`exhausted()` 为 False → 不跳过 → `slice_for(15000)` 返回 300ms → 用 300ms 超时去调 KB/link/web **必然超时** → 按 AC-7.2「超时属调用故障」记入 `degradations`，产出 `degraded:kb_search_failed`。
   后果是可观测性被污染：一条因预算耗尽而降级的记录，看起来像 xiaobao 的 KB 服务挂了。灰度期靠日志判断问题时，这类误报最费时间。
   建议：给 `slice_for` 加最小可用阈值（如 `MIN_SEGMENT_MS = 1000`，返回值低于它即返回 0），并把 §4.5 的跳过条件从 `budget.exhausted()` 改为 `budget.slice_for(段上限) == 0`——这样「预算不足以支撑本段」统一记 `degraded:{tool}_budget_exhausted`（§4.5 已定义该标记），与真实工具故障区分开。

5. **中｜`raw_items.l1_attempt` 的递增时点在写回事务，与 PRD AC-5.1「镜像值、同事务一并推进」不符；claim 后崩溃会让两个计数器漂移。**
   §3.4 步骤 2 在 claim 事务里写 `tasks.attempt = attempt + 1`；而 `raw_items.l1_attempt + 1` 出现在 §4.6（写回成功）与 §4.7（失败）——即**处理完成后**才推进。若 worker 在 claim 之后、写回之前崩溃（预算 240s 的窗口里，这是最可能的崩溃点），`tasks.attempt` 已 +1 而 `l1_attempt` 未 +1，两者永久差 1；xiaobao 的 1800s 回收介入后差距还会继续累积。
   PRD C-8 定 `tasks.attempt` 为判定真源、`l1_attempt` 为镜像，所以这不影响重试判定的正确性；但 `l1_attempt` 是 xiaobao 侧可见的展示值，漂移会让对方看到「尝试 2 次」而实际已尝试 3 次。
   建议移入 claim 事务：§3.4 步骤 4 本来就在 `UPDATE raw_items SET l1_status='processing'`，顺手加 `l1_attempt = l1_attempt + 1` **成本为零**，且真正兑现「同事务一并推进」。相应地 §4.6 / §4.7 里的 `l1_attempt + 1` 应删除，否则会重复计数。

6. **中｜DB 写回失败直接放弃一条已算完的结果，未做任何重试——与本设计 §1.2「高可靠」准则不一致。**
   §4.7 表：「DB 写回失败 → 事务回滚，条目保持 `running`/`processing`，由下一次启动自愈或 xiaobao 1800s 回收」。这意味着：一条已经花掉 **240s 预算 + 一次完整 LLM 调用（含费用）** 的结果，因为一次可能只持续几毫秒的连接抖动或死锁就被整个丢弃，且该条目还要额外占用队列 30 分钟。
   而写回事务本身是**毫秒级**的，重试 1~2 次（间隔 1s）成本可忽略，成功率却很高——DB 写回失败绝大多数是瞬时故障（连接被回收、`deadlock_detected`、短暂网络抖动）。§1.2 把「高可靠」列为三维之一，§7.1 也逐条记录了「不选省力方案」的理由，唯独这一处选了最省力的处置且没有记录取舍理由。
   建议：写回事务失败时做有限次重试（建议 2 次、间隔 1s、仅对可重试的 PG 错误类如连接错误 / 死锁 / 序列化失败），全部失败后再落到现有的「保持 `running` 等回收」路径；并在 §7.1 补一行取舍说明。注意重试须在预算之外（结果已产出，不受 `ItemBudget` 约束）。

7. **低｜§6.1 正文与表格对「每步是否跑黄金样本」的要求不一致。** 正文写「**每步结束都跑黄金样本比对**——回归定位成本因此是 O(1)」，但表格里只有步 3 的完成判据是「黄金样本四类逐字段比对通过」，步 1 / 2 / 4 分别是各自单测与并发验收。按表格实现就拿不到正文承诺的 O(1) 定位能力（步 1、2 的改动若引入行为漂移，要到步 3 才暴露，二分范围又变大）。建议把「黄金样本比对通过」补进步 1、2、4 的完成判据列。

8. **低｜出向映射失败按可重试处理，但它是确定性失败，会白白消耗 3~5 次 × 240s。** §4.7 表把出向映射失败（`server_error`）归为可重试——这是 PRD AC-2.5 的规定，设计遵循无误。但实现角度值得记一笔：出向映射失败的典型原因（字段类型不符、必填缺失、序列化失败）对同一个 `L1Output` 是**确定性**的，重试会用完整的 240s 重新走一遍 LLM 再次失败，直到 `max_attempts` 耗尽。建议在 §7.2 残留风险补一行，并要求该路径的日志显式标注 `mapping_error` 子类型，便于灰度期一眼识别（否则会淹没在普通重试里）。是否改判为不可重试属 PRD 范围，本轮不主张改。

**第二部分：指派项的结论**

- **协议与 SQL 可实现性**：除问题 1 的 `release` 缺失外，`L1Mapper` / `PullSource` / `SourceTypeAdapter` 三个协议签名**可直接照写**；§3.4 两种 claim SQL 的字段、条件、排序、`RETURNING` 列均完整，写法 B 的三条限定（后到者拿空批不记错、依赖 `READ COMMITTED`、多实例前须解 C-6）表述准确无歧义。§4.6 写回 SQL 中 `score_total` / `id` **不出现在任何位置**这一约束写得足够醒目（§2.3 还补了「不是写 NULL，是根本不提及」），这是最容易被实现会话写错的一处，处理得当。
- **async 切分顺序**：自底向上五步的划分正确——工具层 → LLM 层 → graph 层 → 入口层 → 新增层，每层的下游都已 async，不会出现同步/异步混用的中间态。步 0 先录样本是对的。唯一缺口是问题 7。
- **黄金样本可执行性**：四类路径覆盖到位，样本 ④ 的实现约束（`ChainedAIClient` 须同时认 `httpx.TimeoutException` 与 `asyncio.TimeoutError` 为 `timeout` kind）是本次改造最容易静默变化的一处，能在设计阶段被点名，说明 O-8 的风险判断是落到实处的。§7.2 关于「mock 保真度」的自我质疑（须用两种真实异常各跑一次）尤其到位。
- **工作量与 PRD §8 成本表的相符度**：**相符，且本设计新增的部分是必要增量**。§8 五块中的块 1（async 地基）与本文档 §6.1 五步一一对应；块 2（协议分层）在本设计里扩为「两协议 + 注册表 + 三适配器 + URL 规范化」，比 PRD 预估略增，但增量来自 §0 准则裁定 2（协议而非映射函数）与 DevOps 实机发现 B（`domain_tags` 排除集），属已授权范围。新增的 `worker/budget.py`、`worker/state.py`、`obs/logging.py` 在 §8 中分别落在块 4、块 5，未超范围。**未发现设计悄悄扩大范围。**

**未构成问题、明确认可的部分：**

- **`lock_token` 两段式（§2.5）是本设计最漂亮的一处**。它用一个字符串格式同时解决了三件事：能自愈自己上次进程的锁、不误碰他人的锁、pid 复用不造成误判。文档还把「若只用 `hostname:pid`」和「若把启动时间揉进 `worker_id`」两种错法的后果各写了一句——这比只给正确答案有用得多。
- **`_on_worker_done` + `task.exception()`（§4.1）** 直接命中「worker 死了但 `/health` 报健康」这个最隐蔽的失效模式。`add_done_callback` 里必须**取出**异常这一点尤其关键，不取出只会在 gc 时于 stderr 打一行，实现会话很容易漏。
- **N=1 的推翻（ADR-0004）我完全同意，且论证方式值得记**：不是"保守起见取小值"，而是先定单条预算（240s）、再代入不变式发现 `8 × 240s = 1920s > 1800s` **直接违反 AC-3.6**——PRD 的暂定值 8 在预算落定后已经是非法值。同时"取到条目后不 sleep 立即下一轮 claim"补上了 N=1 的吞吐缺口，逻辑闭环。
- **`domain_tags` 用排除集而非一律置空（§3.3）**：把「已确认不是领域标签的值」挡掉、其余放行，使 xiaobao 将来启用真实分类时 ai 侧**自动跟上而不必改代码**。同时文档诚实写明「在其确认前 DB 模式下 `domain_tags` 实际恒为 `[]`」，并要求 PM 据实更新 PRD AC-8.2 的「不再恒空」——不掩盖被实测推翻的结论。
- **空转可观测性（§2.5，据发现 A）**：在不违反「ai 不做孤儿探测」边界的前提下，只用一个计数器就把「队列真空」与「有货无 task」这两个在 ai 侧完全同形的状态变成可分辨的信号。边界与可观测性的平衡处理得很好。
- **§7.1 的「被放弃的省力方案」表**：8 条决策每条都写了"更省力的做法是什么、为什么不选"。这张表在实现阶段的价值不亚于设计本身——它能挡住实现会话"顺手简化一下"的冲动，因为放弃理由已经写在那里了。

**建议修改（按优先级）：**

- **必改（高）**：§3.2 补 `release` 方法并在 §4.7 区分「主动释放」与失败路径（问题 1）。
- **宜改（中）**：订正 §1.3 的 `run_task` 签名表述（问题 2）；§4.5 改走 `complete_json(timeout_ms=…)` 并精确化「v0.1 未传」的含义（问题 3）；`slice_for` 加最小段阈值、跳过条件改用它（问题 4）；`l1_attempt` 递增移入 claim 事务、删除写回/失败路径中的重复递增（问题 5）；写回事务失败补有限重试并在 §7.1 记录取舍（问题 6）。
- **可选（低）**：§6.1 表格补每步的黄金样本判据（问题 7）；§7.2 补出向映射失败重试成本的说明（问题 8）。

**第二部分：问题**

1. **高｜AC-7（三工具「空结果 vs 调用故障」语义统一）在设计中零落点，测试要求表也无对应项——而它是 PRD §4「本迭代做」明列的一项，且是 xiaobao 从 2026-07-04 等到现在的 v0.1 遗留 D-3。**

   全文 `grep "AC-7"` **0 命中**；`空结果` / `kb_search_empty` / `degradations`（除 §4.5 的 `degraded:{tool}_budget_exhausted` 外）均无命中。§1.3 模块地图对 `graphs/news_l1.py` 只标了「4 个 IO 节点改 async；新增 deadline 传递」，**未包含 AC-7.3 点名的三处同构缺陷修复**（`news_l1.py:150` link_read / `:179` web_search / `:213` kb_search 的 `if result.ok and result.items:`）；§8 测试表 16 项中无一项对应 AC-7。

   这不是可以留给实现阶段自行处理的细节，理由有三：

   - **它与本设计新增的 deadline 机制在同一段代码里交汇**。§4.5 规定「预算耗尽 → 跳过该节点并记 `degraded:{tool}_budget_exhausted`」——这恰好是那三处 `if result.ok and result.items:` 判断的**同一个位置**。若实现时先改 async + deadline、再回头补 AC-7，同一段分支逻辑要动两次；若两件事的语义边界没提前想清楚，很容易把「预算跳过」「调用故障」「空结果」三种情形混进同一个 `else`——**而 AC-7 的全部要点正是把它们分开**。
   - **DB 模式下这三处的触发率显著上升**。AC-8.2 已写明预取上下文消失、KB 由预取转主动检索、`tool_summary.kb_search` 从 0 变常态 ≥1；再叠加发现 B（`domain_tags` 实际恒为 `[]`）导致 KB 查询命中率进一步下降——**空结果会从 v0.1 的边缘情形变成 DB 模式的常态**。若仍按「空结果 = 故障」记 `degradations`，产出里会出现大量 `degraded:kb_search_failed` 噪声。
   - **它会污染本设计最看重的观测面**。§1.2 把「高可用」建立在三态探活与日志之上，AC-6.6 又要求降级事实进日志；若空结果被误记为降级，**日志里的降级信号会失去区分度**——灰度期看到满屏 `degraded:` 却无法判断哪些是真故障。

   建议：§1.3 的 `graphs/news_l1.py` 行补上 AC-7 的三处修复；正文（建议并入 §4.5 或新增一节）明确三种情形的判定与产出——**空结果不进 `degradations`、不产生 `degraded:` 标签，只进日志与 `tool_summary`（发起即计数口径不变）；调用故障进 `degradations`；预算跳过记 `degraded:{tool}_budget_exhausted`**；§8 补一条测试项（三工具各造一次「成功但空」，断言 `degradations` 为空且 `tool_summary` 计数 +1）。

问题：

1. **高｜§4.8 把「三层配一致」落成了三层数值全等（都 260s），边界上必然竞态——落地就会产生它本要防的残留锁。**

   §4.8 现写：应用层 = `L1_SHUTDOWN_GRACE_MS`（260s）、ASGI 层 = uvicorn `--timeout-graceful-shutdown 260`、托管层 = systemd `TimeoutStopSec=260`。

   三者语义不同，不能取同一个值：

   - **应用层 grace** = worker 收到停机信号后**最多用多久收尾**（跑完当前条目 + 写回事务）；
   - **systemd `TimeoutStopSec`** = 从发出 SIGTERM 到**发出 SIGKILL** 的墙钟。

   若两者相等，当 worker 恰好用满 260s 完成最后一次写回时，systemd 在同一时刻 SIGKILL——**写回事务可能在 COMMIT 之前被杀**，留下 `l1_status='processing'` 的残留锁，只能等 xiaobao 1800s 回收。这正是整条优雅停机链要防的事，却会因为"三个数字写成一样"而发生。

   正确关系是**逐层放大**，不是相等：

   ```text
   应用层 grace (260s)  ≤  uvicorn --timeout-graceful-shutdown (≥260s)  <  systemd TimeoutStopSec (280s)
   ```

   > **表述责任我认领**：这条的起因是我 R3 高②写的「三层须配一致值」——本意是「三层必须协调、不能各自为政」，但「一致值」字面确实会被读成「数值相等」。建议 §4.8 改为「**逐层放大**：托管层 = 应用层 + 收尾余量（建议 20s）；ASGI 层 ≥ 应用层」。

   **本人已提交的 unit 按 280s 写**（`niuma-ai-worker@.service` 的 `TimeoutStopSec=280`），与本条建议一致、与设计文档现文不一致——请以本条为准订正设计，我不改 unit。

2. **高｜三层关系的强制点被放在了应用启动校验里，而应用读不到 systemd 配置——`N` 一旦调大，应用侧校验全过、systemd 照杀。**

   §2.6 把不变式列为启动门禁，方向正确。但这道门禁只能校验**应用侧**的两个量（`L1_SHUTDOWN_GRACE_MS ≥ N × L1_ITEM_BUDGET_MS`），**管不到 unit 文件里的 `TimeoutStopSec`**。

   具体漂移路径（全程无人报错）：

   - §2.6 对 `L1_CLAIM_BATCH_SIZE` 的校验是 `N × L1_ITEM_BUDGET_MS < 1800000 × 0.6`，即 **N 最大可合法配到 4**；
   - 运维把 `N` 调到 4 → 应用侧强制要求 `L1_SHUTDOWN_GRACE_MS ≥ 960s`，改配置、通过校验、**启动成功**；
   - 而 `TimeoutStopSec` 是 unit 文件里的**常量 280s**，不会跟着变；
   - 结果：worker 以为自己有 960s 收尾，systemd 在 280s 时 SIGKILL。**残留锁照旧，且比不配还隐蔽**——因为应用侧所有校验都是绿的。

   应用进程无法读取自身的 systemd 配置，**这道校验只能落在部署层**。建议 §4.8 显式记一条：「三层一致性的**强制点在部署脚本**，不在应用启动校验；应用侧校验只覆盖应用层内部的两个量」。

   本人将在 `deploy/deploy.sh` 补该校验（读运行目录 `.env` 的 `L1_SHUTDOWN_GRACE_MS`，与 unit 的 `TimeoutStopSec` 比对，不满足则拒绝部署），属 DevOps 侧动作、不占 Architect 工时；但**设计文档需记这条依赖**，否则将来换人维护会以为应用侧校验已经兜住。

3. **中｜§4.1 的启动自愈失败会导致进程拒绝启动，可用性取舍反了。**

   §4.1 中 `await source.reclaim_own_stale_locks()` 在 `lifespan` 内、`yield` 之前，且无异常处理说明。按 Python 语义，它抛异常会使 lifespan 启动失败 → 进程退出 → systemd `Restart=on-failure` 拉起 → 再失败 → `StartLimitBurst=3` 后置 failed，**服务完全不可用**。

   但自愈失败的实际后果很轻：只是上次进程的残留锁没被提前回收，**xiaobao 侧 1800s 卡死回收会兜底**（AC-5.6 本就把「他人的锁」交给对方回收，自愈只是加速自己那部分）。为一个「加速项」失败而拒绝提供服务，取舍反了——尤其自愈失败最可能的原因正是 DB 短暂抖动，而那时更该让服务起来重试。

   建议：自愈失败记 ERROR 日志（含 `error_kind`）后**继续启动**，并在 `/health` 暴露一个标志位（如 `self_heal_failed`），让运维知道有残留锁待兜底。§4.1 的代码骨架请显式写出这个 try/except，否则实现会话照现文写就是 fail-fast。

4. **中｜`stale_tolerance_ms` 的判读顺序没写，停机期间会被误判为异常。**

   §3.6 给出 `stale_tolerance_ms = N × L1_ITEM_BUDGET_MS + L1_POLL_INTERVAL_MS`（默认 255s），供运维判断 `last_poll_at` 是否过陈旧。设计得很好——但**停机期间这个判据会失效**：`stopping` 态下 worker 不再 poll，`last_poll_at` 最长会陈旧 260s（> 255s 阈值），而这完全正常。

   若 v0.3 的 healthcheck timer 只看 `last_poll_at` 与 `stale_tolerance_ms`，会在优雅停机窗口内把正常收尾的进程判为异常——与问题 1 是同一类错误的两种表现。

   建议 §3.6 补一句判读顺序：**先看 `worker_state`，`stale_tolerance_ms` 仅在 `running` 态下适用**；`stopping` 态下 `last_poll_at` 陈旧属预期，`dead` 态直接由 503 表达。这条同时是 v0.3 healthcheck timer 的实现前提。

问题：

1. **高（附条件）｜数据库操作没有任何时间上限——`ItemBudget` 只覆盖处理阶段，claim 与写回两个事务在所有预算之外，§4.8 的宽限期算式因此没有保证。**

   本设计对处理阶段的时间控制很严谨（`ItemBudget` + `slice_for()` + `L1_MIN_SEGMENT_MS`，240s 封顶）。但**两个数据库事务不在任何预算内，且全文没有任何超时配置**——`connect_timeout` / `statement_timeout` / `lock_timeout` 在 §2.6 配置表与 §4.10 连接池设计中**均零命中**。

   §4.6 的断言正建立在这个缺口上：

   > 「重试总耗时（≤2s）要计入 §4.8 的停机宽限期余量（260s 中的 20s 收尾余量已覆盖）」

   该断言**只在每次重试都立即失败时成立**。而 §4.6 自己规定的重试触发条件是「连接错误 / `deadlock_detected` / `serialization_failure`」——**后两者的本质就是锁等待**，无 `lock_timeout` 时 PostgreSQL 会**无限等**。

   这不是理论风险，场景很具体：写回三表（`processed_news` + `raw_items` + `tasks`）时，xiaobao 侧的 1800s 卡死回收正好在 UPDATE 同一行 `tasks`——两侧对同一行的写竞争是这套契约的固有面（AC-5.6 已承认「他人的锁交对方回收」）。后果分两种：

   - **停机时**：worker 卡在写回等锁 → 超出 260s 宽限期 → systemd 在 280s SIGKILL → **写回事务在 COMMIT 前被中断、残留锁**。这正是三层时限链要防的事，只是这次的原因不是配置写错，而是**算式漏了一项**。
   - **非停机时**：worker 静默卡在写回，`in_flight` 恒为 1、`current_item_started_at` 不推进。`/health` 能反映"卡住"（这点设计做到了），但**没有任何自愈机制**，只能人工介入。

   连带影响两处已定的量：`stale_tolerance_ms = N × L1_ITEM_BUDGET_MS + L1_POLL_INTERVAL_MS`（255s）同样只算了处理阶段，两次 poll 的真实最长间隔还要加上 claim + 写回 + 重试。

   **建议（三条配套，缺一不可）**：

   1. §2.6 增 `AI_DB_CONNECT_TIMEOUT_MS`（同机部署，建议 `5000`）。
   2. **池初始化时设置会话级 `lock_timeout` 与 `statement_timeout`**——与 §4.10 已有的 `READ COMMITTED` 断言同一处执行，天然复用现有代码位置。
   3. §4.6 的「≤2s」改为**由参数推导的上界**：`L1_WRITEBACK_RETRY × (statement_timeout + L1_WRITEBACK_RETRY_DELAY_MS)`，并使其 ≤ §4.8 的收尾余量。

   > **注意取值要自洽**：若按常见的 `statement_timeout=30s`，最坏 `2 × (30+1) = 62s`，**远超 20s 余量**，届时要么调大宽限期、要么调小超时。建议取 **`statement_timeout=8s`、`lock_timeout=5s`**，则最坏 `2 × (8+1) = 18s < 20s` 余量，算式自洽且无需改动 260/280 这两个已定的数。写回事务本身是毫秒级的（§4.6 自己也这么说），8s 对正常路径绰绰有余，只对"等锁"这种异常路径起封顶作用。

2. **中｜`dead` 状态在 v0.2 没有任何消费方，§3.6 的「托管层应有反应：重启」会造成误期待。**

   §3.6 表格给 `dead` 一行写的是「HTTP 503 / 托管层应有反应：**重启**」。但 v0.2 的实际情况是：

   - systemd 的 `Restart=on-failure` 只看**进程退出码**。worker 协程死了而进程仍在（这正是 §4.1 `_on_worker_done` 处理的场景），进程没退出，systemd **什么都不会做**；
   - healthcheck timer 是消费 503 的那个组件，而它在本人 `deploy/README.md` 中被明确列为「尚未纳入」——因为它依赖的状态码语义当时刚定；
   - 于是 `dead` 状态下的真实链路是：worker 已死 → `/health` 返回 503 → **没有任何东西在读这个 503** → 靠人工 curl 才能发现。

   这本身是 v0.2「人工看护灰度、不得无人值守」（PRD §4）的**已知取舍**，我不主张改。问题在于表格那句话会让读者以为自动重启已经存在——而灰度期真正的操作规程是"人得去看"。

   建议 §3.6 表格补一句限定：**v0.2 无自动消费方**，`dead` 靠人工/外部监控发现；托管层自动重启待 v0.3 healthcheck timer 落地后生效。一句话的事，但它决定灰度期运维知不知道自己必须主动看。

3. **中｜§4.12 的日志落盘表述停留在托管化之前，与已落地的 journal 方案冲突。**

   §4.12 写「输出到 stdout（AC-6.3，由托管层收集；v0.2 灰度期由 DevOps **指定落盘路径并人工轮转**，不在应用内实现轮转）」。

   括号里那句源自 PRD R1 时期——当时托管化顺延 v0.3，灰度期预设沿用 `nohup`，所以要人工轮转。**但托管化已于 2026-07-28 落地**（Owner 拍板纳入 v0.2，`b5ae3b6`），unit 用的是 `StandardOutput=journal`：journald 自带轮转与配额，**不需要指定落盘路径、也不需要人工轮转**。

   应用侧行为不受影响（照样写 stdout，这条完全正确），但按现文，部署阶段的人会去配一套不需要的日志轮转。建议把括号内改为「由托管层收集——v0.2 起 systemd unit 使用 `StandardOutput=journal`，journald 自带轮转与配额；应用内不实现轮转」。

未构成问题、明确认可的部分：

- **§4.8 的三层语义对照表是本轮最有价值的改动**。我 R1 给的只是一个不等式，R2 把三层各自「到底在度量什么」写清楚了——这才是三者不能取同一个值的根因。将来有人想「简化配置、三个都写 260」时，看到这张表就会知道为什么不行，比记住一个数字耐久得多。
- **`self_heal_failed` 进 `/health`** 比我建议的「记 ERROR 后继续」更进一步：把一个只存在于启动日志里的瞬时事件，变成了运维随时可查的状态位。启动日志会被后续日志淹没，状态位不会。
- **§2.4 的 `L1_MIN_SEGMENT_MS`（R2 补）** 我认为是本轮的一个隐性收获：只判 `remaining <= 0` 的话，`remaining=300ms` 时会拿 300ms 去发起一次必然超时的调用，白白消耗一次 provider 配额还污染 `error_kind`。这个细节我 R1 没看出来。
- **§4.6 写回重试的取舍论证**（已花掉 240s 预算 + 一次 LLM 调用费用，不该因几毫秒抖动整个丢弃）站得住，与 §1.2「高可靠」准则一致。我的问题 1 不是反对重试，而是要给它一个时间封顶。
- **§4.11 把 AC-7 三分支与预算跳过合并在同一次改动里**——判断正确。那三处同构的 `if result.ok and result.items:` 若分两次改，同一段分支逻辑要动两遍，且极易把三种情形混进同一个 `else`，而 AC-7 的全部要点恰恰是把它们分开。
- **§4.12 的 `budget_remaining_ms` 字段**（设计自主新增）：灰度期定位"预算被谁吃掉"时，这一个字段抵得上一堆推算。
