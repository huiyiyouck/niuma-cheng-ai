### 对设计的三处偏离（均已在 commit 记明理由）

1. **步骤顺序调整**：设计步 1 只改工具层，但其完成判据要求「黄金样本通过」——工具改 async 后同步节点无法 await，系统在该步结束时跑不起来，判据不可能达成。实测 `ainvoke` 可执行同步节点，故把入口层提前到第一步。**偏离的是顺序，不是分层原则**；这是唯一能同时满足「分层」与「每步跑黄金样本」的顺序。
2. **`ItemBudget` 的位置**：设计写 `worker/budget.py`，但它要随 `L1State` 流经 graph，而 §1.3 要求处理核心对 `worker/` 零依赖——定义在 `worker/` 下会让处理核心反向 import 拉取型控制流的包。改放 `agent_hub/budget.py` 顶层（它本身是数据源无关的量，§4.5 亦如此认定）。已加静态测试固定该约束。
3. **`extract_url` 保持同步**：设计 §6.1 写「`NewsTools` 协议 4 方法改 async」，但它是纯字典取值 + 前缀判定、无 IO，按 O-8 的划线判据（「无 IO 且耗时毫秒级保持同步」）不应改协程。

### 落地时发现的两处、以及一处我自己票里说反了的

1. **判死检查的位置有两个都错的放法**。放在 `except` 里会被自己捕获（异常
   永远出不去）；放在轮末则**空队列的 `continue` 会绕过它**——写回连败达阈值
   后队列恰好空了，就永远不判死。最终放在 `try` **之前**，每轮开头必过一次。
2. **CN-011 变更 2 的两句话在实现上是冲突的**：它要求「标记单段、缺失明细进
   `degradations` 日志」，但 `degradations` **本身就是标记的来源**
   （`processing.extend(f"degraded:{d}" ...)`）——明细进它等于进标记。生成
   标记时只取冒号前一段，两个要求才同时成立。已在代码注释里写明。

### 高① 我要认的不是漏了几个码，是**验证方法错了**

R2 那次我实测了五项——`42501` / `42P01` / `22P02` / 无 sqlstate / `TimeoutError`

不在名单内，在名单外。**我做了实测、还把它写进报告当证据，方法却答的不是真正
要问的那个问题**——这正是我在票里反复指出别人的那个形状，这次轮到我自己。

漏掉的 5 类里，`57P01 admin_shutdown` 与 `57P03 cannot_connect_now` **正是 PG
例行重启的码**，而 CN-010 变更 1 从头到尾的立论就是「PG 例行重启会走到这条
路径」。后果链是最坏的那条：

```text
判成确定性错误 → 一次重试都没有 → mark_failed(retryable=False)
  → l1_status='final_failed' + tasks.status='failed'   ← 终态

```

即**一条完全正常、已花掉 240s 预算和一次 LLM 调用的数据，因为撞上重启就被烧成
不可恢复，且没有任何信号**。

改为**按 Class 给**：`08`（连接）/ `53`（资源不足）/ `57`（操作员干预）+
`40001` / `40P01` / `55P03`。按码列举时漏的永远是没想到的那个。

**一个有意接受的超收**：`57P04 database_dropped`、`53100 disk_full` 重试确实
无用，按码列本可排除。仍按 Class，因为**两种误判的代价严重不对称**——误判为
可重试只是多试几次后走判死（有信号、可恢复）；误判为不可重试则一次不试就进
终态且不告警（无信号、不可恢复）。已在代码与测试中写明。
