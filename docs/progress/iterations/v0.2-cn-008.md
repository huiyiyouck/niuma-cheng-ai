## 背景

DevOps 在确认 CN-003~CN-007 时查出一处**会卡住启动的算术错误**（commit `a7e90fd`）：设计 §2.6 的公式 `DB_OP_BOUND = (RETRY+1) × (statement_timeout + delay)` 代入默认值得 **27s**，而校验表写的是 **18s**，且该条是启动门禁——按当时默认值 `27s ≤ 20s` 为假，**worker 会直接拒绝启动**。

其认领了算术源头（`RETRY=2` 意为「失败后再试 2 次」、总尝试 3 次，其 R2 给的 `2 × (8+1)` 漏算首次尝试），并给出订正方案 A：`statement_timeout 8000→5000`、`lock_timeout 5000→3000`，使 `3 × 6000 = 18s` 与文档已写的数字吻合。

**Owner 要求 Architect 先确认 claim 事务边界，确认后 DevOps 才执行 `ALTER ROLE`、Developer 才落连接池。** 本 CN 即该确认的结论。

## 问题描述

### A. 先认账：那段文字在我的文档里自相矛盾，我确认 CN-005 时照抄了错值

设计 §2.6 原文在**同一个代码块里**写了两个互相矛盾的算式：

```text
DB_OP_BOUND = (L1_WRITEBACK_RETRY + 1) × (STATEMENT_TIMEOUT + RETRY_DELAY)
            = (2 + 1) × (8000 + 1000)          ← 27s
当前取值下按 DevOps 给出的自洽算式：2 × (8s + 1s) = 18s ≤ 20s ✔   ← 18s
```

DevOps 说「三方同错」是准确的，但**这处自相矛盾在我的文档里**：我把公式和 DevOps 的代入值都抄了进去，没做一次算术核对。这属于我在 CN-005 确认时该拦住的。

### B. 更要紧的一处：`statement_timeout` 是「每条语句」的，不是「每个事务」的

DevOps 的方案 A 在算术上自洽，但它建立在一个**不成立的隐含假设**上——「一次写回 = 一条语句」。

**本次确认的事务边界**（据设计 §3.4 / §4.6 / §4.7 逐条点算）：

| 事务 | 语句数 | 构成 |
|---|---|---|
| **claim 事务**（写法 A） | **4** | `SELECT … FOR UPDATE SKIP LOCKED` → `UPDATE tasks`（置 running）→ `SELECT raw_items ⋈ sources` → `UPDATE raw_items`（置 processing + `l1_attempt+1`） |
| **写回事务** | **3** | `INSERT … ON CONFLICT DO UPDATE` → `UPDATE raw_items` → `UPDATE tasks` |
| 失败事务 | 2 | `UPDATE tasks` → `UPDATE raw_items` |

按 `statement_timeout = 5s` 代入真实语句数：

| 量 | 方案 A 的隐含算法 | **按实际语句数** |
|---|---|---|
| 一次写回最坏 | 5s | **15s**（3 条 × 5s） |
| 写回含重试（3 次尝试 + 2 次间隔） | 18s | **47s** |
| claim 最坏 | 未计入 | **20s**（4 条 × 5s） |
| 单条链路 DB 合计 | 18s | **67s** |

**67s ≫ 20s 收尾余量** —— 即方案 A 改完两个默认值后，启动门禁会通过，但**保证是假的**：真到停机时卡在写回，仍会超出宽限期被 SIGKILL，留下残留锁。这正是 AC-4.7 当初要防的事。

**根因**：PostgreSQL **没有内建的事务执行超时**。`statement_timeout` 逐语句生效，`idle_in_transaction_session_timeout` 管的是空闲而非执行。因此**光靠数据库侧配置给不出事务级上界**。

- 是否改变架构方案：**否**（新增的是一个应用层包装函数与一个配置项，不动分层与依赖方向）

## 处理方式

### 变更 1：`DB_OP_BOUND` 改用事务级超时，拆为两个量

```text
DB_WRITEBACK_BOUND = (L1_WRITEBACK_RETRY + 1) × (AI_DB_TX_TIMEOUT_MS + L1_WRITEBACK_RETRY_DELAY_MS)
                   = (2 + 1) × (5000 + 1000) = 18s      ← 用于收尾余量（停机时只可能卡在写回）
DB_OP_BOUND        = AI_DB_TX_TIMEOUT_MS + DB_WRITEBACK_BOUND
                   = 5s + 18s = 23s                      ← 用于 AC-3.6（单条完整链路含 claim）
```

拆开的理由：两个量的用途不同。收尾余量只需覆盖「停机瞬间正在进行的写回」；AC-3.6 的不变式要覆盖「单条从 claim 到写回的完整链路」，**原式漏了 claim 事务**。

**三条不等式，全部进启动门禁**：

| # | 不等式 | 当前取值 |
|---|--------|---------|
| 1 | `DB_WRITEBACK_BOUND ≤ L1_SHUTDOWN_GRACE_MS − N × L1_ITEM_BUDGET_MS` | `18s ≤ 20s` ✔ |
| 2 | `N × (L1_ITEM_BUDGET_MS + DB_OP_BOUND) < 1800s × 0.6` | `1 × 263s < 1080s` ✔ |
| 3 | `AI_DB_LOCK_TIMEOUT_MS < AI_DB_STATEMENT_TIMEOUT_MS < AI_DB_TX_TIMEOUT_MS` | `3s < 4s < 5s` ✔ |

**已定的 260 / 280 不用改**，`DB_WRITEBACK_BOUND` 仍是 18s——与 DevOps 方案 A 的结论数值一致，**只是语义从「每条语句 5s」纠正为「整个事务 5s」**，这才是 18s 真正成立的前提。不等式 2 由 258s 微调为 263s（含 claim），余量依旧约 4 倍。

### 变更 2：配置项调整（Developer 落地）

| 配置 | 原 | 新 | 说明 |
|---|---|---|---|
| **`AI_DB_TX_TIMEOUT_MS`** | — | **`5000`（新增）** | **事务级**上限，应用层 `asyncio.wait_for` 包整个事务 |
| `AI_DB_STATEMENT_TIMEOUT_MS` | `8000` | **`4000`** | 单语句兜底，须 < 事务级 |
| `AI_DB_LOCK_TIMEOUT_MS` | `5000` | **`3000`** | 等锁应比查询慢更早触发，便于日志区分 |
| `AI_DB_CONNECT_TIMEOUT_MS` | `5000` | 不变 | — |

**连接池统一事务入口**（设计 §4.10 已落）：

```python
async def run_tx(pool, fn):                      # claim / 写回 / 自愈 三类事务统一走这里
    async def _inner():
        async with pool.connection() as conn:    # 连接随事务获取释放，不跨 await 长持
            async with conn.transaction():       # 出作用域自动 COMMIT / 异常自动 ROLLBACK
                return await fn(conn)
    return await asyncio.wait_for(_inner(), timeout=cfg.tx_timeout_ms / 1000)
```

- 超时抛 `asyncio.TimeoutError` → 回滚 → 计入写回重试；`error_kind=db_error`。
- **不得逐事务另设超时**：三类事务统一用同一个值，否则 `DB_OP_BOUND` 要按最大值重算，多一个易漂移的量。

### 变更 3：`ALTER ROLE` 的边界（DevOps 落地）

`ALTER ROLE ai_worker SET statement_timeout = …` / `SET lock_timeout = …` **可以做且推荐**，作为「应用某条路径忘了 `SET`」的兜底。两条约束：

1. **取值须与应用层一致或更宽松**。角色默认值会被连接后的 `_configure`（`SET`）覆盖，故它约束不了应用；反过来若角色默认值**更严**（如 2s），在 `_configure` 执行前的那几条语句上会先生效，造成难以归因的偶发失败。
2. **它不能替代事务级超时**。`ALTER ROLE` 只能设语句级参数，PG 无事务级等价物——**`DB_OP_BOUND` 的保证只来自应用层的 `asyncio.wait_for`**，不能靠数据库侧配置绕开。

### 变更 4：测试 25 扩为三项

① 持锁冲突在 `lock_timeout`（3s）内失败；② **事务级**——mock 一个含多条语句、总耗时超 `tx_timeout` 但**每条都不超 `statement_timeout`** 的事务，断言在 5s 处被取消并回滚（**专验「语句级超时挡不住事务超时」**）；③ 配置校验断言三条不等式。

### 连带：CN-005 变更 3 与 PRD AC-4.7

CN-005 变更 3 给的取值（`statement_timeout=8s` / `lock_timeout=5s`，最坏 `2×(8+1)=18s`）与 PRD AC-4.7 的对应表述**由本 CN 订正**。**其提出该项的判断完全成立**——「claim 与写回两个事务在所有预算之外」这个洞是真的，本 CN 只是把封堵方式从「语句级」换成「事务级」。
