## 背景

Developer 在联调中实测出一处边界：**LLM 未给出 `scores` 字段时，ai 产出的是「结构完整但四维全 0、reason 全空」，不是结构残缺**——而 xiaobao 补算 tick 原本的判据是「结构残缺则跳过并告警」，**抓不到它**，会把该条当有效的「四维全 0」加权落值，这条新闻以「真的 0 分」的身份排到最后。

成因在 `normalize_output_node`：`dim()` 对每个维度取 `d.get("score", 0)` 兜底，故**结构永远完整**。

对方已按 ai 给的当下可用判别手段落地（`662238a`：跳过「四维全 0 **且** reason 全空」并告警），并明确「你方若后续加 `degraded:scores_missing` 标记，两层判别互为冗余，不冲突」。ai 侧是否加，属我方范围决策，登记待判断。

## 问题描述

### A. 该不该加：加

四条理由，按 Owner 定的「兼容性 / 健全性 / 稳定性」权重排：

1. **兼容性——不构成契约变更**。契约 `news-l1` 对 `tags_v2.processing` 的定义是「处理标签（**如** `engine:agent`）」，是开放集不是闭集枚举；且 `processing` 是数组，追加一个元素不改变结构。对方刚修好「`tags_v2` 只认数组形态」的前端缺陷（`aa7a05a`），数组路径已被正确消费。
2. **健全性——数据层直接可判优于靠推断**。当前判别要靠「`score=0` 且 `reason` 为空串」这个约定，它成立的前提是「真实打分时 LLM 必给 reason」——**这是一条经验规律，不是被任何机制保证的量**。本迭代已经因为「校验通过但保证不成立」翻过六次车，不该再新增一条同形状的依赖。
3. **稳定性——成本为一行，且与既有机制同源同形**。落点就在 `normalize_output_node` 已有的两行 `processing.extend(f"degraded:{d}" ...)` 旁边，不新增任何机制。
4. **两层冗余是好事不是浪费**：对方按 reason 判、ai 按数据判，任一层失效另一层仍在。对方已明确不冲突。

### B. **但 Developer 报的形态只是特例，真正的盲区在部分缺失**

`dim()` 是**逐维**取默认值的：

```python
scores = parsed.get("scores") or {}
def dim(name): d = scores.get(name) or {}; return ScoreDimension(score=_clamp_score(d.get("score", 0)), reason=str(d.get("reason", "")))
```

即 **LLM 给了 3 个维度、漏了 1 个时，那一维同样是伪 0 + 空 reason**。而：

- 对方已落地的判据是「四维**全** 0 且 reason **全**空」——**部分缺失完全抓不到**；
- ai 建议的 reason 判别手段同样是按「全 0 且全空」表述的，**同样抓不到**。

**所以整体缺失反而是最容易被发现的那一种（四维全 0 极其显眼），部分缺失才是真正的静默降级**：三维有正常分数和 reason、一维是伪 0，加权后只是「某条新闻分数偏低一点」，没有任何一侧会察觉。

**这与 `needs_context` 的 `false` 双来源、`domain_tags` 的 `{}` 形态是同一类**——默认值与有效值混在同一取值里且落在错误一侧——但比它们更隐蔽，因为**它连「异常形态」的外观都没有**。

## 处理方式

### 变更 1：判据下沉到维度级

```python
_SCORE_DIMS = ("timeliness", "impact", "confidence", "clarity")
missing = [n for n in _SCORE_DIMS if not isinstance(scores.get(n), dict)]
if missing:
    processing.append("degraded:scores_missing")
    # 缺哪几维进日志，不进标记（见变更 2）
```

**判据用 `not isinstance(..., dict)` 而不是 `not scores.get(n)`**：与 `map_domain_tags` 对 `{}` 的处置同一条纪律——`scores.get(n)` 为 `{}` 时是 falsy 会被蒙对，为 `{"score": 0}` 时是真值却同样缺 reason。**显式类型判定，不依赖真值性**，这正是双方三次踩坑后共同定下的做法（对方 2026-08-02 帖：「建议双方今后对 jsonb 列一律做显式类型判定」）。

### 变更 2：标记保持单段形态，缺失明细进日志

**不写成 `degraded:scores_missing:timeliness`**：既有 `degraded:*` 标记全部是 `degraded:{name}` 单段，对方的消费代码可能按全等或前缀匹配，加第三段有兼容风险，而本 CN 的第一条理由正是兼容性。缺哪几维通过 `obs/logging.py` 已有的 `degradations` 承载，不占契约面。

### 变更 3：知会对方（归 PM，不需其改码）

告知两点：① ai 已加该标记，与其 `662238a` 的 reason 判别互为冗余；② **其判据「四维全 0 且 reason 全空」抓不到部分缺失**，建议其补算 tick 改为**逐维**判别（任一维 `score=0` 且 `reason` 为空即视为该维无效）。这条对其是新信息——ai 上一帖给的判别手段也是按「全 0」表述的，**盲区是 ai 这边先说窄了**。

### 范围纪律（明确不做）

**不改 `_clamp_score` 的默认值行为、不把该情形改判为失败**。产出仍然有效（title / summary / tags / translation 都在），只是评分维度缺失——这正是「部分可用 = `succeeded`」的定义，是 v0.1 已验证的降级语义。加标记是**如实标注**，改判失败是**推翻既有语义**，后者属重大变更且会误伤。
