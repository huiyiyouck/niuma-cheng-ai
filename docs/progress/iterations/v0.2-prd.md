## 1. 迭代目标

处理 v0.1 遗留问题，提升服务稳定性与可观测性，并落地 RunRecord 持久化审计记录。具体包括：结构化 logging、服务托管化、KB 空结果语义优化、工具调用并发化、RunRecord 持久化。架构遵循 REQ-002 调研结论（不做强可重入，RunRecord 可选）。

## 2. 用户故事

- **US-1**（可观测性）作为 ai Owner，我想看到脱敏的结构化日志（run_id / provider / step / 耗时 / 错误 kind），以便定位问题和监控服务健康。
- **US-2**（托管化）作为 DevOps，我想服务能随系统启动自动拉起并在异常时重启，以便保障服务可用性。
- **US-3**（KB 语义优化）作为 xiaobao，当 KB 检索返回空结果时，ai 应正确标记而非误报失败，以便区分"无匹配"与"检索故障"。
- **US-4**（性能优化）作为 xiaobao，我想缩短单条处理耗时，以便提高整批处理吞吐量。
- **US-5**（审计记录）作为 ai Owner，我想持久化每一次 run 的关键元数据（输入摘要、输出摘要、耗时、工具调用、状态），以便审计、回溯和分析。
- **US-6**（生产验证）作为 DevOps，我想在生产环境验证多 provider fallback 真实可用，以便确保主 provider 故障时服务不中断。

## 3. 验收标准

> 每条覆盖正常 + 至少一个异常路径，可验证。PM 不自审本节，由 Architect / Developer 审。

- **AC-1 结构化 logging**：当服务启动时，应初始化统一的结构化日志格式；当各步骤（ingest_context / kb_search / link_reader / web_search / llm_process / normalize_output）执行时，应记录包含 `run_id`、`provider`（如有）、`step`、`duration_ms`、`status` 的日志；当步骤发生错误时，应记录 `error_kind`（区分 client_error / server_error / timeout / rate_limited / auth_error）和脱敏后的 `error_message`。日志不应包含 API key、完整 raw_content 等敏感信息。
- **AC-2 服务托管化**：当系统启动时，ai 服务应自动拉起；当服务进程意外退出时，应在配置的重试次数内自动重启；当服务端口被占用时，应启动失败并记录错误日志，不强行占用。托管配置应支持 systemd（Linux）和 launchd（macOS）两种方式。
- **AC-3 KB 空结果语义**：当 xiaobao `POST /v1/kb-search` 返回 `results:[]`（空数组）时，ai 应标记 `needs_context.kb_search=empty`，不应标记为 `failed`；当 xiaobao 返回非 200 或超时/错误时，才标记 `needs_context.kb_search=failed`。`tags.processing` 不应包含 `stub`。
- **AC-4 工具并发**：当需要同时触发 KB 检索、链接读取和 Web 搜索时，应并行执行而非串行；总耗时应明显低于串行执行（预期减少 ≥30%）；当某一工具失败时，其他工具应不受影响继续执行；并发执行应遵守 `WEB_SEARCH_MAX_RESULTS` 和总 timeout budget 约束。
- **AC-5 RunRecord 持久化**：当一次 news-l1 run 完成（`status=succeeded` 或 `status=failed`）时，应将 run 元数据写入持久化存储（默认 SQLite，支持可插拔），包括：`run_id`、`timestamp`、`input_hash`（raw_content 摘要）、`status`、`duration_ms`、`tool_summary`（各工具调用次数）、`provider_used`（实际使用的 provider）、`output_hash`（output 摘要）、`error`（如有）。当存储不可用时，应降级为仅日志记录，不影响主流程。查询接口支持按 `run_id` 精确查询和按时间范围分页查询。
- **AC-6 契约一致**：响应应符合 `news-l1` v1 契约（输入/输出字段与语义）；本迭代不改对外契约。
- **AC-7 多 provider 生产验证**：当生产环境配置 ≥2 个 provider 且主 provider 返回限流/超时/错误时，应自动切换到备用 provider 并成功返回结果；全部 provider 失败时才返回失败。

## 4. 范围边界

**本迭代做：**
- 结构化 logging：统一格式、脱敏、各步骤耗时与错误记录。
- 服务托管化：systemd / launchd 配置，自动拉起与重启。
- KB 空结果语义优化：区分"空结果"与"检索故障"。
- 工具调用并发化：KB / link / web 并行执行。
- RunRecord 持久化：SQLite 存储 + 基础查询接口。
- 多 provider 生产验证准备：部署阶段验证。

**本迭代不做：**
- 换非 reasoning 模型（需 Architect 评估，属技术选型，可作为后续优化）。
- 主链路算法逻辑变更（保持 v0.1 已验证的评分/标签/摘要/翻译逻辑）。
- 契约变更。
- 强可重入 checkpoint。
- 外部检索接口变更（KB/link/web 保持 v0.1 接口）。
- 第二任务类型实现。
