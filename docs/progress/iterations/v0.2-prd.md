## 0. 本迭代的决策准则（Owner 2026-07-26 定，优先于成本考量）

> 本节是 R2 新增，且**优先级高于本文档其余各节的取舍**。R1 三方 Review 中凡以「成本最低」为由给出的推荐解法，均按本准则重新裁定。

**以基础夯实、可扩展性强的方式开发，而不是图便捷。宁可现在麻烦一点、活多一点，也要让系统更健全、后期接入更友好。**

依据：ai 是**持续迭代**的产品。基础越牢，后续能扩展的功能越多；每次选「当下最方便」，都是给未来迭代加税，且债会在形态变化时集中爆发——本迭代的 async 问题正是此类（见 §2 US-8）。

本准则在 R2 中产生的三处具体裁定：

| # | R1 的成本最优解 | R2 按准则裁定 | 依据 |
|---|----------------|--------------|------|
| 1 | worker 跑独立线程绕开同步阻塞，处理核心零改造（Developer 问题 2 推荐①） | **改为 async 地基改造**（US-8 / AC-9） | 线程方案是「绕过问题」而非「解决问题」；同步阻塞是既有架构债，v0.3 的工具并发与批内并发必然要还，届时 worker 要推倒重来；线程与后续 async 混用会更难收拾 |
| 2 | 适配层 = 两个映射函数（入向/出向），成本几乎为零（Architect O-2 倾向、Developer 确认） | **改为定义数据源协议**（AC-2） | 映射函数方案下，第二个调用方接入要回来改我们的代码；协议方案下只需实现协议。`decisions/0002` 的多调用方定位要求后者 |
| 3 | `tags_v2` 第五类二选一（Developer 问题 1） | **主张 `sentiment` 与 `processing` 两个语义都保留**（C-10） | 二者不是同一种东西被塞进同一字段位：`sentiment` 是业务标签，`processing` 是降级/provider 的唯一结构化线索。丢任一都会削弱系统可诊断性 |

## 1. 迭代目标

承接 coordination `REQ-003`：把 ai 的 news-l1 集成模式从「HTTP 同步调用」**扩展**为「数据库契约边界异步解耦」——xiaobao 入库标记状态，ai 轮询 claim 取数、处理、写回共享库。

四条硬约束：

1. **并行而非替换**：HTTP 模式（`news-l1` v1 契约）继续有效，供灰度与回滚使用；新增 DB 模式（`news-l1-db` **v1.4** 契约）。
2. **协议隔离（按职责分层，不按模式对称）**：数据的**入向/出向映射**封装为映射协议（两种模式都真实实现），**控制流**（谁触发处理、结果落到哪）封装为拉取型数据源协议（仅 pull 型实现）。AI 处理核心不感知数据来源。这是 `decisions/0002`（多调用方预留）的硬要求。
   > **工程成本提示**：v0.1 的 `run_task(task_type, run_id, inp, client, tools)`（`tasks.py:55`）已是与传输层无关的签名、`main.py:34` 只调用它一行，因此**解耦的依赖方向是现成的**（Developer R1/R3 两轮确认）。但注意这不等于「处理核心零改动」——async 地基改造会翻新全仓 IO 相关代码，见 §8。
3. **schema 权属不越界**：共享库 schema 归 xiaobao，ai 只读指定表列、只写指定结果字段，不建表不改表。此约束已在数据库层被强制（xiaobao DevOps 2026-07-25 越权实测：`SELECT alerts` / `INSERT raw_items` / `UPDATE process_type` 均 `permission denied`）。
4. **async 地基先行**：本迭代把 IO 路径从同步改为 async（§0 准则裁定 1），作为 worker 模式与后续并发能力的地基。

**范围重排说明**：v0.2 原范围为稳定性六项，起草于 2026-07-04，比 REQ-003 提报（2026-07-05）早一天。Owner 2026-07-25 拍板重排：REQ-003 为主线，与 worker 形态耦合的三项（托管化 / 工具并发 / RunRecord）顺延 v0.3；logging 与 KB 空结果语义并入本迭代。R2 按 §0 准则追加 async 地基改造。

## 2. 用户故事

- **US-1**（调用方解耦）作为 xiaobao，我想入库并标记状态后立即返回、不必挂起等待单条 74~79 秒的 AI 处理，以便抓取与展示流程不被 AI 处理阻塞。
- **US-2**（多调用方定位）作为 ai Owner，我想取数/写回通过明确定义的协议接入，以便将来新增调用方时只需实现映射协议、无需改动处理核心，也不让 ai 被 xiaobao 的库 schema 绑死。
- **US-3**（worker 闭环）作为 xiaobao，我想 ai 能定期自动领取待处理的 AI 类新闻、处理完把结果写回共享库，以便无需我主动调用即完成 L1 处理。
- **US-4**（灰度与回滚）作为 Owner，我想在灰度出问题时能可靠回滚到 HTTP 模式。
  > **R4 订正（DevOps R3 问题 3）**：回滚**不是 ai 单方"改配置重启"，而是 ai 与 xiaobao 的双侧协同动作、且有顺序**。DB 模式下 xiaobao 不再发 HTTP 请求（改为入库 + 建 task），若 ai 单方切回 HTTP、xiaobao 仍在建 task，则**队列无人处理、静默积压，比不回滚更糟**。正确顺序：**先** xiaobao 切回 HTTP 集成模式（停止建 task、恢复主动调用）→ **后** ai 切 `RUN_MODE=http` 重启。反序会产生「两侧都不处理」的窗口。回滚瞬间已 claim 的在途条目仍需走优雅停机（AC-5.7）或等 xiaobao 1800s 回收。
- **US-5**（失败与卡死可控）作为 xiaobao，我想 ai 处理失败时按契约正确标记状态与尝试次数、按契约退避后才重试、卡死时我能按契约回收，以便队列不被永久占用、下游故障有恢复窗口。
- **US-6**（可观测性）作为 ai Owner，我想看到脱敏的结构化日志，并能从探活面直接判断 worker 是「活着且在处理」「活着但卡住」还是「已经死了」，以便在 worker 模式下定位问题。
- **US-7**（KB 语义修正）作为 xiaobao，当工具检索返回空结果时，ai 应标记「无匹配」而非「检索故障」（v0.1 遗留 D-3）。
- **US-8**（异步地基）作为 ai Owner，我想服务的 IO 路径全面改为 async，以便 worker 在处理长任务时仍能响应探活、且后续的工具并发与批内并发不需要重做架构。
  > 背景：v0.1 代码全同步（`grep "async def\|await" src/` 0 命中），LLM 与三个工具均为同步 `httpx`。FastAPI 本身是 async 框架，同步端点靠线程池兜底，HTTP 模式下侥幸无碍；worker 模式自行控制循环后该保护消失。这是**既有架构债在新形态下暴露**，且 v0.3 的工具并发化必然要还。
  > **R4 补充（Developer R3 问题 1）**：线程池兜底的消失**不只发生在 worker 模式**——`main.py` 端点一旦由 `def` 改为 `async def`，FastAPI 就不再派发线程池。若 async 改造有任何遗漏（某工具仍同步、某 IO 节点仍同步），**HTTP 模式会从「v0.1 的线程池并发」退化为「event loop 串行」，比 v0.1 更糟**。故 AC-9.5 增设对称的并发验收。

## 3. 验收标准

> 每条覆盖正常 + 至少一个异常路径，可验证。PM 不自审本节，由 Architect / Developer / DevOps 审。
> **契约版本**：本节所有契约引用均为 `news-l1-db` **v1.4**（Architect R3 问题 7 订正：实读契约已升 v1.4，权限矩阵已含 3 列 GRANT）。

- **AC-1 双模式开关**：
  1. HTTP 模式：`POST /v1/runs/news-l1` 行为与 v0.1 等价（**含并发行为等价，见 AC-9.5**）、不启动轮询。
  2. DB 模式：worker 按配置间隔轮询共享库。
  3. 配置缺失或非法时，应以 HTTP 模式启动并记录警告，不得静默进入 DB 模式。
  4. 开关粒度为**进程级**（一个进程只跑一种数据来源模式）。
  5. **切换/回滚是双侧协同动作**：ai 侧动作为「改配置并重启」，但整体回滚须按 US-4 的顺序执行（先 xiaobao 切回集成模式、后 ai 切 `RUN_MODE`）。**ai 侧不得单方执行回滚**；回滚预案（触发条件、双方联系方式、执行顺序）须在灰度开始前与 xiaobao DevOps 事先对齐，不得等故障时现商量。

- **AC-2 协议隔离**（判据：**依赖方向 + 两条真实控制流**，不比对输出内容）：
  1. **协议按职责分层，不按模式对称**（R4 重写，Architect R3 问题 1）：
     - **映射协议**（两种模式**均须真实实现，不得有空方法或 `NotImplementedError`**）：`to_l1_input(源数据) -> L1Input`、`from_l1_output(L1Output) -> 落地表示`。这是「第二个调用方需要实现的东西」。
       > **CN-003 澄清**：**恒等映射（identity）属于真实实现**——HTTP 模式的 `to_l1_input` 语义上就是恒等（`L1Input` 由 FastAPI 直接反序列化请求体得到），它明确表达了「HTTP 数据源的入向无需转换」这一事实；其 `from_l1_output` 则有实质逻辑（包装成 `RunResponse`）。本条禁止的是 `pass` / `NotImplementedError` / 返回 `None` 这类**没有语义的占位**。
     - **拉取型数据源协议**（**仅 pull 型数据源实现**，HTTP 模式不实现、也不假装实现）：取批 / 写回成功 / 标记失败 / 释放锁。
     > 原 R3 写法「DB 与 HTTP 数据源均为四操作协议的实现」已作废：HTTP 是「推」（端点被动接收、无取批、无锁），DB 是「拉」，控制流方向相反，套同一协议会让 HTTP 侧产生 2~3 个空方法。
  2. **判据（CN-003 拆为两条可证伪的）**：
     - **静态**：`grep` 断言处理核心（`tasks.py` / `graphs/` / `llm/`）中**不命中任何数据源概念词**（共享库表名、列名、`raw_items`、`tasks` 等）。可自动化执行。
     - **动态**：同一份处理核心分别接上 **HTTP 端点**与 **DB worker** 两条控制流，**两条均真实跑通**。
     > 原写法「两条控制流跑在同一份代码上、核心代码完全相同」是**同义反复**（只要不把核心复制两份就必然成立），描述的是事实而非可证伪的判据。
     > async 改造本身会修改处理核心，那是**地基变更**，不计入本条；本条约束的是「不因数据来源变化而改核心」。
  3. 两条控制流均应能产出结构合法的 `L1Output`（结构合法性判定，内容等价性归 AC-8）。
  4. **入向映射必须回填并规范化 `raw_content` 的 URL 键**（R4 订正，Architect R3 问题 5）：
     - **取值来源**：直接读 `raw_items.source_item_url` 列（契约 v1.4 已 GRANT SELECT，`x_twitter` 与 `rss` 均有值），**三类 source type 统一**。
     - **触发判定的真正落点是 `tools/link_reader.py:23` 的 `extract_url`**，它额外要求 `url.startswith(("http://","https://"))`；`news_l1.py:407` 的 `_extract_url` 是另一处（只被 `ingest_context_node` 用于填 context 条目、判定更宽、不检查前缀）。**两者判定不一致**。
     - **要求**：URL 须**规范化为带 `http(s)://` 前缀**后再填入 `raw_content`；无法规范化的按「无 URL」处理（两处判定因此一致）。
     - 若把 `raw_items.content` 原样塞入而不回填 URL 键，`_should_link_read` 恒为 False，**link_read 不报错、不降级、静默失效**（最难归因的一类问题）。
     - 验证方式（三例）：① `source_item_url` 带前缀 → 断言 link_read 被触发；② **有值但无协议前缀** → 断言规范化后仍触发，且 context 条目与触发判定使用同一个 URL；③ 该列为空 → 断言不触发、不报错、不降级。
  5. 映射失败的错误归类：入向映射失败（必填缺失/类型不符）归 `client_error`、**不重试**直接置最终失败；出向映射失败归 `server_error`、可重试。

- **AC-3 claim 正确性**：
  1. **claim 以 `tasks` 表为准，不扫 `raw_items`**（契约 v1.4 claim 规则）。WHERE 须含：`type='l1_ai_process' AND status='queued' AND run_after <= now() AND raw_item_id IS NOT NULL`。
     > **`run_after` 条件不可省**——缺它则退避完全失效（见 AC-5.2）。
     > **`raw_item_id IS NOT NULL` 不可省**（Architect R3 问题 6）：实读 `schema.ts:258` 该列 **nullable**（`tasks` 是通用任务表，存在不关联 `raw_items` 的任务类型是其设计）。若为空，适配层会在 claim 事务**已提交之后**才失败，此时条目已置 `running`/`processing`、锁已持有；加此条件可让异常 task 留在队列由 xiaobao 发现，**ai 不把不属于自己的任务标成 `failed`**（越界）。
     > **只 claim `tasks` 是安全的**（xiaobao Architect 确认）：`raw_items` 入库时 `l1_status` 默认 `not_started`、此时尚无 task，这类条目本就不该被领；ai 侧**不需要**孤儿条目探测逻辑。
  2. **取件顺序（R4 补回，Architect R3 问题 2）**：须 `ORDER BY priority DESC, run_after ASC`（走 `ix_tasks_queue(status, run_after, priority)`）。
     > 这是一条**回归修复**：R1 原有「按 `published_at` 升序」，R3 改为「只查 tasks」后该载体消失、未补替代，导致 R3 的 AC-3 **没有任何取件顺序**——无 `ORDER BY` 时 PG 返回顺序由执行计划决定，队列积压时新条目插队、老条目饿死完全可能，而 REQ-003 的动机之一正是解决积压。同时 `tasks.priority`（`schema.ts:262`，其队列索引形状明示预期访问模式）会被无视，对方设了优先级也不生效，且这类问题不报错、只是顺序不对，联调极难发现。
     > `priority` 的方向语义（数值大 = 优先？）已作为 **C-11** 转达 xiaobao 确认，**ai 不做假设**；确认前实现按「数值大 = 优先」编码并在代码注释标注待确认。
  3. claim 时同事务写入：`tasks.status='running'` + `attempt = attempt + 1` + `locked_by` + `locked_at`，`raw_items.l1_status='processing'`（后者是 xiaobao 卡死回收的判定依据，必须写）。
  4. 无待处理条目时 worker 应空转等待而非报错退出。
  5. **并发安全**：同一条目已被其他 worker 领取时不得重复领取。
  6. **批量上限不变式（正确性约束，非调优建议）**：单批 claim 数 N 必须满足 **`N × (单条 wall-clock 预算（AC-3.8） + DB 操作上界（AC-4.7）) < 1800s`**（xiaobao 卡死阈值）。
     > **CN-005 收敛**：原式未含 DB 操作时间，而写回重试明确在预算之外（设计 §4.6）。当前取值 `1 × (240 + 18) = 258s`，相对 1800s 有 7 倍余量。**AC-3.6 被声明为正确性约束，其输入就该与实际最坏值一致**——否则 N 上调时会重现「式子算得过、实际不够」（正是 CN-004 A 项刚修好的那类）。违反会直接产生「xiaobao 误回收 + ai 仍在处理」的双写竞态。验证方式：配置校验中拒绝超限取值。
     > **CN-003 订正**：原写「按 v0.1 实测 74~79s → N ≤ 22 → 取 N ≤ 8」。**79s 是 HTTP 模式 happy path 的实测均值，不是被任何机制保证的上限**——各段超时独立串行累加（`kb_search` 180s + `link_read` 8s + `web_search` 180s + LLM 180s），`RunOptions.timeout_ms` 默认 180000ms（`schemas.py:15`）下**单条最坏 ≈ 548s**，`8 × 548 = 4384s ≫ 1800s`，**用 PRD 自己的默认配置即违反**。且 74~79s 出自 HTTP 模式（彼时工具结果由 xiaobao 预取），用它约束 DB 模式的批量**基准不成立**（AC-8.2 已写明 DB 模式 KB 转为主动检索）。
     > 故 **`N ≤ 8` 降为暂定值**：**实现阶段不得直接按 `N ≤ 8` 落地**；N 须由 **O-3** 依据 AC-3.8 确定的单条预算重算。
  7. **claim 原子性：先实证、且已有 fallback，不阻塞实现**（R4 更新，C-6 + Architect R3 降风险附项）：
     - **实证：✅ 已完成（CN-007）** —— xiaobao DevOps 2026-07-28 以 `ai_worker` 身份在 `news_test` 实测，`FOR UPDATE SKIP LOCKED` + claim 写入**在列级 GRANT 下可行**（返回 `UPDATE 1`）。**claim 采用写法 A**，不再是「两种写法二选一」。
     - **C-6 已完整闭合（2026-07-28 实机订正）**：xiaobao DevOps 验权限侧（单会话可行性），**ai DevOps 补齐并发侧**——两会话同时 claim 拿到**不同行**，`SKIP LOCKED` 生效、并发不重复领取；越权仍被拒；全程 `ROLLBACK`、队列未消耗。**列级 GRANT 足以支撑行锁**，xiaobao 预留的「改授表级 UPDATE」**不必执行**。
     - **§4 的「v0.3 多实例前必须先解决 C-6」前置据此解除**（因 C-6 已解决，非要求被放弃）。**fallback 写法仍保留为备用**（作为权限变更后的退路，非因 C-6 未闭合），其三条限定同样保留。
     - 原实证要求（保留供多实例验证时复用）：以 `ai_worker` 身份执行 claim SQL，断言可执行且并发不重复。执行安排见 §5「C-6 实证」（DevOps 已给出 6 步方案，全程事务内 `ROLLBACK`、不消耗预置队列）。**时点为实现阶段开工前**（前置条件见 §5 待办 1、2）。
     - **fallback（若列级 GRANT 不支撑 `FOR UPDATE`）**：改用不依赖行锁的条件式原子 `UPDATE ... RETURNING`——子查询按 AC-3.1/3.2 的条件与排序选出 id，外层 `UPDATE ... WHERE id IN (...) AND status='queued' RETURNING id, raw_item_id`。它只需列级 UPDATE + 子查询列 SELECT，不触发 `FOR UPDATE` 的表级权限检查，且**不会重复领取**。
     - **fallback 的三条限定（CN-003 订正）**：
       ① **并发行为**：子查询不带 `SKIP LOCKED`，两个 worker 会选出**完全相同的 N 行**；外层 `UPDATE` 一个阻塞另一个，先提交者拿走全部 N 行，后到者解除阻塞后重新求值 `AND status='queued'` 时这 N 行全被排除 → `RETURNING` 返回 **0 行**。即**后到者本轮拿空批**（不是「阻塞后拿到其他行」），需等下一轮询周期。
       ② **前置条件：须在 `READ COMMITTED` 隔离级别下执行，驱动/连接池不得改隔离级别**。该写法的正确性依赖 PG 的 **EvalPlanQual 重新检查**，仅 READ COMMITTED 生效；在 `REPEATABLE READ` / `SERIALIZABLE` 下第二个事务不重新求值，而是直接抛 `could not serialize access due to concurrent update`——**claim 会报错而非安全拿空批**，且表现为偶发报错、极难归因。PG 默认 READ COMMITTED，但某些池化配置会显式设置。归 O-6/O-9 落定并在实现中断言。
       ③ **已知限制**：多实例下并发语义与 `SKIP LOCKED` **不等价**（见 §4 的 v0.3 前置）。
     - v0.2 为单 worker 实例、批内串行（§4），上述代价可忽略。
     - 因此 **C-6 不构成 worker 地基返工风险，降级为「两种写法二选一」**；实现阶段不必等待 xiaobao 改授权。

     > 实现成本低：`ChainedAIClient` 已有 budget 机制（`client.py:99`，但 `client.py:216` 构造时未传 `budget_ms` 故退化为 `timeout_ms`）、`tool_budget_used`（`news_l1.py:69`）已有**次数**预算——本条是补**时间**维度并提到 graph 层。

- **AC-4 写回正确性**：
  1. **写入方式：UPDATE 占位行**。占位 `processed_news` 由 xiaobao 在 L0 通过时创建（其产品硬约束：L0 通过后新闻须立即在前台可见），Architect 已独立核证（其 `v0.6.1-design.md:357` 推荐方案①、`schema.ts:202-205`、`:201`）。

- **AC-4.7 数据库操作超时上限（CN-005 新增，解 DevOps 设计 R2 附条件）**：
  1. 数据库操作须设时间上限，**不得依赖默认无限等待**：`connect_timeout`（新增配置 `AI_DB_CONNECT_TIMEOUT_MS`）、`statement_timeout`、`lock_timeout` 三项须在连接池初始化时显式设置。
     > 背景：`ItemBudget` 只覆盖**处理阶段**，claim 与写回两个事务**在所有预算之外**；无上限则 AC-5.7 的宽限期算式（260s = 240s 预算 + 20s 收尾余量）与设计 §4.6 写回重试的「≤2s」断言均失去保证。
  2. **取值须与 AC-5.7 的收尾余量自洽**：`(写回重试次数 + 1) × (statement_timeout + 重试间隔) ≤ 收尾余量`。按设计当前取值（重试 2 次 / 间隔 1s / 余量 20s），**`statement_timeout=8s`、`lock_timeout=5s`** 满足自洽（最坏 `2 × (8+1) = 18s < 20s`），**无需改动已定的 260/280**。
  3. 验证方式：配置校验中断言上述不等式；构造一次持锁冲突，断言在 `lock_timeout` 内失败而非无限等待。
  4. 写回事务本身是毫秒级的，上述超时只对「等锁」这类异常路径起封顶作用，对正常路径无影响。

- **AC-5 失败、退避与重试语义**：
  1. **重试上限读 `tasks.max_attempts` 列，禁止硬编码 3**（C-8 定案）。判定用 `tasks.attempt` 对比 `tasks.max_attempts`；`raw_items.l1_attempt` 为镜像值、同事务一并推进。
  2. **退避真源是 `tasks.run_after`，禁止自行用 `updated_at + backoff(attempt)` 计算**。
     > 根因：并非「契约 claim SQL 缺时间条件」，而是 xiaobao 此前 GRANT 少给了 `run_after` 的 UPDATE 权限（已认领并补 GRANT，双库对称）。ai 自算会与其 `requeueTask` 形成两套退避真源，卡死回收介入后必然漂移。
     **实现**：可重试失败时写 `tasks.status='queued'` + `run_after = now() + backoff(attempt)`，claim 时按 `run_after <= now()` 过滤。
     **退避数组越界行为（R4 补，Architect R3 问题 3）**：契约退避表为 `[60s, 300s, 900s]`（长度 3），而 `tasks.max_attempts` 的 **schema 默认为 5**（`schema.ts:265`）——第 4、5 次重试 `backoff(attempt)` 越界。**规定：`attempt` 超出退避数组长度时取数组末值（900s）**，不得取 0 或崩溃（取 0 即静默退化回「立刻重领」，正是 C-4 刚修好的问题）。该行为已作为 **C-12** 请 xiaobao 确认（补齐退避表 或 书面确认「超出取末值」），并请其订正契约 §task type「最大尝试次数 3」与 schema 默认 5 的不一致。
  3. 可重试失败（未达上限）：同事务写 `tasks.status='queued'` + `run_after`、`raw_items.l1_status='retryable_failed'` + 脱敏 `l1_error`、`tasks.last_error_kind`，递增计数并释放锁。
  4. 最终失败（达上限）：写 `tasks.status='failed'`、`raw_items.l1_status='final_failed'` + `l1_error` + `l1_processed_at`。
  5. 验证方式：构造失败条目，断言退避窗口内不被重领、窗口后被重领；断言 `attempt` 达 `max_attempts` 后进 `final_failed` 且不再被领；**断言 `attempt=4`（越界场景）时退避取 900s 而非 0**。
  6. **残留锁自愈口径**：ai 仅可在启动时回收 `locked_by` 等于**本 worker 标识**的残留 `processing` 条目；其余交 xiaobao 的 1800s 回收，ai 不回收他人锁。`locked_by` 标识规则见 O-10。
  7. **优雅停机（R4 补下限与跨层一致，DevOps R3 问题 2）**：
     - 收到 SIGTERM 时停止新 claim、处理完当前条目后释放锁再退出；超出宽限期才强杀并退回卡死回收路径。
     - **宽限期须 ≥ 单批最长处理时间（N × 单条耗时上限，N=8 时约 632s），且 < 1800s**。
       > 只写上限是不够的：配 60s / 90s 完全符合「< 1800s」的字面要求，但在真实批量下每次停机都会中途强杀，残留锁照样产生、AC 验收必然失败。
     - **三层须逐层放大，且不得取同一数值**（**CN-005 订正**，原写「三层须配一致值」）：**应用层 `L1_SHUTDOWN_GRACE_MS` ≤ ASGI 层 `--timeout-graceful-shutdown` < 托管层 systemd `TimeoutStopSec`**（设计 §4.8 落定为 260s / ≥260s / 280s）。
       - 三层语义：① 应用层 = worker 收到停机信号后**最多用多久收尾**；② ASGI 层 = uvicorn 等待在途请求与 lifespan 收尾的上限；③ 托管层 = 从 SIGTERM 到**发出 SIGKILL** 的墙钟。
       - **为什么不能相等**：若应用层与托管层同为 260s，当 worker **恰好用满** 260s 完成最后一次写回时 systemd 在同一时刻 SIGKILL——**写回事务可能在 COMMIT 之前被杀**，留下 `l1_status='processing'` 残留锁等 1800s 回收。这正是整条优雅停机链要防的事，却会因为「三个数字写成一样」而发生；且该竞态**只在恰好用满宽限期时触发，自测几乎必不复现**。
       - **强制点在部署脚本，不在应用启动校验**：应用进程**读不到自身的 systemd 配置**，启动门禁只能校验应用侧的两个量（`L1_SHUTDOWN_GRACE_MS ≥ N × L1_ITEM_BUDGET_MS`）。
       > 原表述由 CN-003 变更 3.4 逐字搬用 DevOps 措辞而来，本意是「三层必须协调、不能各自为政」，字面被读成「数值相等」——**表述责任在 PM**。
     - **验证方式**：在 **N > 1 的批处理进行中**（而非单条）发送 SIGTERM，断言**整批**锁均被释放、状态未停留在 `processing`。
     - **CN-003 补充**：① 宽限期下限的计算基准由「N × 单条耗时上限」改为「**N × AC-3.8 的单条 wall-clock 预算**」（原基准 79s 未被保证，见 AC-3.6 的 CN-003 订正）；② **优雅停机期间探针失败是预期行为**，托管层的健康检查重启策略须与 `TimeoutStopSec` 协同——与 AC-9.3 的三态映射是同一处的两面：那条管「别把收尾当死」，本条管「等多久」。

- **AC-6 结构化 logging**：
  1. 服务/worker 启动时初始化统一结构化日志格式；各处理步骤记录 run 标识、`raw_item_id`、`step`、`duration_ms`、`status`；错误时记录 `error_kind`（`client_error` / `server_error` / `timeout` / `rate_limited` / `auth_error` / `db_error` / `mapping_error` / **`budget_exhausted`**）与脱敏 `error_message`；**并记 `budget_remaining_ms`**（该步骤结束时的剩余预算，CN-005 新增）。
     > **`budget_remaining_ms` 的作用**：`error_kind=budget_exhausted` 只能告知「预算耗尽了」，逐步的剩余预算才能定位**是哪一段吃掉的**，从而判断该调 `KB_TIMEOUT_MS` / `WEB_SEARCH_TIMEOUT_MS` 还是总预算。
     > **`budget_exhausted` 与 `timeout` 必须分开（CN-004 新增）**：`timeout` = **某次外部调用自身超时**（LLM/工具的单次调用未在其段上限内返回）；`budget_exhausted` = **单条 wall-clock 预算（AC-3.8）被耗尽**——前序步骤已把时间用光，本步骤根本没机会发起或未能完成。二者处置完全不同：前者指向 provider 侧（调 provider / 查 fallback 链），后者指向各段上限分配（调 `KB_TIMEOUT_MS` / `WEB_SEARCH_TIMEOUT_MS` / 总预算）。DB 模式下日志是主要观测面，混记会让灰度期无法定位该调哪一个。
  2. **数据库口令脱敏须可验证**：最常见的泄漏路径是连接失败时驱动异常带出 DSN。数据库连接/查询异常必须在记录前重写为不含连接串与口令的消息。验证方式：以错误口令发起连接，断言日志中不出现口令子串。
  3. 日志统一输出到 **stdout**，由托管层收集——**v0.2 起 systemd unit 使用 `StandardOutput=journal`，journald 自带轮转与配额**，无需指定落盘路径、无需人工轮转；**应用内不实现轮转**。
     > **CN-005 订正**：原写「由 DevOps 指定落盘路径并人工轮转」源自托管化顺延时期的 `nohup` 预设，托管化落地后已不适用（按原文会去配一套不需要的日志轮转）。应用侧行为不变。
  4. **logging 须以注入方式接入**（随 state 或依赖注入传入），不得在 `graphs/` 内直接 import 全局 logger。
  5. 日志不得包含 API key、数据库口令、完整 `raw_content`。
  6. 降级与 provider 事实须在日志中冗余一份（不只依赖 `tags.processing` 承载）。

- **AC-9 async 地基、探活与回归**（§0 准则裁定 1）：
  1. IO 路径全面改为 async：四个出网调用点（`llm/client.py:176`、`tools/kb.py:50`、`tools/web_search.py:24`、`tools/link_reader.py:38`——经 Developer `grep` 实查，全仓仅此四处、行号逐一准确）由 `httpx` 同步接口改为 `AsyncClient`，沿调用链改造至 `tasks.run_task` 与 `main.py` 端点；LangGraph 节点使用 async 形态（`tasks.py:64` `invoke → ainvoke`）。
  2. **DB 驱动须与 async 地基一致**（选型见 O-9）——不得出现「同步驱动 + async 核心」的混合形态。
  3. **探活可用性（三重，可验证）**：
     - **抗阻塞**：DB 模式下**单条处理进行中（≥60s）时，`/health` 仍须在 2s 内返回**。DB 模式的 `/health` 只做存活探针，不注册 `POST /v1/runs/news-l1` 路由。
       > 这条一次性验死或验活「进程级 + DB 模式仍监听 `/health`」的组合：若 async 改造不彻底导致 event loop 被阻塞，探针会按超时判死 → 重启 → 制造残留锁 → 每条延迟 30 分钟等回收，比没有探活更糟。
     - **worker 生死 —— 三态 + 状态码映射（CN-003 订正，解 Architect R4 中③ + DevOps R4 中②）**：worker 循环必须包在**顶层异常捕获**内，任何逃逸异常须记 `error_kind` 日志并显式标记状态，不得静默退出。`/health` 响应体须含 **`worker_state ∈ {running, stopping, dead}`**，并**写死 HTTP 状态码映射**：

       | `worker_state` | HTTP 状态码 | 托管层应有反应 |
       |---|---|---|
       | `running` | **200** | 保持 |
       | `stopping`（收到停机信号、正在收尾） | **200**（附 `stopping` 状态） | **等待**（等到宽限期），**不得重启** |
       | `dead`（异常退出） | **非 200** | 重启 —— **⚠️ v0.2 无自动消费方**（CN-005 补） |

       > **`dead` 的 v0.2 能力边界**：`Restart=on-failure` 只看**进程退出码**，而 worker 协程死亡时**进程仍存活**（设计 §4.1 `_on_worker_done` 正是该场景），systemd 不会做任何事；消费该 503 的 healthcheck timer 顺延 v0.3。**v0.2 的 `dead` 靠人工或外部监控发现**，表中「重启」描述的是 v0.3 落地后的目标状态。

       > **为什么必须三态**：二态（活/死）无法表达「正在正常地退出」。停机过程是 SIGTERM → 停止 claim → 收尾（最坏 = 单批预算）→ worker task 结束，此时进程仍在（uvicorn 关闭中）。若 `stopping` 落进「非 200」，v0.3 托管层会在正常收尾期间判死重启——Architect 要避免的事原样发生。
       > **为什么必须写死状态码**：托管层探针判的是**状态码**而非响应体字段；只改字段值不改映射，等于换了个字段名而问题不变（DevOps R4 中②）。
       > 若 worker 以 `asyncio.create_task` 跑在同一 event loop 上，其**未捕获异常不会终止进程、不会打断 loop**——只在 task 被 gc 且异常从未取出时于 stderr 打一行 `Task exception was never retrieved`。此时 worker 已死，而进程、HTTP、`mode` 全部正常，**探针会完整地报告「健康」**，托管层永远不会重启它。
     - **在途进度（R4 补，DevOps R3 问题 4）**：`/health` 除 `mode`、`last_poll_at` 外还须暴露**在途处理进度**（`in_flight` 条数与 `current_item_started_at`，或等价字段），使「活着且在处理」与「活着但卡住」可区分；并写明 `last_poll_at` 的**陈旧容忍上限 = N × AC-3.8 的单条 wall-clock 预算 + 轮询间隔**（CN-003 订正基准）。
       > 否则：worker claim 一批 8 条后进入处理，若轮询与处理同循环，`last_poll_at` 在整批处理期间（最坏 632s）都不更新，**正常工作的 worker 与卡死的 worker 表现相同**；运维按「60s 未轮询即判死」处理会重启健康进程并制造残留锁。
     - 三者分工：`worker_alive` 答「还在不在」，`in_flight`/`current_item_started_at` 答「有没有卡住」，2s 响应答「探活本身可不可信」。

- **O-2（P1）协议的抽象边界**：**按职责分层（映射协议 / 拉取协议），不按模式对称**（R4 定，Architect R3 问题 1）。协议切在 `tasks.run_task` 之上；协议应含哪几个操作、`L1Input`/`L1Output` 是否直接作为跨层契约、实现的注册与选择方式，由 Architect 落定。
- **O-6（P1）事务边界与连接管理**：三段式（claim 短事务 / 处理无事务 / 写回短事务）已写入 AC-4.3。**async 下连接必须随事务获取与释放，不得跨 `await` 长持**（R4 补，Architect R3）——三段式的价值正是让连接只在毫秒级事务内被占用；若图省事在 worker 循环外层开一个连接贯穿整批（8 × 79s ≈ 632s），会同时踩上服务端 `idle_in_transaction_session_timeout` 与连接池饥饿，等于把三段式作废。连接池规模按「worker 实例数 × 批内并发度 + 1」，v0.2 单实例串行下 2~3 即可。
- **O-8（P0，本迭代最大技术风险）async 改造的切分与回归策略**：改造涉及 4 个 IO 点 + 2 个协议 + `DefaultNewsTools` + 4 个 IO 节点 + `invoke→ainvoke` + `run_task` + 端点 + 约 21/36 例单测。**风险在回归，不在重写。**
  - 回归基线已从本条**提升进 AC-9.4**（黄金样本外部化），不再是「待定的方法」。
  - **async 划线判据（R4 补）**：**无 IO 且耗时为毫秒级**的节点保持同步（`ingest_context` / `normalize_output` 是纯内存字符串处理）。不是单看有无 IO——LangGraph 的 `ainvoke` 允许同步节点混用，但同步节点**在协程中被直接执行、其耗时会占用 event loop**；若将来某纯计算节点变重（引入本地推理或大文本分词），必须移出 loop。
  - **实现提醒（CN-003 记入，Architect R4 附注）**：async 化后 `except Exception` **不捕获** `asyncio.CancelledError`（它继承 `BaseException`），这是**正确且必须保持**的行为——若改造中有人把节点的 `except Exception` 顺手改成 `except BaseException` 或裸 `except:`，`CancelledError` 会被吞掉，**AC-5.7 的优雅停机会静默失效**（SIGTERM 后协程不响应取消、一直跑到宽限期强杀），而该失效在验收里只表现为「优雅停机断言失败」，极难定位到具体 `except` 子句。
  - 切分方式（一次性改 vs 分层改）、LangGraph async 节点的编排调整，由 Architect + Developer 落定。
- **O-9（P1）DB 驱动选型**：**倾向 psycopg3(async)**（Developer 建议、Architect 采纳）。理由（均非成本理由）：① psycopg3 用 `%s` 占位符与标准 DBAPI 语义，若 C-6 实证失败需在 `FOR UPDATE` 与 `UPDATE ... RETURNING` 两种 claim 写法间迁移，成本最低；asyncpg 的 `$1` 会把 SQL 与驱动绑死；② 同步与 async API 同构，将来若需同步运维脚本不必引第二个驱动；③ 服务端游标与 `COPY` 对 v0.3 的 RunRecord 更友好。性能差异在本场景无意义（瓶颈是 74~79s 的 LLM 调用）。最终由 Architect 拍定。
- **O-11（P2，CN-007 降级）v0.2 的处理能力已确认满足 xiaobao 日增量**：
  - **xiaobao PM 已答（2026-07-28）**：活跃期日均 **15~30 条**（生产 757 条系 X Stream 约 50+ 天累积），当前断流中日增为 0。可预见增长逐项排查——账号扩容仍在几十条量级 / rss·jin10 近期不接入 / 无按比例放量计划 / **无任何「上千条/天」规划场景**。对照 ai v0.2 能力上界（340~920 条/天）**有 5~10 倍余量**。
  - **结论：v0.3 并发化无需排期前移**（原 P1 的核心不确定性已消除，降为 P2）。
  - **监测保留但降级**：灰度期仍监测队列长度趋势作为兜底，判据由「单调增长超 24h 即触发排期前移」放宽为「**若出现持续单调增长则复核日增量假设**」。
  - **对方承诺**：xiaobao PM 承诺若未来出现量级跃迁（如批量新增信息源），**提前经 coordination 沟通文档知会**，不让 ai 靠队列报警才发现。

1. **高｜DB 模式下探活面缺失，AC-1~AC-8 无一条覆盖「怎么判断 worker 活着」。** O-4 倾向进程级开关，则 DB 模式进程很可能不起 HTTP 服务，`/health`（`main.py:20`）随之消失。v0.1 的全部运维手段（`curl /health`、`lsof` 看端口）在 DB 模式下同时失效，而 worker 静默死亡的表现与「队列为空空转」完全一样——运维无法区分。这不是实现细节，是验收缺项：没有探活面就无法定义部署就绪检查的通过条件，也无法接任何托管层的存活探针。建议 AC-1 增补：DB 模式下仍须提供可外部观测的存活面，最低限二选一——① DB 模式进程仍监听 `/health`（只做探活、不接受 run 请求）；② 每轮轮询输出心跳日志并暴露 `last_poll_at`，由 DevOps 按日志时间戳判活。选哪个由 Architect 在 O-4 定，但「必须有」应写进 PRD。

2. **高｜停机与回滚时的残留 `processing` 锁无任何验收覆盖，回滚不是「改配置重启」那么简单。** AC-1 把回滚定义为「改配置并重启」，US-4 同调。但 DB 模式的回滚风险不在开关，在**回滚瞬间的库状态**：worker 被停时，已 claim 未处理完的条目停留在 `l1_status='processing'` + `locked_by` 已写，切回 HTTP 模式后这批条目在 ai 侧无人处理，只能等 xiaobao 侧 30 分钟卡死回收（契约 §卡死回收）。按单条 74~79s、批量 N 条计，一次不优雅的停机会让 N 条新闻延迟至少 30 分钟。AC-5 只覆盖了「worker 被杀死」这一被动路径（依赖 xiaobao 回收，正确），但没覆盖**主动停机/回滚**这一必然发生的路径。建议 AC-1 或新增 AC 增补：收到停机信号（SIGTERM）时 worker 应优雅停机——停止新 claim、处理完当前条目后释放锁，超出宽限期才强杀并退回卡死回收路径；并明确宽限期上限须小于 xiaobao 的 1800s 阈值。这条同时是 v0.3 托管化的前置（无优雅停机，systemd/launchd 的 restart 会持续制造残留锁）。

- 与 DevOps R1 的关系：DevOps 已覆盖运行形态、探活、停机、脱敏、造数、日志 sink。本轮不重复其 7 条，只在 A-5 与末节对其 O-3 数学与 O-4 相关结论做确认或补充。本轮问题集中在**输入侧映射与状态机真源**——这是 DevOps 未覆盖、且比 O-1 影响面更大的一片缺口。

**总体判断**：worker 闭环的**输出侧**（写回 `processed_news` + 推进状态）在契约里被描述得较完整，但**输入侧**（如何从库里的 `raw_items` 构造出与 HTTP 模式等价的处理输入）几乎没有真源支撑。AC-8 要求「两种模式产出的业务字段等价」，而按现有契约授权的可读列，DB 模式**构造不出等价的输入**，因此 AC-8 当前不可达。这不是实现难度问题，是契约缺项，须回到 xiaobao 侧补齐后 PRD 才能定稿。

问题：

1. **阻塞｜DB 模式的输入构造缺口，AC-8「两模式业务字段等价」当前不可达。** 三处具体缺口：

   - **`domain_tags` 无契约授权来源**。HTTP 契约 `L1Input.domain_tags`「来自 L0 分类」，是 prompt 与工具路由的输入之一（`graphs/news_l1.py:311` `_build_query` / `:320` `_build_kb_query` 均消费）。但 `news-l1-db` v1 §raw_items 的 ai_worker 可读列只有 `id / source_id / content / published_at / l0_status / l1_status / l1_attempt / process_type`——只有 L0 的**状态**，没有 L0 的**分类结果**。DB 模式下 `domain_tags` 只能恒为 `[]`，与 HTTP 模式输入不等价。
   - **原文 URL 不在可读列**。HTTP 契约 §raw_content 约定明写「若 `raw_items.source_item_url` 存在而 `raw_content.url`/`canonical_url` 不存在，xiaobao 必须补入 `raw_content.url`」——也就是说 URL 在 xiaobao 侧是**独立列 `source_item_url`**，靠调用方在构造请求时补进 `raw_content`。DB 模式没有这个构造方，而 `source_item_url` 不在 ai 可读列清单里。后果是 `_extract_url`（`graphs/news_l1.py:407`）取不到 URL → `link_read` 工具在 DB 模式下**整条路径失效**（`_should_link_read`，`:267`），处理质量与 HTTP 模式产生系统性差异。
   - **预取上下文在 DB 模式无提供方，且引出一个 PRD 未讨论的架构事实**。HTTP 模式下 `kb_results` / `link_content` / `search_summary` 由 xiaobao 预取传入；DB 模式无人预取，KB 检索只能由 ai **主动**发起，而 KB 检索的唯一通道是回调 xiaobao 的 `POST /v1/kb-search`（`tools/kb.py`，契约 `kb-search.md`）。**结论：DB 模式并未消除 ai → xiaobao 的 HTTP 依赖，只是把方向反转了。** PRD §1「集成模式从 HTTP 同步扩展为数据库边界」的表述会让人误读为 DB 模式下两侧无 HTTP 耦合，实际仍需 xiaobao 侧 `kb-search` 接口与 `x-admin-token` 可用；xiaobao 侧 HTTP 不可用时，DB 模式退化为无 KB 上下文。这同时改变 `tool_summary` 的统计口径（DB 模式下 kb_search 计数必然从 0 变为常态 ≥1），而 AC-8 说「业务字段等价」——工具调用统计不属业务字段，但该差异应显式写明，否则联调时会被当成 bug。

   建议：§5 前置依赖追加「DB 模式输入构造所需的可读列补充」，并在 coordination 向 xiaobao 提出契约订正请求——最少需要把 L0 分类结果字段与 `source_item_url` 纳入 ai_worker 可读列（或明确它们已在 `content` jsonb 内、给出 key 名）。AC-8 应把等价口径**限定**为「在输入等价的前提下业务字段等价」，并单列一条说明 DB 模式的输入差异项与 KB 主动检索带来的 `tool_summary` 口径变化。

2. **阻塞｜`tasks.status` 的取值集合没有任何真源，AC-4 / AC-5「同步更新 tasks 状态」不可实现、不可验证。** `news-l1-db` v1 给了 `l1_status` 的完整枚举（§l1_status 枚举），但 `tasks.status` 只在字段表里写「任务状态 / 可更新」，取值集合与状态转移全缺。AC-4 要求「同步更新 `tasks` 状态」、AC-5 要求「置 `retryable_failed` / `final_failed`」——后者是 `l1_status` 的值，`tasks.status` 该写什么无从得知，也无法写出可验证的断言。ai 侧不能自行猜一套枚举写进库（`tasks` 是 xiaobao 业务真源，猜错会污染其状态机与卡死回收逻辑）。建议：作为 P0 契约缺项提报 xiaobao，要求补 `tasks.status` 枚举与转移规则（含「谁设置」列），与 `l1_status` 的对应关系写清；在此之前 AC-4/AC-5 中涉及 `tasks.status` 的部分不能定稿。

3. **阻塞｜`processed_news` 是 INSERT 还是 UPDATE 未定，且与 `news_positions` 触发器时序耦合，AC-4 存在两种互斥实现。** 契约 §职责边界表写 xiaobao 侧「`processed_news` 写入（AI 类）| ❌ 占位创建」，字面意思是 xiaobao **已插入占位行**、ai 做 UPDATE；但 §权限矩阵给 ai_worker 的是 `SELECT, INSERT, UPDATE` 三权，PRD AC-4 也只写「向 `processed_news` 写入」，未区分。两种语义导致的差异是实质性的：

   - 若 xiaobao 占位 INSERT：`news_positions` 触发器（§触发器，`INSERT` 后触发、`SECURITY DEFINER`）在**占位时**就已执行，此时 `score_total` / `score_dimensions` 均为空——若排序位依赖分值，会先按空值排一次；ai 后续 UPDATE 不再触发关联，排序位如何更新无契约说明。
   - 若 ai INSERT：触发器在结果齐备后触发，语义自然，但 ai 需生成 `id`（uuid PK，`raw_item_id` 是否有唯一约束未说明），且重试场景必须定义幂等键（同一 `raw_item_id` 重试时是 upsert 还是产生第二行）。

   AC-4 的「单事务、不留结果已写但状态未推进的不一致」在两种语义下事务范围也不同。建议：PRD 明确采用哪一种（架构上我倾向 **ai INSERT + 以 `raw_item_id` 为幂等键做 upsert**，让触发器在结果齐备后触发，语义最干净），并请 xiaobao 在契约中把写入方式、`raw_item_id` 唯一约束、重试幂等语义、触发器与 UPDATE 的关系一并写明。这条与 O-1 强相关：若 `score_total` 归 xiaobao（方案 A），还须明确 xiaobao 何时补算——ai 写完 `completed` 之后由谁触发，以及在补算完成前 `news_positions` 的排序位是否可见。

4. **高｜契约定义的退避间隔没有进入 claim 条件，失败条目会被立即重复领取，AC-5 的重试语义与契约自相矛盾。** 契约 §task type 定义 `l1_ai_process` 退避间隔 `[60s, 300s, 900s]`，但 §AI 待处理队列 claim 规则的 SQL 只有 `process_type='ai' AND l1_status IN ('queued','retryable_failed') ORDER BY published_at ASC LIMIT N`——**没有任何时间条件**。按此实现，一条刚被置为 `retryable_failed` 的条目会在下一个轮询周期（DevOps 建议 10~30s）立刻被重新 claim，退避完全失效：失败条目将以轮询间隔的节奏连续消耗 3 次尝试，几十秒内耗尽重试预算进入 `final_failed`，而退避本意是给下游故障（LLM 限流、provider 5xx）恢复窗口。AC-5 只写了「递增 attempt / 置 retryable_failed」，没写退避判定，因此这个矛盾在验收层不会被发现。建议：AC-5 增补退避判定条件（可用 `tasks.attempt` + `tasks.updated_at` 推导：`updated_at + backoff(attempt) <= now()` 才可被 claim，`updated_at` 在 ai 可更新列内，实现上可行），并请 xiaobao 把该条件补进契约的 claim 规则 SQL，避免两侧各写一套。

5. **高｜确认 DevOps 的批量上限约束成立，并补充其边界条件。** DevOps 问题 O-3 给出的 `N × 79s < 1800s → N ≤ 22`、建议 N ≤ 8，架构上我确认成立，推导前提正确（`locked_at` 在 claim 时一次性写入且此后不更新，批内串行则最后一条的持锁时长≈N×单条耗时）。补两点：① 该不变式是**正确性约束而非调优建议**——违反它会直接产生「xiaobao 误回收 + ai 仍在处理」的双写竞态（ai 处理完写 `completed`，xiaobao 已把它回收为 `retryable_failed`，最终状态取决于写入顺序），因此应写进 AC-3 作为可验证约束，而不是只留在 O-3 开放问题里；② 若设计阶段改为批内并发，上限按「批内最长完成时间」重算的同时，并发度还受 LLM provider 速率限制约束（`ADR-0002` 的 fallback 链在被限流时会串行重试多个 provider，单条耗时的尾部会显著拉长），故并发化顺延 v0.3 的前提下，v0.2 取 N ≤ 8 是稳妥的。
6. **高｜claim 的原子性在现有列级 GRANT 下能否实现，未经验证就被写成了验收标准。** AC-3 要求「同一条目已被其他 worker 领取时不得重复领取」，标准实现是 `SELECT ... FOR UPDATE SKIP LOCKED` 或带条件的原子 `UPDATE ... RETURNING`。但契约 §权限矩阵下有两处约束需要先验证：① ai_worker 对 `tasks` **只有 SELECT 与部分列 UPDATE，没有 INSERT**——claim 只能 UPDATE xiaobao 预建的 task 行，可行，但要求「xiaobao 入库时必然为每条 `process_type='ai'` 的 `raw_items` 建好 `l1_ai_process` task」，契约未明确承诺这一点（若 task 缺失，条目在 `raw_items` 里是 `queued` 但无 task 可 claim，会成为永久漏处理的黑洞）；② PostgreSQL 对 `SELECT ... FOR UPDATE` 的权限判定按**表级** UPDATE 权限进行，而契约给的是**列级** UPDATE——列级授权是否满足行锁的权限检查，须在真实库上验证，不能假定。建议：把这两项作为 R-1 就绪确认的子项明确列出（「以 `ai_worker` 身份实际执行一次 claim SQL 并断言可执行 + 并发不重复」），并请 xiaobao 补充「AI 类条目入库时必建 task」的承诺；AC-3 的并发要求保留（是正确性底线），但其可实现性不能悬空。

7. **中｜`processed_news.language` 与 `id` 在 AC-4 被要求写入，但两者都没有 AI 输出来源。** 契约 §processed_news 中 `language` 的「对应 AI 输出」列是 `—`，`id` 也是 `—`；而 `L1Output`（`schemas.py:49`）确实没有 language 字段。AC-4 把 `language` 列进「契约指定字段」要求写入，取值从哪来、缺省写什么都没定义（是原文语种检测结果？固定 `zh`？沿用 `translation` 的 key？）。`id` 则取决于问题 3 的 INSERT/UPDATE 结论。建议：AC-4 逐字段标注来源，无来源的字段要么从写入清单移出（由 xiaobao 侧填），要么明确取值规则；若决定由 ai 产出语种标识，属 `L1Output` 扩展，需先改 `news-l1` HTTP 契约（变更纪律第 1 条），不能只在 DB 模式偷偷多产一个字段。

8. **中｜`raw_items.l1_attempt` 与 `tasks.attempt` 双计数器，重试上限的判定真源未定。** AC-4 要求递增 `l1_attempt`，AC-5 要求递增 `attempt`，两者都在 ai 可写范围内，但「尝试次数未达上限（3）」按哪个判定没写。两个计数器在 xiaobao 侧卡死回收（回收也会推进状态）介入后必然出现漂移。建议：明确以 `tasks.attempt` 为重试判定真源（它与 §task type 的最大尝试次数 3 和退避表同源），`raw_items.l1_attempt` 视为对外展示的镜像值，并在 AC 中写明「两者在同一事务内一起推进」。

9. **中｜「不回收他人锁」的口径需要区分「他人」与「自己上次进程」。** AC-5 写 ai 侧不自行回收他人锁（正确，与契约 §卡死回收一致）。但 worker 重启后，库里会留下一批 `locked_by` = 本 worker 标识的 `processing` 条目——这类锁按契约字面属于「ai 自己写的锁」，却又不是当前进程持有的。若一律等 xiaobao 的 1800s 回收，则每次重启都会让队首若干条延迟至少 30 分钟（与 DevOps 问题 2 的优雅停机是同一问题的两面：优雅停机能覆盖计划内重启，覆盖不了崩溃）。建议：PRD 明确口径——ai 仅可在启动时回收「`locked_by` 等于本 worker 标识」的残留锁（属自愈，不越权），其余一律交 xiaobao；`locked_by` 的标识规则（是否含实例名 / 进程启动时间）需在设计阶段定，并请 xiaobao 确认该自愈行为不与其回收逻辑冲突。

10. **低｜claim 的 join 路径可能缺索引支撑。** AC-3 要求按 `published_at` 升序取，而 `published_at` 在 `raw_items`、claim 目标在 `tasks`，两表关联只能走 `tasks.metadata->>'raw_item_id'`（`metadata` 对 ai 只读、jsonb）。jsonb 表达式 join 若无对应索引，队列增长后 claim 会成为周期性全表扫。不阻塞 PRD，但建议在 R-2（schema 迁移确认）中附带确认是否存在支撑该访问路径的索引，必要时由 xiaobao 侧补。

**O-1（`score_total` 归属）— Architect 结论**：支持 **方案 A**（`score_total` 归 xiaobao 写入，ai 只产 `score_dimensions`）。理由三条，按权重排序：

1. **加权是消费侧策略，不是处理侧事实**。四维原始评分是对新闻内容的判断（ai 的职责），加权公式是「这个产品当前认为什么更重要」的排序策略——它会随 xiaobao 的产品目标频繁调整，而 L1 处理逻辑不该因为排序偏好变化而改动、重测、重新部署。
2. **与 `decisions/0002` 的多调用方定位直接冲突**。ai 是生态内部通用 AI 中枢，第二个调用方的加权口味必然不同；把加权放进 ai 会迫使 ai 为每个调用方持有一份权重配置，等于把调用方的业务策略吸进服务方。
3. **会形成双向耦合与真源分裂**。ai 若要算加权，就得知道权重定义在哪、谁能改、改了如何生效——目前契约与沟通文档均未提供（REQ-003 沟通文档已自行指出这是方案 B 的额外前提）。而权重真源一旦跨仓同步，`news-l1` HTTP 契约明写「不由 ai 计算」也必须一并推翻。

补充一条方案 A 落地时必须同时定的事项（与问题 3 相关）：**xiaobao 侧补算 `score_total` 的时机**。ai 写回 `completed` 后由谁触发补算（触发器 / 轮询 / 应用层），以及补算完成前 `news_positions` 的排序位是否已对外可见。若不定这一条，方案 A 会把冲突从「谁算」推迟成「什么时候算」。若 Owner 最终选方案 B，则按 PRD 已写的路径回 PRD 阶段增补，且需 xiaobao 先交付权重真源、可配置性与变更通知机制——在此之前不建议进设计阶段。

**O-2（适配层抽象边界）— Architect 倾向（设计阶段落定）**：切在 **`tasks.run_task` 之上**，`L1Input` / `L1Output` 直接作为跨层契约，处理核心零改动。依据是 v0.1 的入口已经是解耦的——`main.py:32` 仅做 `run_task("news-l1", run_id, inp, client=..., tools=...)`，HTTP 关注点（请求解析、响应包装、耗时统计）全在 `main.py` 内，`tasks.py` / `graphs/news_l1.py` 不含任何传输层概念。因此适配层的职责收敛为：`raw_items`+`sources` 行 → `L1Input` 的入向映射、`L1Output` → `processed_news` 列的出向映射，两个映射器 + 一个 worker 循环，处理核心不动。AC-2 提出的验证方式（同一条用例在两种数据源各跑通一次）正确且成本低，认可保留。映射失败的归类建议：入向映射失败（必填字段缺失/类型不符）归 `client_error` 类、不重试直接 `final_failed`（重试不会让脏数据变干净），出向映射失败归 `server_error` 类、可重试——此项请在 AC-5 的 `error_kind` 分类里补上，DevOps 的 AC-6 `error_kind` 枚举当前也未含映射错误。

**O-4（双模式开关粒度）— Architect 结论**：采纳 **进程级**（一个进程只跑一种模式），与 PM 倾向一致；**但 DB 模式进程仍监听 `/health`**，即选 DevOps 问题 1 的方案①。两者不矛盾：`/health` 只做存活探针、不注册 `POST /v1/runs/news-l1` 路由，因此「一个进程只处理一种数据来源」的灰度与回滚推理不受影响，同时保住了 v0.1 已有的全部运维手段（`curl /health` + `lsof`）与未来托管层的存活探针。相比方案②（心跳日志 + `last_poll_at`），复用现成 `/health` 的实现成本几乎为零，且不需要 DevOps 靠解析日志时间戳判活。建议在 `/health` 响应中附 `mode` 与 `last_poll_at`，让探活同时能区分「活着且在轮询」与「活着但轮询卡住」。

**O-6（事务边界）— Architect 倾向（设计阶段落定）**：`processed_news` 写入 + `raw_items.l1_*` 推进 + `tasks` 状态与锁释放三者放**同一事务**，与 AC-4 的「不留结果已写但状态未推进」一致；`news_positions` 由触发器在同一事务内完成（`SECURITY DEFINER`，ai 无需权限）。需在设计阶段一并处理的是：该事务与 LLM 调用必须**分离**——LLM 调用（74~79s）绝不能持有数据库事务，否则连接被长时间占用且极易撞上服务端 idle-in-transaction 超时。即 claim 一个短事务、处理无事务、写回一个短事务，共三段。连接池规模按「worker 实例数 × 批内并发度 + 1」即可，v0.2 单实例串行下 2~3 个连接足够。

2. **高｜AC-5.7 的优雅停机宽限期只约束了上限、没约束下限，也没覆盖 ASGI 与托管层——按字面配置一个"合规"的值，优雅停机会完全失效。**

   AC-5.7 写「宽限期上限须小于 1800s」。但真正决定成败的是**下限**：单条 74~79s、单批 N ≤ 8 且批内串行（§4 明写 v0.2 批内串行），则「处理完当前条目后退出」的最坏等待 ≈ 632s。若把宽限期配成 60s 或 90s——**完全符合 AC-5.7 的字面要求**——则每次停机都在处理中途被强杀，AC-5.7 的验收（"断言锁被释放"）在真实批量下必然失败，残留锁照样产生。

   更麻烦的是宽限期在真实部署里由**三层**共同决定，PRD 只约束了最里面一层：
   - 应用层：worker 自己的宽限期（AC-5.7 已写）
   - **ASGI 层**：DB 模式进程是 uvicorn 托着 `/health` + worker 循环（AC-9.3 要求同进程），uvicorn 的 graceful shutdown 超时会先于 worker 结束进程

   建议：AC-5.7 补下限与跨层一致性——「宽限期须 ≥ 单批最长处理时间（N × 单条耗时上限），且 < 1800s；应用层、ASGI 层、托管层三处须配一致值」；§4 托管化顺延条目点名 `TimeoutStopSec` 为 v0.3 的具体前置。验证方式也应据此加严：**在 N > 1 的批处理进行中**发 SIGTERM（而非单条），断言整批锁均被释放。

3. **高｜回滚被 US-4 / AC-1 描述成 ai 单方"改配置重启"，实际是 ai 与 xiaobao 的双侧协同动作，且有顺序要求——故障时按 PRD 字面执行会把问题放大。**

   AC-8.2 自己给出了证据：xiaobao 侧存在「database 模式」与「HTTP/内建 L1 路径」两条路（其 `calcScoreTotal` 只挂后者，`l1-processor.ts:171`）。也就是说 DB 模式下 **xiaobao 不再发 HTTP 请求**，它改为入库 + 建 task。那么 ai 单方"切回 HTTP 模式"的实际后果是：ai 不再 claim，而 xiaobao 仍在往 `tasks` 里堆 `queued`——**队列无人处理、静默积压**，比不回滚更糟（DB 模式至少还在处理）。

   正确的回滚是双侧、有序的：**先** xiaobao 切回 HTTP 集成模式（停止建 task、恢复主动调用），**后** ai 切 `RUN_MODE=http` 重启；反序会产生一个"两侧都不处理"的窗口。此外回滚瞬间已 claim 的在途条目仍需走优雅停机（问题 2）或等 1800s 回收。

4. **中｜`last_poll_at` 没有陈旧阈值定义，运维拿到这个字段仍判不出死活。**

   AC-9.3 让 `/health` 暴露 `last_poll_at`，方向对（是我 R1 提的）。但没定义"多旧算死"。而 DB 模式下这个判断并不平凡：worker claim 一批 8 条后进入处理，若轮询与处理是同一循环，`last_poll_at` 在整批处理期间（最坏 632s）都不更新——**正常工作的 worker 看起来和卡死的 worker 一样**。运维若按"超过 60s 未轮询即判死"处理，会重启一个健康进程并制造残留锁（正是 Developer R1 问题 2 担心的那类反噬）。

**第二部分：本轮新问题**

1. **高｜AC-2.1 的四操作协议对 HTTP 模式是退化的——「推」与「拉」是两种控制流方向，套同一个协议会让 AC-2.2 被一个空实现糊弄过去。**

   AC-2.1 要求协议含「取批 / 写回成功 / 标记失败 / 释放锁」四类操作，并说「DB 数据源与 HTTP 数据源**均为该协议的实现**」。但两种模式的控制流方向是相反的：

   - DB 模式是**拉**：worker 主动 `fetch_batch()` → 处理 → 写回。四个操作全都有意义。
   - HTTP 模式是**推**：FastAPI 端点收到请求才处理，数据由调用方推入，处理完直接进响应体。**没有「取批」这个动作**（没人去取），**没有「释放锁」**（没有锁），「写回成功 / 标记失败」也只是构造 `RunResponse` 而非落地。

   照 AC-2.1 字面实现，HTTP 数据源的四个方法里会有两到三个是 `pass` 或 `raise NotImplementedError`。而 AC-2.2 的判据是「切换数据源实现时处理核心 diff 为空」——**一组空实现完全能让这条判据通过**，验收因此验不出协议是否真的对。这与 §0 准则裁定 2 的意图正相反：裁定 2 要的是「第二个调用方只需实现协议」，而一个对半数实现者退化为空方法的协议，恰恰说明抽象切错了位置。

   架构上的正解是**按职责拆而不是按模式拆**：把「数据的入向/出向映射」与「控制流（谁触发处理、结果落到哪）」分开——

   - **映射协议**（两种模式都必须真实实现，无空方法）：`to_l1_input(源数据) -> L1Input`、`from_l1_output(L1Output) -> 落地表示`。这才是「第二个调用方要实现的东西」。
   - **拉取型数据源协议**（只有 pull 类实现）：`fetch_batch / commit_success / mark_failed / release_lock`。HTTP 模式**不实现它，也不需要假装实现**。

   这样 AC-2.2 的判据可以改成有牙齿的版本：**「同一份处理核心，分别接上 HTTP 端点与 DB worker 两条控制流，核心代码完全相同」**——用两条真实跑通的路径证明，而不是用一次「切换」证明。协议的最终形状归设计阶段（O-2），但**PRD 不应把「HTTP 数据源也是该协议的实现」写成验收前提**，否则设计阶段要么被这句话绑住、要么得回来改 PRD。

   建议：AC-2.1 改为「应存在数据源协议，其中**映射部分**两种模式均须真实实现（不得有空方法或 `NotImplementedError`）；**拉取部分**仅 pull 型数据源实现」；AC-2.2 判据改为上述「同一核心、两条控制流」表述。O-2 相应补一句：协议按职责（映射 / 拉取）分层，不按模式对称。

2. **高｜AC-3 在 R1→R3 的演进中把「排序」整条弄丢了，claim 目前没有任何取件顺序，且忽略了 `tasks.priority`。**

   R1 的 AC-3 写「按 `published_at` 升序、按配置批量上限领取」。R3 把 claim 改为「以 `tasks` 表为准，不扫 `raw_items`」（正确的改动），但 `published_at` 在 `raw_items` 上，随之失去载体——**而 AC-3.1 没有补任何替代排序，现在整条 AC-3 没有一个字提到取件顺序**。

   后果有两层：

   - **FIFO 保证消失**。无 `ORDER BY` 时 PG 返回顺序由执行计划决定，队列积压时新条目插队、老条目饿死是完全可能的。REQ-003 的动机之一就是解决积压，取件顺序不该是未定义行为。
   - **`tasks.priority` 被无视**。实读 `schema.ts:262` `priority: integer().notNull().default(0)`，且其队列索引 `ix_tasks_queue` 建在 **`(status, run_after, priority)`** 上（`schema.ts:274`）——这个索引形状明确表达了预期访问模式：按 `status` 与 `run_after` 过滤、按 `priority` 排序。xiaobao 显然为优先级留了机制，ai 若不按它排序，对方设了优先级也不生效，而且这种「设了没用」的问题在联调时极难被发现（不报错、只是顺序不对）。

   建议：AC-3.1 补排序要求 `ORDER BY priority DESC, run_after ASC`（走 `ix_tasks_queue`），并请 PM 向 xiaobao 确认 `priority` 的方向语义（数值大 = 优先，还是相反——契约与 schema 均未写明，我不做假设）。这是一条**回归**而非新需求：R1 已有的要求在重构中掉了，值得在 R4 里补回来。

3. **高｜退避数组只有 3 个值，而 `tasks.max_attempts` 的 schema 默认是 5——第 4、5 次重试的退避间隔无定义。**

   AC-5.1 要求「读 `tasks.max_attempts` 列，禁止硬编码 3」（C-8 定案，正确）。AC-5.2 要求退避取 `[60s, 300s, 900s]`（契约 §task type）。两条各自成立，**合起来有洞**：实读 `schema.ts:265` `maxAttempts: integer("max_attempts").notNull().default(5)`——建 task 时若不显式写入，该列即为 **5**，而退避数组只有 **3** 个元素。第 4、5 次重试时 `backoff(attempt)` 越界，实现要么崩、要么静默退化（取末值 / 取 0 → 退化为立刻重领，正是 C-4 刚修好的那个问题）。

   注意契约 §task type 写的是「最大尝试次数 3」，与 schema 默认值 5 **不一致**——C-8 只解决了「重试上限读哪里」，没有解决「契约写 3、schema 默认 5」这个残留矛盾。C-8 的答复说该列「按 xiaobao 的 `AI_MAX_RETRIES` 写入」，但那是 xiaobao 应用层行为，ai 无法验证它是否真的每次都显式写；只要有一条 task 走了 schema 默认值，ai 就会遇到 attempt=4。

   建议：AC-5.2 明确越界行为——**`attempt` 超出退避数组长度时取数组末值（900s）**，并把这条作为 PM 转达项请 xiaobao 确认（要么其契约的退避表补齐到 `max_attempts` 长度，要么书面确认「超出取末值」）。这条成本极低但漏了会在重试第 4 次时炸，且只在故障场景触发——正是最不容易在自测中覆盖的路径。

4. **高｜AC-9.3 的 `/health` 200 在 async 结构下可能是假信号：worker 循环若以 asyncio task 形式跑在同一 event loop 上，其未捕获异常会被静默吞掉，进程与 HTTP 都还活着，只有 worker 死了。**

   AC-9.3 要求「DB 模式进程仍监听 `/health`」+「处理进行中 `/health` 须 2s 内返回」。在 async 地基下，worker 循环的自然实现是 FastAPI `lifespan` 中 `asyncio.create_task(worker_loop())`。这个结构有一个具体且常见的失效模式：**`asyncio.Task` 内未捕获的异常不会终止进程，也不会打断 event loop**——它被存在 task 对象里，只有当 task 被垃圾回收且异常从未被取出时，才在 stderr 打一行 `Task exception was never retrieved`。

   结果是：worker 循环因一个未预料的异常（驱动连接池耗尽、映射层 `KeyError`、`asyncio.CancelledError` 误吞）退出，而 `/health` 依然 200、依然 2s 内返回、`mode` 依然是 `db`。**AC-9.3 的探活会完整地报告「健康」**。这比 DevOps 问题 4 描述的「假死难区分」更进一层：那是「活着但可能卡住」，这是「探针说活着但那部分已经死了」。

   DevOps 问题 4 建议补 `in_flight` 与 `current_item_started_at`，方向对，但仍是**间接推断**（靠字段陈旧度判断）。架构上应该给一个**直接**的信号：worker task 的生死是进程内已知事实，不该让运维靠时间戳去猜。

   建议：AC-9.3 补两条——① worker 循环必须包在顶层异常捕获内，任何逃逸异常须记 `error_kind` 日志并显式标记 worker 状态为 `dead`（而非静默退出）；② `/health` 响应体须含 `worker_alive`（或等价的 `worker_state`）字段，worker task 已结束时该字段必须为假，**且 `/health` 应返回非 200**——否则托管层探针（v0.3）永远不会重启一个 worker 已死的进程。这条与 DevOps 问题 4 是互补关系：他的字段回答「有没有卡住」，这条回答「还在不在」。

5. **中｜AC-2.4 引用的函数指错了——真正决定 `link_read` 是否触发的不是 `news_l1.py:407`，而且两个 URL 提取实现的判定条件不一致。这个错是我 R1 引入的，我认领。**

   AC-2.4 写「`_extract_url`（`news_l1.py:407`）只认 `raw_content["url"]` / `["canonical_url"]`；若把 `raw_items.content` 原样塞入，`_should_link_read` 恒为 False」。实读后这句话有两处不准：

   - **`_should_link_read`（`news_l1.py:269`）调用的是 `state["tools"].extract_url(...)`**，即 `tools/base.py:51` → `tools/link_reader.py:23` 的 `extract_url`；模块内的 `_extract_url`（`news_l1.py:407`）只被 `ingest_context_node`（`:121`）用来填 context 条目的 `url` 字段，**与 link_read 的触发判定无关**。
   - **两个实现的判定条件不同**：`link_reader.extract_url`（`:25`）额外要求 `url.startswith(("http://", "https://"))`；`news_l1._extract_url`（`:408`）只要是非空字符串就返回。

   后果不只是引用不准。既然 URL 现在直读 `raw_items.source_item_url`（AC-2.4 R3 订正），就存在一种真实情形：**该列的值不带协议前缀**（例如存 `x.com/user/status/123`）。此时 `_should_link_read` 为 False（不触发 link_read），而 `ingest_context_node` 的 `_extract_url` 会把这个值填进 context 的 url 字段——**同一个 URL，两处给出不同判断**，且 link_read 依旧是「不报错、不降级、静默失效」。AC-2.4 给的验证方式「构造一条 `source_item_url` 非空的输入，断言 link_read 被触发」会因为这一点而不稳定：非空但无协议前缀时断言必然失败，而失败原因看起来像映射写错了。

   建议：AC-2.4 订正函数引用为 `tools/link_reader.py:23 extract_url`（并注明 `news_l1.py:407` 是另一处、判定更宽），并补一句入向映射要求——**URL 须规范化为带 `http(s)://` 前缀后再填入 `raw_content`，无法规范化的按「无 URL」处理**；验证方式相应补一例「`source_item_url` 有值但无协议前缀」的用例。请 PM 同时把这条同步给 xiaobao（`source_item_url` 的存储格式是否保证带协议前缀，属 R-5 结构说明未覆盖的细节）。

6. **中｜`tasks.raw_item_id` 是 nullable，claim 后的入向映射缺一条空值前置。**

   C-9 已澄清 `tasks.metadata` 不存在、`raw_item_id` 是一级列（正确）。但实读 `schema.ts:258-260`：`rawItemId: uuid("raw_item_id").references(rawItems.id, {onDelete:"cascade"})`——**没有 `.notNull()`**。`tasks` 是通用任务表（`type` 字段区分用途），存在不关联 `raw_items` 的任务类型是合理的，因此该列可空是其设计而非疏漏。

   对 ai 的影响：AC-3.1 的 WHERE 已按 `type='l1_ai_process'` 过滤，正常情况下这类 task 必有 `raw_item_id`；但契约并未**承诺**这一点，而 claim 之后 ai 会立即拿它去读 `raw_items`。一旦为空，适配层在 claim 事务已提交之后才失败——此时条目已被置 `running`/`processing`、锁已持有，失败路径要走 AC-2.5 的「入向映射失败 → 不重试直接最终失败」，但那条针对的是数据内容问题，不是「压根没有关联条目」。

   建议：claim SQL 的 WHERE 增加 `AND raw_item_id IS NOT NULL`（成本为零，且能让这类异常 task 留在队列里由 xiaobao 侧发现，而不是被 ai 领走后标记失败——ai 把不属于自己的任务标成 `failed` 是越界的）。

**第三部分：指派任务的其余三项 — 架构结论**

**async 地基的架构影响（AC-9 / O-8）**：我确认 Developer 的判断——风险在回归不在重写，且「黄金样本外部化」是这个 P0 风险唯一的客观兜底，支持把它从 O-8 提升进 AC-9.4。补两点架构侧的输入：

- **Developer 问题 7「有 IO 才 async」我确认成立**，但理由要补一条边界：LangGraph 的 `ainvoke` 允许同步节点混用，同步节点在协程中被直接执行（不额外开线程），因此**同步节点的耗时会占用 event loop**。`ingest_context` 与 `normalize_output` 是纯内存字符串处理，量级在毫秒，占用 loop 无实际影响——所以结论对，但判据应写成「**无 IO 且耗时为毫秒级**的节点保持同步」，而不是单看有无 IO。若将来某个纯计算节点变重（例如引入本地模型推理或大文本分词），它就必须移出 loop。这条建议进设计阶段的 O-8 而非 AC。
- **O-9 驱动选型**：我采纳 Developer 的 psycopg3(async) 建议，理由补一条更贴架构的——问题 1 若按「映射 / 拉取分层」落地，拉取型协议的实现会包含一段可能需要随 C-6 结论改写的 claim SQL（见下），psycopg3 的 `%s` 占位符与标准 DBAPI 语义让这段 SQL 在两种写法间迁移的成本最低；asyncpg 的 `$1` 占位符会把这段 SQL 与驱动绑得更紧。性能差异在本场景（瓶颈是 74~79s 的 LLM 调用）无意义，这一点两方判断一致。

**事务边界（O-6）**：AC-4.3 的三段式（claim 短事务 / 处理无事务 / 写回短事务）我确认为正确结构，无修改意见。补一条设计阶段要落的约束：**async 驱动下连接必须随事务获取与释放，不得跨 `await` 长持**——三段式的价值正是让连接只在毫秒级事务内被占用，若实现时图省事在 worker 循环外层开一个连接贯穿整批（8 条 × 79s ≈ 632s），会同时踩上服务端 `idle_in_transaction_session_timeout` 与连接池饥饿两个坑，等于把三段式设计作废。连接池规模按「worker 实例数 × 批内并发度 + 1」，v0.2 单实例串行下 2~3 即可（与我 R1 结论一致，async 化不改变这个量级）。

**C-6 行锁实证 — 架构侧兜底方案（降低其风险等级）**：DevOps 已给出完整的 6 步实证安排（全程事务内 `ROLLBACK`，不消耗 5 条预置队列），执行层面我无补充。但两方都把 C-6 的失败后果描述为「等 xiaobao 改授表级 UPDATE，否则 claim 要返工」——**这个后果被高估了**。即使实证失败且 xiaobao 不改 GRANT，仍有一条不依赖 `FOR UPDATE` 的原子 claim 路径：

```sql
UPDATE tasks SET status='running', attempt=attempt+1, locked_by=$1, locked_at=now()
WHERE id IN (
  SELECT id FROM tasks
  WHERE type='l1_ai_process' AND status='queued' AND run_after <= now() AND raw_item_id IS NOT NULL
  ORDER BY priority DESC, run_after ASC LIMIT $2
) AND status='queued'
RETURNING id, raw_item_id;
```

普通 `UPDATE` 自身取写锁，并发时第二个事务会**阻塞等待**而非 `SKIP LOCKED` 跳过；第一个事务提交后，PG 会对被阻塞的行重新求值 `WHERE`，`AND status='queued'` 此时不再成立，该行被排除——**不会重复领取**。代价是并发 claim 从「跳过」变成「短暂阻塞」，而 claim 事务是毫秒级、v0.2 又是单实例，代价可忽略。权限上它只需要列级 UPDATE（更新的都是已授权列）+ 子查询列的 SELECT，**不触发 `FOR UPDATE` 的表级权限检查**。

因此建议 AC-3.6 补一句 fallback：「若实证表明列级 GRANT 不支撑 `FOR UPDATE`，claim 改用不依赖行锁的条件式原子 `UPDATE ... RETURNING`（并发退化为阻塞而非跳过，v0.2 单实例下可接受），**不必阻塞实现阶段等待 xiaobao 改授权**」。这样 C-6 从「可能导致 worker 地基返工」降级为「两种写法二选一」，Developer 问题 3 所担心的返工风险随之大幅下降——虽然环境前移仍然该做（DevOps 问题 1 成立，理由不止 C-6 一条）。

**第二部分：本轮问题**

1. **高｜AC-9.4 的黄金样本没有定义覆盖哪些路径——只录 happy path 的话，这个「P0 风险唯一的客观兜底」只兜住了一半，而 async 改造最容易坏的恰恰是它没覆盖的那一半。**

   AC-9.4 现写「固定若干组 `L1Input` + 固定的 mock LLM 响应，跑出 `L1Output` 的 JSON 快照落盘」。方向完全正确（回归判据独立于测试代码改写，解了 Developer 指出的循环论证）。问题在于**「若干组」没有约束覆盖面**，而 §8 与 §6 都把它认定为 O-8 这个 P0 风险的唯一客观兜底——**兜底的覆盖面不该是自由裁量的**。

   同步转 async 的回归，绝大多数不出在正常路径上（正常路径改错了，40 例单测里立刻就红），而是集中在异常与边界路径：

   - **超时**：`httpx` 同步 client 的超时抛 `httpx.TimeoutException`，async client 同样抛它，但 `ADR-0002` 的 ChainedAIClient 还有一层**总 timeout budget**——同步实现下靠逐次调用累减，async 下若改用 `asyncio.wait_for` 包裹，抛的是 `asyncio.TimeoutError`，**不是同一个异常类型**。现有 `except` 分支若按类型分派（`llm/client.py` 的 error kind 判定就是按类型），会漏接 → 降级语义变化 → `tags.processing` 的降级标记与 `error_kind` 一起失真。
   - **provider fallback 链**：多 provider 依次重试的顺序与终止条件，在 async 下若不慎用了 `gather` 或改了异常传播，行为会变而单测未必覆盖到具体链路。
   - **工具全失败降级**：三工具失败后走 `degradations` 的部分可用路径（v0.1 的 AC-6 语义：部分可用 = `succeeded`）。
   - **LLM 返回非法 JSON**：`llm/json.py` 的解析容错分支。

   这四类正是 v0.1 花了整个迭代才调稳的语义，也是 DB 模式下**唯一的观测面**所依赖的（AC-6.6 要求降级与 provider 事实进日志）。若黄金样本只有正常路径，改造后这些分支静默变化，40 例单测因为 fake 被同步改写而照绿，**兜底失效且无人知道**。

   建议：AC-9.4 的验证方式补一句覆盖要求——**黄金样本须至少覆盖四类路径：① 全工具命中的正常路径 ② 工具全失败的降级路径 ③ LLM 返回非法 JSON 的解析容错路径 ④ LLM 超时触发 provider fallback 的路径**；每类的快照均须逐字段比对（含 `tags.processing` 的降级标记）。成本极低（都是构造 mock 响应，不需要真实外部依赖，也不依赖 §5 的服务器环境，改造动手前就能录），但它决定这个 P0 兜底是真兜底还是半个。

   > 附一条实现提醒（归 O-8，不必进 AC）：async 化后 `except Exception` 不会捕获 `asyncio.CancelledError`（它继承 `BaseException`），这是**正确且必须保持**的行为——一旦有人在改造中把节点的 `except Exception` 顺手改成 `except BaseException` 或裸 `except:`，`CancelledError` 会被吞掉，**AC-5.7 的优雅停机会静默失效**（SIGTERM 后协程不响应取消，一直跑到宽限期强杀），而这个失效在验收里表现为「优雅停机断言失败」，原因极难定位到某个 except 子句。

2. **中｜AC-3.7 的 fallback 并发行为描述不准，是我 R3 引入的、PM 照抄——它不是「退化为阻塞」，而是「后到的 worker 拿到空批」，因此这个 fallback 是 v0.2 单实例专用，v0.3 上多实例前必须解决 C-6。**

   我 R3 写的是「并发 claim 从『跳过』变为『短暂阻塞』」，AC-3.7 逐字采纳。正确性结论没错（不会重复领取），但并发行为的推演我说得太轻。准确的行为是：

   fallback 的子查询**不带 `FOR UPDATE SKIP LOCKED`**，因此两个 worker 的子查询会选出**完全相同的 N 行**。外层 `UPDATE` 一个阻塞另一个；先提交者拿走全部 N 行并把它们置为 `running`；后到者解除阻塞后 PG 重新求值 `AND status='queued'`，**这 N 行全部被排除** → `RETURNING` 返回 **0 行**。也就是说后到的 worker 不是「稍等一下拿到另外 N 行」，而是**这一轮完全空手**，要等下一个轮询周期（10~30s）再试。

   对 v0.2 没有任何影响（§4 明确单 worker 实例、批内串行），我 R3 的结论「代价可忽略」在 v0.2 范围内仍然成立。但对 v0.3 有实际影响：**多 worker 实例下，fallback 写法的吞吐不随实例数增长**——极端情况下 K 个实例里只有 1 个能拿到活干，其余每轮空转。而 §4 已把「批内多条并发处理」顺延 v0.3、O-3 也把「多实例」留给 v0.3 与托管化一并验证。

   建议：① AC-3.7 的 fallback 描述订正为上述行为（「后到者本轮拿空批」而非「短暂阻塞后拿到其他行」）；② §4 的「批内多条并发处理——顺延 v0.3」条目补一句前置——**v0.3 上多 worker 实例前，必须先解决 C-6（xiaobao 改授 `tasks` 表级 UPDATE 以支持 `FOR UPDATE SKIP LOCKED`）**，否则 fallback 写法会成为多实例的吞吐瓶颈。这样 C-6 即使在 v0.2 走了 fallback，也不会被当成「已经解决、可以忘掉」。

3. **中｜AC-5.7 的优雅停机与 AC-9.3 的探活在「停机中」这个状态上互相打架，v0.3 托管化落地时会爆。**

   两条 AC 各自都对，合起来有个没定义的状态：

   - AC-9.3 要求 worker task 结束时 `worker_alive` 为假、**`/health` 返回非 200**。
   - AC-5.7 要求收到 SIGTERM 后停止新 claim、处理完当前批（最坏 632s）再退出，且三层宽限期配一致。

   把两条并起来看停机过程：SIGTERM 到达 → worker 停止 claim、继续收尾 → 最后一条处理完、worker task 结束 → **此时进程还在（uvicorn 在关闭中），`worker_alive` = false → `/health` 返回非 200** → 托管层探针判死。若 v0.3 的 systemd 配了基于健康检查的重启策略，它会在进程正常收尾期间判定失败。更直接的是：uvicorn 进入 graceful shutdown 后**停止接受新连接**，探针请求直接连接失败，效果与非 200 相同。

   根因是 `worker_alive` 被设计成二态（活 / 死），而真实生命周期有三态：**`running`（正常）/ `stopping`（收到停机信号、正在收尾）/ `dead`（异常退出）**。托管层对这三态的正确反应完全不同——`running` 保持、`stopping` **等待**（等到宽限期）、`dead` **重启**。二态无法表达「正在正常地退出」。

   建议：AC-9.3 的 `worker_alive` 改为 `worker_state ∈ {running, stopping, dead}`（或保留 `worker_alive` 但增补 `stopping` 标志），并写明：**仅 `dead` 时 `/health` 返回非 200；`stopping` 期间返回 200 并附 `stopping` 状态**，托管层据此等待而非重启。同时在 AC-5.7 的三层一致性里补一句：**优雅停机期间探针失败是预期行为，托管层的健康检查重启策略须与 `TimeoutStopSec` 协同**（这条与 DevOps R3 问题 2 的三层宽限期是同一处的另一面，他管「等多久」，这条管「等的时候别把它当死的」）。

   v0.2 无托管（§4 已把无人值守排除），所以这条不影响本迭代验收，但 AC-9.3 现在就要定成三态——上线托管时再改，`/health` 的契约形状已经被 DevOps 的探针配置依赖了，改起来比现在贵。

4. **中｜AC-2.1 的「不得有空方法」需要一句澄清：HTTP 侧的 `to_l1_input` 是恒等映射，它是真实实现，不是空方法。**

1. **中｜AC-3.7 的 fallback 写法依赖 READ COMMITTED 隔离级别，PRD 未写明；且其并发语义与 `SKIP LOCKED` 不等价，应作为已知限制登记。** fallback 的推理链——「普通 UPDATE 取写锁 → 第二个事务阻塞等待 → 第一个提交后 PG 重新求值 WHERE → `AND status='queued'` 不再成立故排除」——在 PostgreSQL 中**只在 READ COMMITTED 下成立**（EvalPlanQual 重新检查）。在 REPEATABLE READ / SERIALIZABLE 下，第二个事务不会重新求值，而是直接抛 `could not serialize access due to concurrent update`，claim 会**报错而非安全跳过**。PG 默认是 READ COMMITTED，所以默认路径没问题，但这是一条隐式依赖：一旦驱动或连接池显式设置隔离级别（某些池化配置会），fallback 的正确性就没了，且表现为偶发报错、极难归因。
   另一处不等价：批量 claim 时子查询 `SELECT ... ORDER BY ... LIMIT N` 是快照读，**两个并发 worker 的子查询会选出相同的 id 集合**；外层 UPDATE 一个先提交，另一个重新求值后得到 **0 行**（整批被抢），而不是像 `SKIP LOCKED` 那样拿到"另外 N 条"。v0.2 单实例无影响，但 v0.3 上多实例时并发吞吐会显著低于预期。
   建议：在 AC-3.7 的 fallback 描述里补一句隔离级别依赖（「须在 READ COMMITTED 下执行，驱动/连接池不得改隔离级别」），并把「多实例下吞吐不等价」登记为已知限制、随 v0.3 多实例一并重估。**归设计阶段 O-6（事务与连接管理）+ O-9（驱动选型）一并落定即可，不必回 PRD 阶段。**

2. **中｜AC-2.2 的判据前半句「同一份处理核心……核心代码完全相同」是同义反复，验收时会失去判定力。** 只要不是把核心代码复制成两份，两条控制流跑在同一份代码上，"代码完全相同"必然成立——它描述的是事实而非可证伪的判据。真正有牙齿的是后半句「处理核心中不得出现共享库表名、列名或 `raw_items`/`tasks` 等概念」。

问题：

1. **高｜单条处理没有 wall-clock 总预算，AC-3.5 的 `N ≤ 8` 用默认配置就会违反它自己声明的正确性约束。**

   AC-3.5 的推导是 `N × 单条耗时上限 < 1800s`，取「v0.1 实测 74~79s」→ N ≤ 22 → 保守取 8。**但 79s 是 v0.1 happy path 的实测均值，不是被任何机制保证的上限。** 代码实查，单条 pipeline 的各段超时是**各自独立、串行累加**的，没有任何统一的 wall-clock 预算：

   | 段 | 超时来源 | 实际上限 |
   |---|---|---|
   | `kb_search` | `news_l1.py:205` 传 `inp.options.timeout_ms` | **180s** |
   | `link_read` | `news_l1.py:143` `min(timeout_ms, 8000)` | 8s |
   | `web_search` | `news_l1.py:173` 传 `inp.options.timeout_ms` | **180s** |
   | LLM（含 provider fallback 链） | `llm_process_node` 传 `inp.options.timeout_ms`；`client.py:99` 的 budget 在 `_budget_ms` 为 None 时**退化为 `timeout_ms`**，而 `client.py:216` 的 `ChainedAIClient(providers)` **正是未传 `budget_ms`** | **180s** |

   `RunOptions.timeout_ms` 默认 **180000ms**（`schemas.py:15`）。即**单条最坏 wall-clock ≈ 548s**，不是 79s。代入 AC-3.5：`8 × 548s = 4384s ≫ 1800s`——**用 PRD 自己的默认配置就能算出违反**，而 AC-3.5 明写违反会「直接产生 xiaobao 误回收 + ai 仍在处理的双写竞态」。按最坏值反推，N ≤ 3 才安全。

   两点加剧，都不是假设：
   - **DB 模式的耗时基线本就高于 HTTP 模式**。74~79s 是 HTTP 模式实测的，那时 `kb_results` / `link_content` / `search_summary` 由 xiaobao **预取传入**；AC-8.2 自己写明 DB 模式下 KB 转为 ai 主动检索、`tool_summary.kb_search` 从 0 变常态 ≥1。**用 HTTP 模式的耗时去约束 DB 模式的批量，基准选错了。**
   - **尾部正是最需要保障的时候**。逼近上限的场景（Tavily 不可达、KB 慢、LLM 被限流触发 `ADR-0002` 的 fallback 链串行重试多个 provider）恰恰是故障期——而故障期又是队列积压、批量价值最高的时候。按均值配容量，故障时必然踩线。

   同一个数字还撑着另外两条：AC-5.7 的宽限期下限（632s = 8 × 79s）与 AC-9.3 的 `last_poll_at` 陈旧容忍上限，两者都会随之偏小——宽限期配 632s 而实际需 4384s，等于优雅停机在故障期必定强杀。

   建议（二选一，倾向前者）：
   - **① 定义并强制单条 wall-clock 预算**（推荐）：新增一条 AC——单条处理设总耗时预算（建议 150~200s，与 v0.1 实测留 2 倍余量），超预算即主动放弃该条、按 AC-5.3 置 `retryable_failed` 并释放锁。实现上成本很低：`ChainedAIClient` 已有 budget 机制（`client.py:99`），把同样的 deadline 思路提到 graph 层即可；`tool_budget_used`（`news_l1.py:69`）当前只是**调用次数**预算，正好补上时间维度。这样 AC-3.5 的不等式才有被保证的输入。
   - ② 或把 AC-3.5 的 N 按最坏值重算为 **N ≤ 3**，并显式写明「该取值随单条耗时上限变化，若引入 wall-clock 预算须重算」。

   **附条件**：本条不阻塞设计阶段开工（协议分层、驱动选型、事务边界均不依赖它），但 **AC-3.5 的 `N ≤ 8` 是当前 PRD 里唯一一个"被声明为正确性约束、却建立在未被保证的量上"的条款**，须在设计阶段落定 O-3（worker 运行参数）之前经 Change Note 订正，实现阶段不得直接按 `N ≤ 8` 落地。

2. **中｜`worker_alive` 三态化后的 HTTP 状态码语义必须写死，否则三态化达不到它的目的。**

   Architect R4 附条件之一是把 `worker_alive` 从二态改为三态 `running/stopping/dead`，理由是二态无法表达「正在正常退出」、v0.3 托管层会在优雅停机期间判死重启。方向我完全支持——这正是我 R3 问题 2（宽限期）与问题 4（探活）的交叉点。

   但只改字段值不够：**AC-9.3 当前写的是「worker task 已结束时该字段为假，且 `/health` 须返回非 200」**，托管层探针判的是**状态码**，不是响应体字段。若三态化后 `stopping` 仍落进"非 200"，托管层照样在优雅停机的 632s 窗口内判死重启——Architect 要避免的事原样发生，只是换了个字段名。
