## 1. 迭代目标

承接 coordination `REQ-003`：把 ai 的 news-l1 集成模式从「HTTP 同步调用」**扩展**为「数据库契约边界异步解耦」——xiaobao 入库标记状态，ai 轮询 claim 取数、处理、写回共享库。

三条硬约束：

1. **并行而非替换**：HTTP 模式（`news-l1` v1 契约）继续有效，供灰度与回滚使用；新增 DB 模式（`news-l1-db` v1 契约）。
2. **适配层隔离**：取数与写回封装为独立数据源适配层，AI 处理核心不感知数据来源（数据库 / HTTP 请求）。这是 `decisions/0002`（ai 定位为生态内部通用 AI 中枢、多调用方预留）的硬要求——ai 直连 xiaobao 库读 schema 会把 ai 焊死在 xiaobao 上。
3. **schema 权属不越界**：共享库 schema 归 xiaobao，ai 只读指定表列、只写指定结果字段，不建表不改表。

**范围重排说明**：v0.2 原范围为稳定性六项（logging / 托管化 / KB 空结果语义 / 工具并发 / RunRecord / 多 provider 生产验证），起草于 2026-07-04，比 REQ-003 提报（2026-07-05）早一天，故未包含 REQ-003。Owner 2026-07-25 拍板重排：REQ-003 为 v0.2 主线，稳定性项中与 worker 形态耦合的三项（托管化 / 工具并发 / RunRecord）顺延 v0.3，避免先做外围再改架构导致返工；logging 与 KB 空结果语义因是 worker 模式的前置或低成本项，并入本迭代。

## 2. 用户故事

- **US-1**（调用方解耦）作为 xiaobao，我想入库并标记状态后立即返回、不必挂起等待单条 74~79 秒的 AI 处理，以便抓取与展示流程不被 AI 处理阻塞。
- **US-2**（多调用方定位）作为 ai Owner，我想取数/写回逻辑与 AI 处理核心彻底分层，以便将来新增调用方或换数据来源时不改处理核心，也不让 ai 被 xiaobao 的库 schema 绑死。
- **US-3**（worker 闭环）作为 xiaobao，我想 ai 能定期自动领取待处理的 AI 类新闻、处理完把结果写回共享库，以便无需我主动调用即完成 L1 处理。
- **US-4**（灰度与回滚）作为 Owner，我想用配置开关在 HTTP 模式与 DB 模式之间切换，以便灰度验证期间出问题可立即切回 HTTP 模式。
- **US-5**（失败与卡死可控）作为 xiaobao，我想 ai 处理失败时按契约正确标记状态与尝试次数、卡死时我能按契约回收，以便队列不被永久占用。
- **US-6**（可观测性）作为 ai Owner，我想看到脱敏的结构化日志（run 标识 / 步骤 / 耗时 / 错误 kind），以便在 worker 模式下定位问题——worker 模式没有 HTTP 响应可看，日志是唯一观测面。
- **US-7**（KB 语义修正）作为 xiaobao，当 KB 检索返回空结果时，ai 应标记「无匹配」而非「检索故障」，以便区分两种情况（v0.1 遗留 D-3）。

## 3. 验收标准

> 每条覆盖正常 + 至少一个异常路径，可验证。PM 不自审本节，由 Architect / Developer / DevOps 审。

- **AC-1 双模式开关**：当配置为 HTTP 模式时，`POST /v1/runs/news-l1` 行为与 v0.1 完全一致、不启动轮询；当配置为 DB 模式时，worker 按配置间隔轮询共享库；当配置缺失或非法时，应以 HTTP 模式启动并记录警告，不得静默进入 DB 模式。切换模式只需改配置并重启，不需改代码。
- **AC-2 适配层隔离**：AI 处理核心的入口应只接受「与数据来源无关的处理输入」，不出现共享库表名/列名；当把数据源从数据库换成 HTTP 请求时，处理核心代码无需修改（以两种数据源各跑通同一条处理用例为验证）。适配层负责库字段 ↔ 处理输入/输出的双向映射。
- **AC-3 claim 正确性**：当库中存在 `process_type='ai'` 且 `l1_status IN ('queued','retryable_failed')` 的条目时，worker 应按 `published_at` 升序、按配置批量上限领取；claim 时应写入 `locked_by` 与 `locked_at` 并把 `l1_status` 置 `processing`；当同一条目已被其他 worker 领取时，本 worker 不得重复领取（并发 claim 不产生重复处理）；当无待处理条目时，worker 应空转等待而非报错退出。
- **AC-4 写回正确性**：当处理成功时，应向 `processed_news` 写入契约指定字段（`raw_item_id` / `title` / `summary` / `translation` / `context` / `analysis` / `score_dimensions` / `tags_v2` / `language`），并把 `raw_items.l1_status` 置 `completed`、写 `l1_processed_at`、递增 `l1_attempt`，同步更新 `tasks` 状态并释放锁；写回应为单事务，中途失败不得留下「结果已写但状态未推进」的不一致；ai 不得对 `raw_items` 写契约未授权的列，不得建表改表。
- **AC-5 失败与重试语义**：当处理失败且尝试次数未达上限（3）时，应把 `l1_status` 置 `retryable_failed`、写 `l1_error`（脱敏）与 `tasks.last_error_kind`、递增 `attempt` 并释放锁；当尝试次数耗尽时，应置 `final_failed`；当 worker 进程在处理中被杀死时，条目保持 `processing` 且 `locked_at` 不再更新，使 xiaobao 侧 30 分钟卡死回收机制能够生效（ai 侧不自行回收他人锁）。
- **AC-6 结构化 logging**：当服务/worker 启动时应初始化统一结构化日志格式；当各处理步骤执行时应记录包含 run 标识、`raw_item_id`、`step`、`duration_ms`、`status` 的日志；当发生错误时应记录 `error_kind`（区分 client_error / server_error / timeout / rate_limited / auth_error / db_error）与脱敏 `error_message`。日志不得包含 API key、数据库口令、完整 `raw_content`。
- **AC-7 KB 空结果语义**：当 xiaobao `POST /v1/kb-search` 返回 200 且 `results: []` 时，应标记为「空结果」而非 `kb_search_failed`；当返回非 200 或超时/连接错误时，才标记检索故障。`tags.processing` 不应包含 `stub`。
- **AC-8 输出语义与契约一致**：DB 模式写回的输出字段语义应与 `news-l1` HTTP v1 契约逐字段一致（同一条输入在两种模式下产出的业务字段应等价）；本迭代不改 HTTP 对外契约。

## 4. 范围边界

**本迭代做：**

- 数据源适配层：库字段 ↔ 处理输入/输出双向映射，处理核心与数据来源解耦。
- 轮询 worker：claim → 处理 → 写回 → 释放锁的完整闭环，含批量上限与轮询间隔配置。
- `news-l1-db` v1 契约落地：读 `raw_items` / `sources` 指定列、claim `tasks`、写 `processed_news` 与状态字段。
- 双模式配置开关（HTTP / DB），支持灰度与回滚。
- 失败与重试语义、锁释放；配合（不替代）xiaobao 侧卡死回收。
- 结构化 logging（worker 模式下的唯一观测面，故本迭代必做）。
- KB 空结果语义修正（v0.1 遗留 D-3）。

**本迭代不做（顺延 v0.3 或独立任务）：**

- **服务托管化**（systemd / launchd）——顺延 v0.3：托管对象在本迭代后从「HTTP 服务」变为「常驻 worker」，先定形态再写托管配置，避免返工。
- **工具调用并发化**——顺延 v0.3：并发单元在 worker 模式下从「单请求内三工具并行」扩展为「还可批内多条并行」，两种并发维度应一起设计。
- **RunRecord 持久化**——顺延 v0.3：与本迭代 `processed_news` / `tasks` 写回存在职责重叠，需先看 DB 模式落地后还缺哪些审计信息。
- **多 provider 生产验证**——顺延部署阶段/v0.3（DevOps，v0.1 遗留发布检查项 3）。
- 换非 reasoning 模型（技术选型，需 Architect 评估）。
- 主链路算法逻辑变更（保持 v0.1 已验证的评分/标签/摘要/翻译逻辑）。
- HTTP 对外契约变更。
- 建表改表、角色与 GRANT 管理、`news_positions` 关联（均属 xiaobao 权属）。
- 评分加权 `score_total`——**除非 O-1 结论推翻现有边界**，见下。
- 强可重入 checkpoint（REQ-002 结论：不做）。
- 第二调用方的实际实现（只留适配层接口形状）。

## 6. 风险和开放问题

**界面要点**：本迭代为纯后端服务迭代，无用户可见界面变更（判断依据：ai 不含前端，调用方为 xiaobao；DB 模式连 HTTP 接口都不暴露给终端用户）。故不展开界面要点。

**开放问题：**

- **O-1（P0，阻塞定稿）`score_total` 归属冲突**：`news-l1-db` v1 §职责边界表把「评分加权 `score_total`」标为 **ai 侧 ✅ / xiaobao ❌（由 ai 写入最终值）**，`processed_news` 也把 `score_total` 列为 ai_worker 写入字段（「四维加权后最终值」）。但这与三处既有真源直接冲突：① `news-l1` HTTP v1 契约明写「评分加权 `score_total` 留在 xiaobao，不在本契约内传输，**也不由 ai 计算**」；② ai `project-context.md` §业务边界「本项目不做 `score_total`」；③ `news-l1-db` 自身第 5 条变更纪律「输出字段语义以 HTTP 契约为准」——契约内部自相矛盾。**处理方式**：本 PRD 暂按既有边界（ai 不算 `score_total`）写范围，需 xiaobao 侧确认是订正契约、还是 Owner 决定把加权职责迁到 ai。若迁到 ai，属业务边界变更，需改 `news-l1` HTTP 契约 + ai 业务边界，并追加对应用户故事与验收标准（PRD 需回本阶段增补）。
- **O-2（P1）适配层抽象边界**：适配层切在哪一层（数据源接口 / 仓储 / 消息映射）、`L1Input`·`L1Output` 是否直接作为跨层契约、映射失败如何归类——Architect 设计阶段定。
- **O-3（P1）worker 运行参数**：轮询间隔、单批 claim 上限、单进程内是否并发处理多条、多 worker 实例是否允许——Architect + DevOps 定。当前单条 74~79s，批量与并发度直接决定吞吐。
- **O-4（P2）双模式开关粒度**：进程级（一个进程只跑一种模式）还是可同时启用（HTTP 接口 + worker 并存）——Architect 定；PM 倾向进程级以简化灰度与回滚推理。
- **O-5（P2）契约小瑕疵**：`news-l1-db` v1 的 `l1_status` 枚举表中 `completed` 出现两行（ai_worker 完成 / xiaobao direct 类入库），语义相同但来源不同，建议 xiaobao 侧合并或加注，避免实现方误读为两个状态。
- **O-6（P2）事务边界与连接管理**：写回单事务的具体范围（`processed_news` + `raw_items` + `tasks` 是否同一事务）、连接池规模、与 xiaobao 侧触发器（`SECURITY DEFINER`）的交互——Architect 设计阶段定。
- **O-7（P1）凭据注入**：`ai_worker` 口令的注入方式与轮换、`.env.example` 需新增哪些变量名、日志与错误信息如何确保不带口令——DevOps 在 Review 与部署阶段定。
