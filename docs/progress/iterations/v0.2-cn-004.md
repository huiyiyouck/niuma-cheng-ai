## 问题描述

### A. `l0_label` 实为流程标记，PRD C-1 的闭合结论与 AC-8.2 的表述均被实测推翻

**PRD 现写**（AC-8.2 已知差异第 1 条，CN-003 前即有、CN-003 未动）：

> `domain_tags` 为单值来源，仍不完全等价：契约 v1.4 已 GRANT `raw_items.l0_label`（SELECT），故**不再恒空**；但 `l0_label` 是单值 varchar，而 HTTP 模式 `domain_tags` 是数组。适配层按单值处理（`[l0_label]`），**语义近似但非等价**。

**实测事实**（DevOps 2026-07-28，两库）：`raw_items.l0_label` **只有 `direct_display` 一个非空取值**（`news_test` 154/154；生产 637 条非空全部相同 + 120 条 NULL）。它**不是领域分类结果，而是一个流程标记**。

因此 PRD 的两处表述均不成立：

| PRD 表述 | 实际 |
|---|---|
| 「不再恒空」 | **在 xiaobao 补齐真实领域分类前，`domain_tags` 在 DB 模式下实际恒为 `[]`** |
| 「语义近似但非等价」 | 不是「近似」，是**零信息量**——它与领域分类无任何语义关系 |

**照 PRD 字面实现会比恒空更糟**：`domain_tags = ['direct_display']` 是**真值**，会穿过 `news_l1.py:206` 的 `or None`，把一个零信息量的流程标记同时塞进 **prompt**（`prompts.py:33`）与 **KB 检索的过滤条件**（`news_l1.py:206`）。恒空会被正确忽略，噪声则会实际污染推理与检索。

设计 §3.3 已用「排除集」正确处置（`direct_display` → `[]`，其他值放行以便 xiaobao 将来启用真实分类时 ai 自动跟上）。**但 PRD 的验收标准仍写着一份被推翻的差异清单**——若不订正，实现阶段会按错误的基准验收。

### B. `N = 1` 把处理能力钉死在串行单条，而 PRD 无任何吞吐验收标准

ADR-0004 定 `N = 1` 的三条理由（串行下 N>1 零吞吐收益、风险放大 N 倍、`8 × 240s > 1800s` 违反不变式）**产品侧完全认可，本变更不动该决定**。

问题在于**没有人确认过 v0.2 的处理能力是否够用**。按设计参数算上界：

| 场景 | 单条周期 | 日处理能力 |
|---|---|---|
| 正常（v0.1 实测 79s + 轮询 15s） | ≈ 94s | **≈ 920 条/天** |
| 走满预算（240s + 轮询 15s） | ≈ 255s | **≈ 340 条/天** |

已知事实：xiaobao 生产库有 **757 条** `x_twitter` 历史数据（DevOps 2026-07-25 交付时给出）；**日增量未知，从未有人问过。**

三条使这个缺口是实的而非理论的：

1. REQ-003 的提报动机明写解决「重试、超时、解耦能力弱」与积压问题；ai Architect 在 PRD R3 问题 2 也写过「REQ-003 的动机之一就是解决积压」。**既然积压是动机，处理能力就该被验证，而不该只被推导。**
2. v0.2 是**单实例 + 批内串行 + 无托管**（PRD §4 三重约束），处理能力无横向扩展余地；批内并发与多实例都排 v0.3，且多实例还卡着 C-6 前置。
3. 若日增量超过处理能力，队列会**持续单调增长**，且**不表现为任何报错**——US-1「xiaobao 不必挂起等待」照样达成，只是新闻越积越旧。这与设计 §7.2 对 `l0_label` 的判断同型：不报错、只是变差，**最难在灰度期被发现**。

### C. 预算机制引入的失败情形无对应 `error_kind`

PRD AC-6.1 的 `error_kind` 枚举为七类：`client_error` / `server_error` / `timeout` / `rate_limited` / `auth_error` / `db_error` / `mapping_error`。

设计 §4.5 新增了两类此前不存在的情形：

- **单条总预算耗尽**（`llm_process` 进入时预算已尽 → 整条按超时处理）
- **单段预算耗尽**（工具节点进入时预算已尽 → 跳过并记 `degraded:{tool}_budget_exhausted`）

二者当前都只能归入 `timeout`。但**它们与「LLM 真的慢」的处置完全不同**：

| 现象 | 归因 | 处置 |
|---|---|---|
| LLM 真的慢 / 限流 | provider 侧 | 调 provider、看 fallback 链 |
| 预算被前面的工具吃光 | 各段上限分配不当 | 调 `KB_TIMEOUT_MS` / `WEB_SEARCH_TIMEOUT_MS` |

灰度期若两者都记 `timeout`，**无法区分该调 provider 还是该调段上限**——而 DB 模式下日志是主要观测面（US-6）。

## 处理方式

### 变更 1（A 项）：AC-8.2 第 1 条据实订正

**PRD AC-8.2 的 `domain_tags` 差异条改写为**：

> - **`domain_tags` 在 DB 模式下实际恒为 `[]`**（2026-07-28 实测订正，**推翻 C-1 原闭合结论与本条原表述**）：契约 v1.4 虽已 GRANT `raw_items.l0_label`（SELECT），但实测该列**只有 `direct_display` 一个非空取值**（`news_test` 154/154；生产 637 非空全同 + 120 NULL），**是流程标记而非领域分类结果**。
>   - 适配层须把已确认的流程标记映射为 `[]`（设计 §3.3 用**排除集**实现：`direct_display` → `[]`；NULL / 空串 / 纯空白 → `[]`；其他任何值 → `[v]` 保守放行）。
>   - **不得照单值字面映射**：`['direct_display']` 是真值，会穿过 `news_l1.py:206` 的 `or None`，把零信息量标记同时塞进 prompt 与 KB 检索过滤条件——**比恒空更糟**（恒空会被正确忽略，噪声会实际污染推理与检索）。
>   - **不采用「一律置 `[]`」**：那样在 xiaobao 将来启用真实领域分类时 ai 侧会无声失效、需改代码才能受益；排除集能让语义修复在对方侧发生时 ai 自动跟上。
>   - 后果：**DB 模式的处理质量系统性低于 HTTP 模式，且不表现为任何报错**——只表现为评分与标签变差。已作为 **C-14** 提报 xiaobao（`l0_label` 完整取值域与语义 / 是否另有列承载真实 L0 分类）。

**连带**：PRD §6 的 C-1 行状态由「✅ 闭合（部分满足）」改为「⚠️ **闭合结论被实测推翻，重新开放**，已并入 C-14 提报」；已闭合计数由 14 项改为 **13 项**。

### 变更 2（B 项）：新增灰度期吞吐观察项

**PRD §4「本迭代不做」的「批内多条并发处理 / 多 worker 实例——顺延 v0.3」条目补一句前置观察**，并在 §7 新增开放问题 **O-11**：

> - **O-11（P1，新增）v0.2 的处理能力是否满足 xiaobao 的日增量**：`N = 1` + 单实例 + 批内串行下，处理能力上界约 **340~920 条/天**（正常 79s / 走满 240s 预算两种口径）。xiaobao 生产已有 757 条 `x_twitter` 历史数据，**日增量未确认**（已作为提报项转达）。
>   - **灰度期必须监测队列长度趋势**（`tasks` 中 `type='l1_ai_process' AND status='queued'` 的计数随时间变化）。判据：**若队列长度单调增长且持续超过一个观察窗口（建议 24h），即触发 v0.3 并发化的排期前移**。
>   - 该监测不需要新代码——设计 §2.5 已有 `consecutive_empty_polls`（空转侧），队列增长侧由 DevOps 在灰度期用 SQL 定期取数即可；若灰度期证明需要常态化，再进 v0.3 的可观测性范围。
>   - **本条不改变 v0.2 的任何实现与验收**，只要求灰度期把这个数看住，避免「解耦达成但积压未解」——那会让 REQ-003 只兑现了一半动机。

### 变更 3（C 项）：`error_kind` 枚举增补

**PRD AC-6.1 的 `error_kind` 枚举增加一类**：

> `error_kind` ∈ `client_error` / `server_error` / `timeout` / `rate_limited` / `auth_error` / `db_error` / `mapping_error` / **`budget_exhausted`**（新增）
>
> - **`budget_exhausted` 与 `timeout` 的区分**：`timeout` 表示**某次外部调用自身超时**（LLM / 工具的单次调用未在其段上限内返回）；`budget_exhausted` 表示**单条 wall-clock 预算（AC-3.8）被耗尽**——即前序步骤已把时间用光，本步骤根本没机会发起或未能完成。
> - **为什么必须分开**：二者的处置完全不同——`timeout` 指向 provider 侧（调 provider、查 fallback 链），`budget_exhausted` 指向各段上限分配（调 `KB_TIMEOUT_MS` / `WEB_SEARCH_TIMEOUT_MS` / 总预算）。DB 模式下日志是主要观测面，两者混记会让灰度期无法定位该调哪一个。
> - 适用位置：设计 §4.5 的两处——工具节点因预算耗尽被跳过（同时记 `degraded:{tool}_budget_exhausted`）、`llm_process` 进入时预算已尽导致整条放弃。

**连带**：PRD AC-3.8.2 中「写 `error_kind=timeout`」改为「写 `error_kind=budget_exhausted`」；AC-3.8.3 的验证方式同步。
