## 问题描述

### A. DevOps 附条件（高）：`N ≤ 8` 建立在一个未被保证的量上

AC-3.5 的推导是 `N × 单条耗时上限 < 1800s`，取「v0.1 实测 74~79s」→ N ≤ 22 → 保守取 8。**但 79s 是 v0.1 happy path 的实测均值，不是被任何机制保证的上限。**

DevOps 代码实查：单条 pipeline 各段超时**各自独立、串行累加**，无统一 wall-clock 预算——

| 段 | 超时来源 | 实际上限 |
|---|---|---|
| `kb_search` | `news_l1.py:205` 传 `inp.options.timeout_ms` | **180s** |
| `link_read` | `news_l1.py:143` `min(timeout_ms, 8000)` | 8s |
| `web_search` | `news_l1.py:173` 传 `inp.options.timeout_ms` | **180s** |
| LLM（含 provider fallback 链） | `client.py:99` 的 budget 在 `_budget_ms` 为 None 时退化为 `timeout_ms`，而 `client.py:216` 的 `ChainedAIClient(providers)` **正是未传 `budget_ms`** | **180s** |

`RunOptions.timeout_ms` 默认 **180000ms**（`schemas.py:15`）→ **单条最坏 wall-clock ≈ 548s**。代入 AC-3.5：`8 × 548s = 4384s ≫ 1800s`——**用 PRD 自己的默认配置就能算出违反**，而 AC-3.5 明写违反会「直接产生 xiaobao 误回收 + ai 仍在处理的双写竞态」。

两点加剧（均非假设）：
1. **基准选错**：74~79s 是 **HTTP 模式**实测，彼时 KB/link/search 由 xiaobao 预取传入；AC-8.2 自己写明 DB 模式下 KB 转为 ai 主动检索、`tool_summary.kb_search` 从 0 变常态 ≥1。**用 HTTP 模式的耗时约束 DB 模式的批量，基准不成立。**
2. **尾部正是最需要保障的时候**：逼近上限的场景（Tavily 不可达 / KB 慢 / LLM 限流触发 `ADR-0002` fallback 链串行重试）恰是故障期，而故障期又是队列积压、批量价值最高的时候。按均值配容量，故障时必然踩线。

同一个数字还撑着另外两条：AC-5.7 的宽限期下限（632s = 8 × 79s）、AC-9.3 的 `last_poll_at` 陈旧容忍上限——两者会随之偏小，宽限期配 632s 而实际需 4384s，等于**优雅停机在故障期必定强杀**。

### B. Architect 附条件（高）：黄金样本没有定义覆盖面

AC-9.4 的黄金样本外部化方法论正确（解了 Developer 指出的循环论证），但「若干组」未约束覆盖面，而 §6/§8 都把它认定为 O-8 这个 **P0 风险的唯一客观兜底**——**兜底的覆盖面不该是自由裁量的**。

同步转 async 的回归绝大多数不出在正常路径（正常路径改错了，单测立刻红），而集中在异常与边界路径。Architect 点名四类，且指出它们正是 v0.1 花整个迭代才调稳的语义、也是 DB 模式唯一观测面所依赖的（AC-6.6）。

其中最具体的一个失效场景：`ADR-0002` 的总 timeout budget 在同步实现下靠逐次调用累减，async 下若改用 `asyncio.wait_for` 包裹，抛的是 `asyncio.TimeoutError` 而非 `httpx.TimeoutException`——**不是同一个异常类型**。现有按类型分派的 `except`（`llm/client.py` 的 error kind 判定）会漏接 → 降级语义变化 → `tags.processing` 的降级标记与 `error_kind` 一起失真，而单测因 fake 被同步改写而照绿。

## 处理方式

### 变更 1（A 项，DevOps 附条件）：新增单条 wall-clock 预算，AC-3.5 的 N 值改为待 O-3 重算

采纳 DevOps 建议 **①（定义并强制单条 wall-clock 预算）**，不采纳建议 ②（直接把 N 改为 3）。

**理由（按 §0 准则裁定）**：建议 ② 是把 N 调小以绕开「上限不被保证」这个根因，属**图便捷**；建议 ① 是给系统一个**被保证的量**，之后 AC-3.5 的不等式、AC-5.7 的宽限期下限、AC-9.3 的陈旧容忍上限**三条才有确定的共同输入**。§0 准则要求宁可多干活也要让基础牢固，且 DevOps 已核实实现成本很低（`ChainedAIClient` 已有 budget 机制，`tool_budget_used` 已有次数预算，本项是补时间维度并提到 graph 层）。

**PRD 落点**：

1. **新增 AC-3.8（单条 wall-clock 预算）**：
   - 单条处理须设**总耗时预算**（`L1_ITEM_BUDGET_MS`，DB 模式生效）；预算耗尽时应主动放弃该条，按 AC-5.3 置 `retryable_failed`、写 `error_kind=timeout`、释放锁，**不得让单条无限累加各段超时**。
   - 预算须覆盖 pipeline 全程（含工具与 LLM provider fallback 链），而非各段独立超时之和。
   - 验证方式：mock 各段耗时使总和超预算，断言在预算点被放弃、状态与锁均正确、日志含 `error_kind=timeout`。
   - **具体数值归 O-3**（DevOps 建议 150~200s，与 v0.1 实测留 2 倍余量）。
2. **AC-3.5 订正**：`N ≤ 8` 标注为**待 O-3 重算的暂定值**，并写明「**实现阶段不得直接按 `N ≤ 8` 落地**；N 须由 O-3 依据 AC-3.8 确定的单条预算重算，不等式为 `N × 单条 wall-clock 预算 < 1800s`」。
3. **AC-5.7 订正**：宽限期下限由「N × 单条耗时上限」改为「**N × AC-3.8 的单条预算**」，三层一致性要求不变。
4. **AC-9.3 订正**：`last_poll_at` 陈旧容忍上限同步改为「**N × 单条预算 + 轮询间隔**」。
5. **§8 补充**：块 4（claim + worker 循环）的改动面增加「单条 wall-clock 预算（graph 层 deadline）」。

### 变更 2（B 项，Architect 附条件）：AC-9.4 补黄金样本四类路径覆盖

AC-9.4 的验证方式补：**黄金样本须至少覆盖四类路径**——

| # | 路径 | 覆盖理由 |
|---|------|---------|
| ① | 全工具命中的正常路径 | 基线 |
| ② | 工具全失败的降级路径 | v0.1 的部分可用语义（部分可用 = `succeeded`），DB 模式下工具触发率更高 |
| ③ | LLM 返回非法 JSON 的解析容错路径 | `llm/json.py` 的容错分支 |
| ④ | LLM 超时触发 provider fallback 的路径 | **最易在 async 化中静默变化**：同步下抛 `httpx.TimeoutException`，async 下若用 `asyncio.wait_for` 包裹则抛 `asyncio.TimeoutError`，按类型分派的 `except` 会漏接 → 降级标记与 `error_kind` 一起失真 |

每类快照均须**逐字段比对，含 `tags.processing` 的降级标记**。四类均为 mock 构造，不依赖真实外部依赖、不依赖 §5 的服务器环境，**改造动手前即可录制**。

**另记入 O-8（实现提醒，不进 AC）**：async 化后 `except Exception` 不捕获 `asyncio.CancelledError`（继承 `BaseException`），这是**正确且必须保持**的行为——若改造中有人把节点的 `except Exception` 顺手改成 `except BaseException` 或裸 `except:`，`CancelledError` 会被吞掉，**AC-5.7 的优雅停机会静默失效**（SIGTERM 后协程不响应取消、跑到宽限期强杀），且该失效在验收里表现为「优雅停机断言失败」，极难定位到具体 except 子句。
