## 问题描述

### A. `domain_tags` 真源被订正（C-14）—— 影响最大，且是好消息

对方 Architect 追出了 HTTP 模式 `L1Input.domain_tags` 的完整取数链路：

```text
sources.domain_tags (jsonb, schema.ts:67)
  → l1-processor.ts:243      SELECT s.domain_tags
  → l1-processor.ts:257-278  归一化为 string[] → L1Input.domainTags
  → ai-hub.ts:45             domain_tags: input.domainTags → HTTP 请求体
```

**`L1Input.domain_tags` 从来不是 L0 的产物，而是信息源级的静态领域标签**；`l0_label` 是「是否值得送 AI + 优先级 + 是否需补上下文」的处理决策标记，两者语义无关。对方已执行 `GRANT SELECT (domain_tags, attention_level) ON sources`（test + prod 双库 verify）。

后果：**DB 模式取到该列后与 HTTP 模式同字段同数据、完全等价**，原「`domain_tags` 恒为 `[]`」的已知差异整条消失。设计 §3.3 的排除集方案（建立在「`l0_label` 是 `domain_tags` 对应物」这一已撤回前提上）随之作废。

### C. 一项待架构拍板：KB 检索的鉴权方式

对方 DevOps 澄清：`/v1/kb-search` 走全局 `adminGuard`，鉴权 = **`ADMIN_TOKEN` 或 IP 白名单**（满足其一即放行）；**后端不存在 `KB_ADMIN_TOKEN` 这个 env**。给出两个方案并**把选择权交给「架构/Owner」**：

- 方案 A：同机直连 `127.0.0.1`，IP 白名单放行，**免 token**；
- 方案 B：需 token，但当前唯一可用的是其**全权 `ADMIN_TOKEN`**——下发即授予 ai 所有 admin 写接口权限（改源 / 删空间 / 同步规则），其 DevOps 明确不建议、也不擅自下发。

## 变更判断

- 是否改变产品范围：**否**
- 是否改变主流程：**否**（claim → 处理 → 写回三段式不变）
- 是否改变架构方案：**否**（协议分层、事务边界、async 地基、N=1、预算机制均不变；`domain_tags` 变的是**取数来源**，映射层位置与依赖方向不变）
- 是否改变接口/数据契约：**否**（不改 `news-l1` HTTP v1；`news-l1-db` 由对方升 v1.5，ai 侧跟进读取新授权列）
- 是否改变验收/回归：**是** —— 均为**收紧或消解**，不放宽任何一条：AC-8.2 的 `domain_tags` 差异条应撤回（差异已消失）、测试 11 用例据实重写、测试 20 前置解除
- 是否改变部署方式：**否**（KB 走同机直连是对既有同机部署事实的确认，非新增部署动作；但新增一条部署约束）
- **结论：轻量变更** —— 全部由外部权威答复驱动，落在数据来源、待确认项闭合与验收用例上，不触及范围、架构与对外契约。符合 §11「轻量变更 → Change Note + 受影响角色确认」，不回设计阶段。

## 处理方式

### 变更 1（A 项）：`domain_tags` 改从 `sources.domain_tags` 取，§3.3 整节重写

- `SourceRecord` 新增 `source_domain_tags: list[str]`（§2.1）；`l0_label` 保留字段但 **v0.2 不消费**。

- claim 事务步骤 3 的 SELECT 增加 `s.domain_tags`（§3.4）。
- 原排除集方案（`direct_display` → `[]`）**作废**。
- **连带（归 PM）**：PRD AC-8.2 的 `domain_tags` 差异条**整条撤回**，**CN-004 变更 1 随之作废**（其前提是对方已撤回的错误结论）。

### 变更 3（C 项）：KB 鉴权定为方案 A，新增设计 §4.13

**采用方案 A：同机直连、不使用任何 token。**

- `KB_SEARCH_URL` 指向 `http://127.0.0.1:8001`（test）/ `:8000`（prod）。
- **不配置 `KB_ADMIN_TOKEN`**；`tools/kb.py:38-40` 现有逻辑为「该 env 为空则不发头」，**零代码改动即兼容**。
- **明令禁止下发 xiaobao 全权 `ADMIN_TOKEN`**（越权严重，与其 DevOps 判断一致，此处固化为设计约束）。
- **部署约束**：本方案唯一前提是**同机**。若将来分机部署，IP 白名单失效、KB 检索全部失败（表现为持续 `degraded:kb_search_failed`，不影响主流程）；届时正确解法是请 xiaobao Developer 加**独立只读 KB token**，不是复用全权 token。已写入 §7.2 与部署就绪检查。

### 范围纪律（明确不做）

对方建议 `l0_label` 可作为处理优先级信号用于 `needs_context` 判定（呼应 Q-1）。**这是新能力，不在 v0.2 范围，登记为 v0.3 候选，本迭代不做。** 不因为对方提了个好主意就扩范围。
