## 问题描述

### A. 主循环没有异常边界，一次 DB 瞬时故障即杀死 worker

`worker_loop` 的 `await source.fetch_batch(...)`（`worker/loop.py:156`）无 try/except；`process_one` 只有 `finally` 无 `except`；`_commit_with_retry` 重试耗尽后 `raise`。异常穿透整个主循环 → task 异常结束 → `_on_worker_done` → `mark_dead` → `/health` 503，**而部署就绪检查 C4 已登记 `dead` 在 v0.2 没有任何自动消费方**（`Restart=on-failure` 只看进程退出码，worker 协程死亡时进程仍存活），只能靠人工 curl 发现。

**触发面比看起来大**：claim 每 `L1_POLL_INTERVAL_MS`（15s）执行一次，是全链路最高频的 DB 操作，**且一次重试都没有**——写回尚有 3 次尝试。PG 例行重启、网络闪断、`PoolTimeout`、单次 tx 超时都会走到这条路径。

**两条路径的性质必须分开说**：

| 路径 | 设计怎么定的 | 实现做了什么 |
|---|---|---|
| 写回重试耗尽 | §4.6 与 §4.7 表**都明确写了**「条目保持 `running`/`processing`，由下一次启动自愈或对方回收」——语义是**放弃这一条、worker 继续跑** | 抛异常杀死 worker；`test_writeback_gives_up_after_retries` 用 `pytest.raises(RuntimeError)` 把它固化成了断言 |
| claim 失败 | §4.7 的失败情形表**根本没有这一行**，§4.2 伪代码也没有 | 同样穿透 |

前者是实现偏离已定稿设计，后者是**我的设计缺口**。设计、实现、测试三层各漏一半。

**它还与设计里另一处已定的取舍方向相反**：§4.1 明确定过「启动自愈失败**不阻止启动**，可用性优先」（DevOps 设计 R1 问题 3），理由是「自愈失败最可能的原因正是 DB 短暂抖动，那时更该让服务起来重试」。**同一个原因（DB 短暂抖动）在启动期被判为「不该拦」，在运行期却直接判死**，两处口径不一致。

### B. `connect_timeout` 的生效值不等于配置值，门禁在断言一个不生效的数

`build_conninfo` 传 `connect_timeout = max(1, connect_timeout_ms // 1000)`，默认取值下为 `1`。而 **libpq 的最小允许值是 2 秒，`1` 被解释为 `2`**。本机实测（psycopg 连不可路由地址 `10.255.255.1:5432`）：

```text
connect_timeout=1  →  实际 2.02s
connect_timeout=2  →  实际 2.02s
connect_timeout=3  →  实际 3.03s
```

当前取值下 `connect(实际 2s) < lock(3s)` **仍成立，正确性不受影响**。但 `validate_worker_settings` 断言的是配置值 `1000`，不是生效值 `2000`：

- 若把 `AI_DB_LOCK_TIMEOUT_MS` 调到 2000 以下，门禁看 `1000 < 5000` 判通过，而实际 `connect(2000) > lock(1800)`——三层超时「便于在日志中区分等锁 / 查询慢 / 事务超时」的意图静默失效；
- 若有人配 `AI_DB_CONNECT_TIMEOUT_MS=1500` 期望 1.5s，实际仍是 2s。

**这是在 CN-008 把 `connect_timeout` 从 5000 收到 1000、并入不等式 3 时引入的**：把一个量拉进启动门禁，却没有验证它在驱动层是否按字面生效。**本迭代第六次「校验通过但保证不成立」，与前五次同一形状——式子没错，错在某个输入量没被真正约束住。**

> **归属订正（2026-08-02，据 DevOps 确认意见 ①）**：本段原写作「**这是我**（Architect）……引入的」。**DevOps 的更正成立**——提出 `5000→1000` 并主张并入不等式 3 的是 DevOps（CN-008 末票中①），我是落地方。
>
> **但更正不等于责任转移，我那一份不因此消失**：我把它写进设计 §2.6 和启动门禁时，同样只核了「值够不够大」，没核「libpq 认不认这个值」。**提出方验了余量、落地方验了算术，两个人都没验语义**——这恰恰说明它不是谁疏忽了一次，而是**「新量入门禁前必须验其生效语义」这一步在流程里根本不存在**。DevOps 已自认「我在 CN-008 里刚写完『新增参与不变式的量，第一件事是问它自己被什么约束着』，然后自己没做到」；对称地，我读到那句话时也没把它套用到它所修饰的那个量上。**该记的教训是流程缺步，不是两个人各自的一次走神。**

## 处理方式

### 变更 1（A）：主循环异常边界 + 连续失败判死

设计 §4.2 主循环改为：

```text
consecutive_db_failures = 0
while state.state == "running":
    try:
        items = await source.fetch_batch(N)
        ... 原有编排 ...
        consecutive_db_failures = 0            # 任一轮成功即清零
    except Exception as exc:                   # CancelledError 是 BaseException，不在此列
        consecutive_db_failures += 1
        log.error("loop_iteration_failed", error_kind="db_error", consecutive=...)
        if consecutive_db_failures >= L1_LOOP_FAILURE_LIMIT:
            raise                              # 交 _on_worker_done → mark_dead
        await sleep_interruptible(poll_interval, stop)
```

- **`except Exception` 而非 `BaseException`**：`CancelledError` 必须穿透，否则优雅停机失效（与 `run_tx` 的同一条推理，pool.py 已写明）。
- **仍保留判死能力**：DB 持续不可用时（如口令失效、库被删）继续空转没有意义，`L1_LOOP_FAILURE_LIMIT` 次后仍走 `mark_dead`。默认取 **15**（**由 20 下调，见变更 3——原值在把失败自身耗时算进去后不满足新增的不等式 4**），实际判死窗口 `15 × (15s + 5s) = 300s ≈ 5 分钟`，**短于对方 600s 卡死回收**。
- **写回路径回归设计原意**：`_commit_with_retry` 耗尽后不再向上抛，改为记 `db_error` 并 return，条目保持 `running`/`processing` 走 §4.7 已定的「由自愈或对方回收」路径。**这条不是新增语义，是把实现拉回设计已经写好的那一条。**
- **⚠️ 但只做这一步会制造一条无限期静默的路径**——见变更 6（据 Developer 中①），该子项必须与本条同时落地，不得单独实施。
- **连带（Developer 中② 引出）：主循环的 `error_kind` 不得硬编码 `db_error`**，按异常类型分流，见变更 7。

§4.7 失败情形表补一行：

| 情形 | 处置 |
|---|---|
| **claim 事务失败（DB 不可达 / 超时）** | 不涉及任何条目（尚未领到），记 `db_error`、退避一个轮询间隔后重试；连续 `L1_LOOP_FAILURE_LIMIT` 次后判死 |

### 变更 2（B）：`connect_timeout` 生效语义归一

`build_conninfo` 与门禁统一按**生效值**处理：

```python
EFFECTIVE_CONNECT_TIMEOUT_S = max(2, connect_timeout_ms // 1000)   # libpq 最小 2s；取整须 floor，见下
```

> **原写作 `round(...)`，据 Developer 低③ 订正为 `//`（floor）**。`round` 下 `3500 → 4`，即配 3.5s 实际生效 **4s，比配置意图更长**；floor 下 `3500 → 3`。**对超时量，生效值只可短于或等于配置意图，不可更长**。原实现 `max(1, ms // 1000)` 本就是 floor，本 CN 只需把下限 1 改成 2，**没有任何理由连取整方式一起换**——这是我在改一个 bug 时顺手引入的第二个。

- 门禁的不等式 3 改用 `EFFECTIVE_CONNECT_TIMEOUT_S * 1000` 参与比较，**断言的数与真正生效的数一致**；
- 设计 §2.6 的 `AI_DB_CONNECT_TIMEOUT_MS` 行补注「libpq 下限 2s，配置小于 2000 时按 2000 生效」，取值仍写 1000 但标明生效 2000（保留配置意图、暴露真实语义）。

**为什么不干脆把默认值改成 2000**：改默认值会让「配置写什么就生效什么」看起来成立，反而掩盖了 libpq 的下限语义——下一个把它调到 1500 的人会再踩一次。**暴露语义比藏起来更值钱。**

### 变更 3（据 DevOps 中①）：判死窗口进启动门禁，**公式须比其建议的多一项**

**采纳「必须加，不是值得判断」**，其三条理由全部成立，尤其 (b)：`L1_POLL_INTERVAL_MS` 的允许区间是 10~30s，配到上限就把窗口拉长一倍，而当前没有任何机制会拦。

**但其建议的式子 `LIMIT × POLL < STALE × 0.6` 少算了一项**：每次失败**自身**要先耗掉一个事务超时才会走到 `sleep`（`fetch_batch` 经 `run_tx`，`asyncio.wait_for` 封顶 `AI_DB_TX_TIMEOUT_MS`）。**一轮失败周期是 `TX + POLL = 20s`，不是 `POLL = 15s`。** 代入实算：

| 算法 | 默认取值下的窗口 | vs `600s × 0.6 = 360s` |
|---|---|---|
| `LIMIT × POLL`（原建议） | `20 × 15s = 300s` | ✔ 通过 |
| `LIMIT × (POLL + TX)`（**真实周期**） | `20 × 20s = **400s**` | **✘ 不通过** |

**即：按原式子门禁会放行，而真实判死窗口已越过 0.6 系数线。我在变更 1 里定的 `LIMIT = 20` 本身就不满足这条不等式。**

**这是第七次「校验通过但保证不成立」，而且它现场发生在我们正为防止这类问题而讨论的那条式子上**——三个人（PM 提请、DevOps 主张、我采纳）都盯着「LIMIT 和 POLL 两个输入会不会被调大」，没有一个人问「**一轮失败到底耗多久**」。**这恰恰反证了 DevOps 中① 的判断**：如果只写注释「LIMIT × POLL 要小于 600s」，这一项会永远缺着；进了门禁、公式被写成可执行代码，启动时一算就拒绝。**能自动执行的约束才会被验算，写在注释里的只会被引用。**

**不变式 4（进启动门禁）**：

```text
L1_LOOP_FAILURE_LIMIT × (L1_POLL_INTERVAL_MS + AI_DB_TX_TIMEOUT_MS) < AI_STALE_TIMEOUT_MS × 0.6
当前取值：15 × (15000 + 5000) = 300s < 360s ✔（1.2 倍余量）
```

- 系数 0.6 与不等式 2 同口径（DevOps 建议，采纳）；
- **默认值 `L1_LOOP_FAILURE_LIMIT` 由 20 下调为 15**——15 × 20s = 300s，恰好回到我在变更 1 原本想要的「≈5 分钟」（当初写 20 就是按漏了 TX 的那个算法算出来的）；
- 它同时锁住**三个**输入（LIMIT / POLL / TX），比原建议多锁一个。

### 变更 4（据 DevOps 中②）：`consecutive_db_failures` 进 `/health`

**采纳，且认为其对 PM 处置的修正方向是对的**：不该要求人去 grep 日志，该把状态暴露出来。其援引的先例贴切——`self_heal_failed` 当初进 `/health` 的理由就是「启动日志会被后续日志淹没，状态位不会」，本处是同一条推理的原样重演。

- `WorkerState` 增 `consecutive_db_failures: int`，`/health` 响应体新增同名字段，与已有的 `in_flight` / `current_item_started_at` / `self_heal_failed` 并列；
- **状态码不变**（连续失败期间仍 `running` → 200）。判死前它就是"活着但在挣扎"，这正是要暴露的信息，不是要改判的状态；
- **日志仍要打**（PM 其④ 的要求保留）：状态位只有当下值，日志有历史与时间线，两者不互替。

### 变更 6（据 Developer 中①）：写回失败单设计数并判死，**判死方向与其建议相反**

**其指出的缺口成立且是我引入的**：变更 1 把写回耗尽改为不抛（方向对，那是设计原意），但与「任一轮成功即清零」叠加后——**claim 成功清零，写回失败不抛异常、不进 except、根本不计数**。于是 DB「可达但写不进」时（磁盘满 / 对方 DDL 持锁 / 写权限变更；claim 是读+单表短写，写回是三表写入，偏态完全可能）：worker 永远 `running`、`/health` 200、`consecutive_db_failures` **恒为 0**，而每个条目走完 `attempt` 后进 `final_failed`，**整个队列被静默报废**。

**其对比一针见血**：改前粗暴但有 503 这个信号，改后一个信号都没有。而变更 4 那个专为暴露「活着但在挣扎」而加的字段，在这个场景下显示的恰恰是「一切正常」。

**① 单设 `consecutive_writeback_failures` 并同样进 `/health`：采纳。** 其理由（根因不同，混在一个计数里判死理由失真）成立，我再补一条：**两者的正确处置方向也不同**，合并计数会连处置一起搞混。

**② 是否判死：其倾向「不判死、但必须可见」，我定为「判死」，且理由与其相反——不判死才是牺牲条目。**

其论据是「条目仍有 `attempt` 上限兜底，判死会牺牲本可正常处理的其他条目」。**该论据的前提在环境性故障下不成立**：写回是每个条目的必经步骤，DB 写不进时**没有任何条目能被处理完**，不存在「本可正常处理的其他条目」。而两条路的代价是不对称的：

| | 继续跑（不判死） | 判死 |
|---|---|---|
| 条目去向 | 逐个走完 `attempt` → **`final_failed`（终态，不再重试）** | 留 `running` → 对方 600s 回收 → `retryable_failed` → **重新排队** |
| 数据 | **持续把可恢复的条目烧成不可恢复的** | **保住** |
| 代价 | 每条还白烧 240s 算力 + 一次 LLM 调用费 | worker 停摆待人工 |

**即「不判死」换来的不是可用性，是把可恢复损失变成不可恢复损失。**

**③ 但其顾虑在另一种场景下完全成立，且指向我 Review 时漏报的一处实现偏离**：若写回失败是**数据相关**的（某条数据触发约束冲突 / 字段超长），确实只影响这一条，其他条目正常——此时判死就是误伤。而设计 §4.6 早已写明「**仅对可重试的 PG 错误类**（连接错误 / `deadlock_detected` / `serialization_failure`）；确定性错误（约束冲突、权限拒绝）**不重试**」，**实现的 `_commit_with_retry` 却是 `except Exception` 无差别重试**（`loop.py:130`）。

**这处偏离我在实现 R1 Review 里漏报了**，是 Developer 的中① 把我引到这里的。补上它，其顾虑自动消解：

- 确定性错误 → **不重试**，直接按该条失败处理（`mark_failed`），**不计入判死计数**——它是数据问题，不该拖垮 worker；
- 可重试错误（连接/死锁/序列化）→ 重试 `L1_WRITEBACK_RETRY` 次，仍失败才计数；
- **连续 `L1_WRITEBACK_FAILURE_LIMIT` 次（默认 3）判死。**

**④ 阈值为什么是 3 而不是像 claim 那样 15**：单次失败的代价差两个数量级——claim 失败一次 = 20 秒空转；写回失败一次 = **240s 算力 + 一次 LLM 调用费 + 烧掉一条 `attempt`**，且该条已内部重试 3 次（跨 18s）才算一次。3 条连续失败 ≈ 13 分钟，足以排除偶发，同时把烧掉的 `attempt` 控制在 3 条以内。**阈值差 5 倍，是因为单次代价差了两个数量级。**

### 变更 7（据 Developer 中②）：主循环 `error_kind` 按异常类型分流，`_error_kind_of` 不删

### 变更 9（据 DevOps 中③）：`task.cancel()` 后须等取消完成再关池——**处置采纳，机理订正**

```python
except asyncio.TimeoutError:
    task.cancel()          # 仅「请求」取消，不等待
finally:
    await pool.close()     # 立即关池
```

**其处置建议正确，采纳**：`task.cancel()` 后加 `await asyncio.gather(task, return_exceptions=True)`。这段代码我 Review 时也读了（当时在核 `_on_worker_done` 与三态），同样没看出来。

**但其给的机理不成立，须订正——这个区分有实际后果**。其称「最坏是事务在 COMMIT 前连接被抽走」。查 `psycopg_pool` 源码与 docstring：

> **Currently used connections will not be closed until returned to the pool.**

`close()` 只关闭**池内空闲**的连接（`connections = list(self._pool)`），**正在使用中的连接不会被抽走**；其 `timeout` 参数等的是池的内部维护 task（`agather(*workers, timeout=timeout)`），与使用中的连接无关。

**真正的机理是**：`lifespan` 的 `finally` 执行完 → ASGI 生命周期结束 → **进程退出，而 worker 协程的取消尚未完成**，它持有的事务随进程一起没了。残留锁的风险是真的，但根因是**没等协程收尾就让进程走**，不是池抽连接。

**为什么必须订正而不是「结论对就行」**：按其机理，一个自然的修法是「给 `pool.close()` 加个更大的 timeout」——**那是完全无效的**，因为该 timeout 根本不等使用中的连接。**机理错会导出一个看起来合理、实际不解决问题的修法，而它同样会「测试通过」。** 唯一有效的修法就是等 `task` 真正结束，即其原本的建议。
