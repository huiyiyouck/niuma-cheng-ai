## 问题描述

### A. 主循环没有异常边界，一次 DB 瞬时故障即杀死 worker

`worker_loop` 的 `await source.fetch_batch(...)`（`worker/loop.py:156`）无 try/except；`process_one` 只有 `finally` 无 `except`；`_commit_with_retry` 重试耗尽后 `raise`。异常穿透整个主循环 → task 异常结束 → `_on_worker_done` → `mark_dead` → `/health` 503，**而部署就绪检查 C4 已登记 `dead` 在 v0.2 没有任何自动消费方**（`Restart=on-failure` 只看进程退出码，worker 协程死亡时进程仍存活），只能靠人工 curl 发现。

**触发面比看起来大**：claim 每 `L1_POLL_INTERVAL_MS`（15s）执行一次，是全链路最高频的 DB 操作，**且一次重试都没有**——写回尚有 3 次尝试。PG 例行重启、网络闪断、`PoolTimeout`、单次 tx 超时都会走到这条路径。

**两条路径的性质必须分开说**：

| 路径 | 设计怎么定的 | 实现做了什么 |
|---|---|---|
| 写回重试耗尽 | §4.6 与 §4.7 表**都明确写了**「条目保持 `running`/`processing`，由下一次启动自愈或对方回收」——语义是**放弃这一条、worker 继续跑** | 抛异常杀死 worker；`test_writeback_gives_up_after_retries` 用 `pytest.raises(RuntimeError)` 把它固化成了断言 |
| claim 失败 | §4.7 的失败情形表**根本没有这一行**，§4.2 伪代码也没有 | 同样穿透 |

前者是实现偏离已定稿设计，后者是**我的设计缺口**。设计、实现、测试三层各漏一半。

**它还与设计里另一处已定的取舍方向相反**：§4.1 明确定过「启动自愈失败**不阻止启动**，可用性优先」（DevOps 设计 R1 问题 3），理由是「自愈失败最可能的原因正是 DB 短暂抖动，那时更该让服务起来重试」。**同一个原因（DB 短暂抖动）在启动期被判为「不该拦」，在运行期却直接判死**，两处口径不一致。

### B. `connect_timeout` 的生效值不等于配置值，门禁在断言一个不生效的数

`build_conninfo` 传 `connect_timeout = max(1, connect_timeout_ms // 1000)`，默认取值下为 `1`。而 **libpq 的最小允许值是 2 秒，`1` 被解释为 `2`**。本机实测（psycopg 连不可路由地址 `10.255.255.1:5432`）：

```text
connect_timeout=1  →  实际 2.02s
connect_timeout=2  →  实际 2.02s
connect_timeout=3  →  实际 3.03s
```

当前取值下 `connect(实际 2s) < lock(3s)` **仍成立，正确性不受影响**。但 `validate_worker_settings` 断言的是配置值 `1000`，不是生效值 `2000`：

- 若把 `AI_DB_LOCK_TIMEOUT_MS` 调到 2000 以下，门禁看 `1000 < 5000` 判通过，而实际 `connect(2000) > lock(1800)`——三层超时「便于在日志中区分等锁 / 查询慢 / 事务超时」的意图静默失效；
- 若有人配 `AI_DB_CONNECT_TIMEOUT_MS=1500` 期望 1.5s，实际仍是 2s。

**这是我在 CN-008 把 `connect_timeout` 从 5000 收到 1000、并入不等式 3 时引入的**：把一个量拉进启动门禁，却没有验证它在驱动层是否按字面生效。**本迭代第六次「校验通过但保证不成立」，与前五次同一形状——式子没错，错在某个输入量没被真正约束住。**

## 处理方式

### 变更 1（A）：主循环异常边界 + 连续失败判死

设计 §4.2 主循环改为：

```text
consecutive_db_failures = 0
while state.state == "running":
    try:
        items = await source.fetch_batch(N)
        ... 原有编排 ...
        consecutive_db_failures = 0            # 任一轮成功即清零
    except Exception as exc:                   # CancelledError 是 BaseException，不在此列
        consecutive_db_failures += 1
        log.error("loop_iteration_failed", error_kind="db_error", consecutive=...)
        if consecutive_db_failures >= L1_LOOP_FAILURE_LIMIT:
            raise                              # 交 _on_worker_done → mark_dead
        await sleep_interruptible(poll_interval, stop)
```

- **`except Exception` 而非 `BaseException`**：`CancelledError` 必须穿透，否则优雅停机失效（与 `run_tx` 的同一条推理，pool.py 已写明）。
- **仍保留判死能力**：DB 持续不可用时（如口令失效、库被删）继续空转没有意义，`L1_LOOP_FAILURE_LIMIT` 次后仍走 `mark_dead`。默认取 **20**，与 `L1_EMPTY_POLL_WARN` 同量级 ≈ 5 分钟——**短于对方 600s 卡死回收**，故不会出现「worker 装死但条目被反复回收」的窗口。
- **写回路径回归设计原意**：`_commit_with_retry` 耗尽后不再向上抛，改为记 `db_error` 并 return，条目保持 `running`/`processing` 走 §4.7 已定的「由自愈或对方回收」路径。**这条不是新增语义，是把实现拉回设计已经写好的那一条。**

§4.7 失败情形表补一行：

| 情形 | 处置 |
|---|---|
| **claim 事务失败（DB 不可达 / 超时）** | 不涉及任何条目（尚未领到），记 `db_error`、退避一个轮询间隔后重试；连续 `L1_LOOP_FAILURE_LIMIT` 次后判死 |

### 变更 2（B）：`connect_timeout` 生效语义归一

`build_conninfo` 与门禁统一按**生效值**处理：

```python
EFFECTIVE_CONNECT_TIMEOUT_S = max(2, round(connect_timeout_ms / 1000))   # libpq 最小 2s
```

- 门禁的不等式 3 改用 `EFFECTIVE_CONNECT_TIMEOUT_S * 1000` 参与比较，**断言的数与真正生效的数一致**；
- 设计 §2.6 的 `AI_DB_CONNECT_TIMEOUT_MS` 行补注「libpq 下限 2s，配置小于 2000 时按 2000 生效」，取值仍写 1000 但标明生效 2000（保留配置意图、暴露真实语义）。

**为什么不干脆把默认值改成 2000**：改默认值会让「配置写什么就生效什么」看起来成立，反而掩盖了 libpq 的下限语义——下一个把它调到 1500 的人会再踩一次。**暴露语义比藏起来更值钱。**

### 变更 3：新增两项测试

| # | 测试 | 判据 |
|---|------|------|
| 29 | 主循环容错 | mock `fetch_batch` 连续抛 N 次后恢复，断言 worker **仍在 running**、后续条目正常处理；连续抛满 `L1_LOOP_FAILURE_LIMIT` 次则断言 `phase == "dead"` |
| 30 | `connect_timeout` 生效值归一 | 断言 `EFFECTIVE_CONNECT_TIMEOUT_S` 在配置 500 / 1000 / 1500 时均为 2，配置 3000 时为 3 |
