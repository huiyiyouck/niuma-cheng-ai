## 2026-08-03 — 生产部署漏掉一条早已登记、明确归我的待办，导致首批 5 条真实数据全废

- 现象：08-03 生产部署时直接复制 test 的 `.env`，其中的火山 CodingPlan provider **订阅早已失效**。而 ai 侧 08-02 的 coordination 帖白纸黑字写过：「部署 `.env` 中原配的火山 CodingPlan 订阅已过期（HTTP 400），**归我方 DevOps 更新**」——**这是一条已登记、指名归我的待办，我做部署前核实时没看**。结果：我报告「B/D 组全绿、生产部署完成」，对方据此切 `database` 并放 5 条小批量，**5/5 `llm_process:provider_error` 进 `final_failed`**。对方在待跟进 22 里的判断一针见血：「你方 08-02 帖自报过期归 ai DevOps 更新；**08-03 部署验证清单未含真实 LLM 调用**」。
- 修正：换用本机 openclaw 的 plan 端点 + 有效 key（Owner 早已明确要用它），两环境同修并实测通过；补判据 **B5「LLM provider 实际可调用」**，要求用部署 `.env` 的真实配置发起真实调用、不接受「配置项非空」这类间接判据。
- 预防（两条，第二条更重要）：
  1. **部署前必须读一遍 coordination 待跟进表中归我的项**，不能只跑自己的判据清单。
  2. **我把「跑完自己的判据」当成了「检查完了」——而判据是我自己写的，它的盲区就是我的盲区，永远不会自己暴露。** 24 条判据覆盖了 DB 不变式、三层时限、角色超时、探活、停机、残留锁、跨项目坐标，**唯独没有一条问「这个服务的核心能力还在不在」**。我逐项核过 `LLM_PROVIDERS_JSON` 结构、`api_key_env` 指向、环境变量非空——**全部「正常」，而 key 早就废了**。这与本迭代反复出现的「校验通过但保证不成立」同形，只是这次的「校验」是我自己设计的那套判据。
- 关联：同日还犯过一次「结论下早了」——把根因报成「需 Owner 处理订阅、ai 无法自行修复」，而可用凭据本就在本机 openclaw 配置里、Owner 也早说过要用它。**我在报出阻塞前没查本机是否已有可用凭据**，把「换配置即可」报成「等外部采购」，让对方多等一轮。两件事的共性：**在下结论前，我没有把「已经存在的信息」找全**。

## 2026-08-03 — 我提了一个不存在的问题，并在随后三轮复核里都没验过它的前提

- 现象：实现 R1 我提出中③「`task.cancel()` 后未 await 即关池，worker 可能正持有连接」，被采纳为 CN-010 变更 9，Developer 落地、我 R2 报「未落地」、R3 报「已落地且有专测」。直到实现 R4 由 Developer 反向注入才查出：**`asyncio.wait_for` 超时时已经取消并等待 task 结束**（我在 3.11 与部署机 3.12 独立复验，`task.done()=True` 且收尾已跑完）——**这个问题在生产代码里从未成立**。五个环节、四轮实现，无人问过「它真的会发生吗」。
- 修正：R4 复核中据实认领并写入 Review；生产代码的两行冗余保留（防 `wait_for` 语义再变），注释已写明它是防御性冗余而非修 bug。
- 预防：**我 R2/R3 两次复核都写了「不读留痕、逐项实测」，但实测的是「代码有没有按建议改」，不是「这个改动要解决的问题是否真实」——我把实测用在了验证落地，没用在验证前提。** 今后提出任何「可能发生 X」的问题时，**先构造最小复现证明 X 会发生**，再提；提不出复现就标注为「未经复现的推测」，不进 CN 正文。**这与我在 CN-008 写下又自己没做到的那条同形**（当时是「新增参与不变式的量，先问它被什么约束着」）——两次都是我写下了正确的纪律，然后在下一件事上没有套用它。
- 附一条同日的方法教训：R4 复核中我做反向注入验证测试鉴别力，**第一次注入无效**——我在原 `close()` 之外**增加**了一次提前的 close，而 spy 的 `task_done_at_close` 是每次覆盖写，被第二次抹掉，6 个测试全绿。差点据此报出「测试仍无鉴别力」。**注入了不等于注对了**：反向注入必须**真正违反不变量**，而不是在旁边加一个动作。与 Developer 同轮那次「注入点打在复刻件上」是同一类。

## 2026-08-01 — `git add -A` 把 Architect 未提交的工作卷进我的 commit

- 现象：提交 CN-009 确认（`a2943e2`）时用 `git add -A`，把工作区里 Architect 尚未提交的 `v0.2-design.md` 改动（24 行，CN-009 变更 1 的设计侧连带落地 + `needs_context` 语义核查）一并提交并推送。该 commit 的 message 完全没提这部分，**造成归属错乱与 message 范围不符**。我当时确实跑了 `git diff --cached --stat`，输出里明明有 `v0.2-design.md | 24 +++`，**但只扫了一眼没核对就继续了**——[P0]「push 前贴 `git diff --stat` 核对；与 message 范围不符则停等 Owner」这条我执行成了形式动作。
- 修正：已 push 且 [P0] 禁止 force push，故**不改写历史**；改为补一个说明 commit 交代归属，并在此立档。Architect 的那部分内容本身有效、无需回退。
- 预防：**多角色并行的仓里，`git add -A` 是默认不安全的**。今后提交一律满足其一：① `git add <明确文件列表>`（首选，本次若用此法根本不会发生）；② 用 `-A` 时，`git diff --cached --stat` 的**每一个文件名都要能对上我这次改过的清单**，对不上就停——**核对的判据是「文件清单逐一匹配」，不是「看一眼有没有报错」**。
- 关联：同期还犯过两次「拿旧认知说当前状态」（CN-008 的 PM 确认状态、6i② 的闭合状态），共性是**该在下结论前查的，等被追问才查**。三次合起来指向同一条：**核对动作要在产生后果之前完成，不能事后补**。
- **同日镜像事件（补记）**：数小时后 **ai PM 会话反向卷入了我的改动**——我写好未提交的 REQ-003 回帖（约 40 行）被其 commit `0cc7510` 一并提交（内容完整、已正常发布，仅归属记错）。**方向相反的同一问题当天发生两次，说明这不是我的个人疏忽，而是「多角色共享同一 git 工作区」这个形态的固有缺口**：我的预防措施只能约束我自己，约束不了别的角色会话。据此已提报 **BCR-016** 到 coordination 基线修正提案池，建议把提交范围从「事后核对」提前为「事前限定」（默认禁裸 `git add -A`）。**本条保留在我的 corrections 里不因提了 BCR 而撤销**——BCR 是否采纳由 Owner + 参谋长定，在它落地前，我自己这条纪律照守。
