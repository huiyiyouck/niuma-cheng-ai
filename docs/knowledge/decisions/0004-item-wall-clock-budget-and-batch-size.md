# ADR-0004: 单条 wall-clock 预算优先于批量，批量大小取 1
- 日期: 2026-07-27
- 状态: 提议

## 背景

DB 模式下 ai claim 一批条目后会把它们同时置为 `processing` 并写入 `locked_at`；xiaobao 侧有 **1800s 卡死回收**机制（`news-l1-db` v1.4 §卡死回收），超阈值未完成的任务被强制回收为 `retryable_failed`。若批内最后一条的持锁时长超过 1800s，会产生「xiaobao 误回收 + ai 仍在处理」的双写竞态——ai 处理完写 `completed`，而 xiaobao 已把它回收，最终状态取决于写入顺序。

PRD 一度按「v0.1 实测单条 74~79s」推导 `N ≤ 22`、保守取 `N ≤ 8`。DevOps 在 R4 复审中指出这个推导的**输入不成立**：79s 是 happy path 的实测均值，不是被任何机制保证的上限。代码实查显示各段超时**各自独立、串行累加**——

| 段 | 超时来源 | 实际上限 |
|---|---|---|
| `kb_search` | `news_l1.py:205` 传 `inp.options.timeout_ms` | 180s |
| `link_read` | `news_l1.py:143` `min(timeout_ms, 8000)` | 8s |
| `web_search` | `news_l1.py:173` 传 `inp.options.timeout_ms` | 180s |
| LLM（含 provider fallback 链） | `client.py:99` 的 budget 在 `_budget_ms` 为 None 时退化为 `timeout_ms`，而 `client.py:216` 构造 `ChainedAIClient` 时**未传 `budget_ms`** | 180s |

`RunOptions.timeout_ms` 默认 180000ms（`schemas.py:15`）→ **单条最坏 ≈ 548s**。代入不变式：`8 × 548s = 4384s ≫ 1800s`——**用 PRD 自己的默认配置就能算出违反**。

两点加剧：① 74~79s 出自 **HTTP 模式**（彼时 KB/link/search 由 xiaobao 预取传入），而 DB 模式下 KB 转为 ai 主动检索，基准本就不可比；② 逼近上限的场景（Tavily 不可达 / KB 慢 / LLM 限流触发 fallback 链串行重试）恰是故障期，而故障期正是队列积压、批量价值最高的时候——按均值配容量，故障时必然踩线。

同一个数字还撑着另外两条：AC-5.7 的停机宽限期下限、AC-9.3 的 `last_poll_at` 陈旧容忍上限。

## 决策

**① 引入单条 wall-clock 预算 `L1_ITEM_BUDGET_MS`，默认 240000（240s），并以 deadline 传递方式覆盖 pipeline 全程。**

不是给各段配更小的常量，而是给整条一个总闸：`ItemBudget.slice_for(段上限)` 返回 `min(段上限, remaining)`，每个 IO 节点发起调用前用它换取本段可用时间。预算耗尽则跳过该节点（记降级）或整条按 `error_kind=timeout` 走可重试路径。

同时收紧三个工具的段上限，不再透传 `options.timeout_ms`：

| 段 | v0.1 | v0.2 |
|---|---|---|
| `kb_search` | 180s | 15s |
| `link_read` | 8s | 8s |
| `web_search` | 180s | 20s |
| LLM | 180s（budget 未实传） | `budget.remaining_ms()`，**实传给 `ChainedAIClient(budget_ms=…)`** |

三个工具之和 43s 仅占预算 18%，把绝大部分预算留给 LLM 及其 fallback 链。

240s 的取值依据：v0.1 实测 79s 的约 3 倍余量，覆盖「主动 KB 检索 + 一次 provider fallback」的现实最坏情形；它是**可调参数**（改配置不改代码），灰度期按日志 `duration_ms` 分布复核。

**② 批量大小 `L1_CLAIM_BATCH_SIZE` 默认取 1**（推翻 PRD 的暂定值 8；PRD AC-3.6 已授权 O-3 重算）。

**③ 三条派生量共用同一个被保证的输入**：

| 量 | 公式 | v0.2 取值 |
|---|---|---|
| 批量上限不变式（AC-3.6） | `N × 预算 < 1800s × 0.6` | `1 × 240s = 240s` ✔（7.5 倍余量） |
| 停机宽限期下限（AC-5.7） | `≥ N × 预算` 且 `< 1800s` | 260s |
| `last_poll_at` 陈旧容忍（AC-9.3） | `N × 预算 + 轮询间隔` | 255s |

**④ 配置校验是启动门禁**：三条不等式在进程启动时校验，任一不满足即拒绝启动并打印算式——它们是正确性约束，不是调优建议。

## 为什么 N = 1

在 v0.2 的前提下（PRD §4 明确：**批内串行、单 worker 实例**），N > 1 **零收益、纯风险**：

- **吞吐完全相同**。8 条串行处理的总时间与逐条 claim 8 次相同。多出的只是 7 次毫秒级 claim 事务，相对 240s 的单条处理不足 0.01%。取到条目后 worker 立即进入下一轮 claim（不等轮询间隔），空队列才 sleep——所以 N=1 不会因为「等下一次轮询」而损失吞吐。
- **持锁时长线性放大**。批内最后一条的持锁时长 ≈ `N × 预算`：N=1 是 240s（余量 7.5 倍），N=8 是 1920s——**已经超过 1800s 阈值**。
- **崩溃影响面放大 N 倍**。worker 在处理第 1 条时崩溃，其余 N-1 条**根本没被处理过**，却同样被锁 30 分钟等回收。N=1 时只有 1 条受影响。
- **配置项保留**，v0.3 批内并发落地后可上调，且不变式校验会自动约束上限——不是把能力删掉，是把默认值放在正确的位置。

## 考虑的替代方案

| 方案 | 优点 | 缺点 | 为什么不选 |
|------|------|------|-----------|
| **A. 直接把 N 调小到 3，不引入预算**（DevOps 建议②） | 改一个数字，成本最低 | 单条上限仍不被保证：`3 × 548s = 1644s`，逼近 1800s；故障期（fallback 链全走一遍）仍会越界 | 这是绕开根因而非解决根因（PRD §0 准则）；且 AC-5.7 与 AC-9.3 依旧没有可靠输入 |
| **B. 各段配更小的独立超时** | 不需要 deadline 传递机制 | 各段之和仍会累加，无法保证单条上限；每加一个工具就要重新算一遍总和 | 与 A 同类问题：治标 |
| **C. 用 `asyncio.wait_for` 在最外层包整条** | 实现最简单 | 超时点在任意 `await` 处抛 `CancelledError`，可能中断到一半的写回；且无法「跳过某个工具但继续处理」的部分可用语义 | 破坏 v0.1 已验证的降级语义（部分可用 = `succeeded`）；外层硬砍不如逐节点让路 |
| **D. 保持 N=8，靠 worker 主动续锁（heartbeat 刷新 `locked_at`）** | 批量与安全兼得 | `locked_at` 的语义归 xiaobao 的回收机制，ai 频繁刷新等于单方改变对方机制的判定基础，须先改契约 | 越界改动对方的卡死回收语义，且 v0.2 从批量得不到任何收益，不值得为此改契约 |

## 后果

**正面**

- 单条耗时有了**被机制保证的上限**，AC-3.6 / AC-5.7 / AC-9.3 三条从此共用一个确定输入，不再各自引用一个未被保证的经验值。
- 卡死误回收的余量从「逼近阈值」变为 7.5 倍。
- 单条卡住不再拖垮整个 worker：预算到点主动放弃并释放锁，条目按退避重试。
- 单点崩溃的影响面从 N 条降到 1 条。

**负面**

- 每条多一次 claim 往返（毫秒级，可忽略）。
- 预算逼近时会主动放弃本可以再等一会儿就成功的条目——但它会按退避重试，且这类条目本就是拖慢队列的源头。
- 三个工具段上限收紧后，极慢的 KB / Web 搜索会更早降级为「无结果」，处理质量在这些场景下略降；这是用质量换可预测性的自觉取舍。

**风险**

- 240s 是估计值，过小会误杀慢条目。缓解：属可调参数，灰度期按 `duration_ms` 分布复核。
- deadline 传递要求每个 IO 节点都正确消费 `slice_for`——漏掉一个节点，该节点就会退回独立超时。缓解：AC-3.8 的验证方式（mock 各段耗时使总和超预算，断言在预算点被放弃）能覆盖这种遗漏。
