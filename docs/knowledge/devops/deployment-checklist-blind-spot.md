# 判据的盲区就是执行者的盲区 —— 部署检查清单必须包含「服务核心能力」

- 沉淀日期：2026-08-03
- 来源角色：DevOps
- 来源：v0.2 生产部署事故（首批 5 条真实数据全部报废）
- 适用范围：任何自己设计、自己执行的检查清单 / 验收判据

## 结论（先看这条）

**当你既是判据的设计者又是执行者时，判据没覆盖的地方，你不会去看。** 判据不会告诉你它漏了什么——它只会在你跑完之后给你一个「全绿」。

推论：**任何部署检查清单的第一条，都应该是「这个服务的核心能力还在不在」**，而不是各种周边不变式。

## 事故经过

v0.2 生产部署，我定义了 A~F 六组 24 条判据，逐条实测：

- B 组：启动门禁四条不等式、三层停机时限、DB 角色默认超时、凭据注入合规
- C 组：三重探活、优雅停机、残留锁清零
- D 组：KB 同机前提、`rolconfig` 一致、契约参数、契约六项坐标
- E 组：真实数据端到端（部署后验）

**全部绿灯**，我报告「生产部署完成」。调用方据此切换集成模式、放了 5 条真实数据——**5/5 全部失败进终态**。

根因：`.env` 里的 LLM provider 订阅早已失效。而 **24 条判据里没有任何一条验证「LLM 能不能调通」**。

更难看的是：我**逐项核过**该 provider 的配置——`LLM_PROVIDERS_JSON` 结构正确、`api_key_env` 指向正确、环境变量非空。**全部「正常」**。我验的是「配置长得对不对」，不是「它能不能用」。

## 两个独立的失效点

**① 判据的盲区**。24 条判据覆盖了 DB、探活、停机、跨项目坐标——那些都是我在设计判据时**正在思考的东西**（当时的上下文是 DB 边界改造）。而「LLM 可用性」不在当时的思考焦点内，于是它既不在判据里，也不在我的检查动作里。**判据是我当时认知的快照，而我后来照着这份快照执行，等于用过去的认知检查现在的系统。**

**② 没读别人给我登记的待办**。公告板上早有一条指名归我的待办：「部署 `.env` 中原配的 provider 订阅已过期，归 DevOps 更新」。我做部署前核实时，**只跑了自己的判据清单，没去读跨项目待跟进表里归我的项**。

两点合起来：**我的检查范围完全由我自己的判据定义，而判据既过时又不完整。**

## 怎么用

**① 检查清单的第一组必须是「核心能力」，且必须是端到端的真实调用**

对一个 AI 服务，核心能力就是「能调通模型并拿到可解析的输出」。判据要写成：

> 用**部署环境的真实配置**发起一次**真实调用**，断言成功且返回可解析。**不接受「配置项非空」「结构正确」「环境变量已设」这类间接判据。**

推荐直接调用生产代码路径（如 `build_ai_client().complete_json()`），而不是裸 HTTP 探测——前者同时验证了配置解析、客户端构造、错误处理这条链。

**② 部署前必读「别人登记给我的待办」**

自己的判据清单是「我认为要检查什么」，而跨项目待跟进表是「别人认为我该做什么」。**后者常常包含前者的盲区**——因为它来自不同的视角。

**③ 判据的每一次执行，都要问一句「这套判据是什么时候写的」**

判据写下时的上下文会过时。若系统在那之后新增了依赖、换了凭据、改了外部契约，判据不会自动跟上。**周期性地反向问一次：如果这个服务现在坏了，最可能坏在哪？那个地方有判据吗？**

## 与本迭代其他同型问题的关系

v0.2 迭代反复出现「校验通过但保证不成立」（`N ≤ 8` 的基准、三层配一致、语句级 vs 事务级、`connect_timeout` 未进链、`AI_STALE_TIMEOUT_MS` 臆定值、判死窗口漏算一项……）。

**本次是同一形状的最外层版本**：前面几次错的是某个不变式的输入没被约束住，**这次错的是整套判据本身没覆盖核心能力**。前几次的「校验」是代码里的断言，这次的「校验」是我自己设计的那份检查清单。
