# 跨层约束的强制点选址：谁读得到两端，谁才能强制

- 沉淀日期：2026-08-01
- 来源角色：DevOps
- 来源：v0.2 设计 R2 Review 问题 2（三层停机时限）、CN-008 末票中②（DB 角色默认超时）
- 适用范围：任何「约束的两端分属不同层」的场景，不限本项目

## 结论（先看这条）

**一条约束能不能被强制，取决于「有没有哪一层同时读得到它的两端」。找不到这样的层，约束就是纸面上的——写得再清楚也没人守。**

推论：**约束的强制点应放在能读到两端的最低层，而不是放在它被写下来的那一层。**

## 两次实例（同一形状）

| # | 约束 | 两端 | 应用层能否强制 | 实际强制点 |
|---|------|------|--------------|-----------|
| 1 | 三层停机时限须**逐层放大**（应用 ≤ ASGI < systemd） | 应用侧 `L1_SHUTDOWN_GRACE_MS`（`.env`） / 托管层 `TimeoutStopSec`（unit 文件） | ❌ **应用进程读不到自身的 systemd 配置** | `deploy.sh [4.5/6]` |
| 2 | `ALTER ROLE` 的角色默认超时**不得严于**应用层 `SET` 的值 | 应用层 `AI_DB_*_TIMEOUT_MS`（`.env`） / 数据库侧 `pg_roles.rolconfig` | ❌ 应用**连接后立刻 `SET` 覆盖**，读不到自己的角色默认值 | `deploy.sh [4.6/6]` |

两次都是**部署层**成为唯一可行的强制点——因为只有部署脚本同时站在「配置文件」和「运行环境（systemd unit / 数据库）」之间。

## 为什么「没有强制点」比「配置错了」更危险

两个实例的失败模式相同，且都**不报错**：

- **实例 1**：把 `N` 调到应用侧合法上限 → 应用要求 `grace` 变大 → 改配置 → **应用侧所有校验全绿、启动成功**；而 `TimeoutStopSec` 是 unit 常量不会跟着变 → systemd 提前 SIGKILL → 写回在 COMMIT 前被杀、留残留锁。**比不配更隐蔽，因为一切看起来都是对的。**
- **实例 2**：角色默认设成 2s（严于应用层 4s）→ 只在连接建立后、`_configure` 执行前的那几条语句上生效 → 表现为**只在建连瞬间出现的偶发失败**，且归因极难。

共性：**校验通过但保证不成立**。这与同期几次不变式事故（`N ≤ 8` 的基准、语句级 vs 事务级、`connect_timeout`）是同一个病——**不变式的输入不被任何机制保证**。

## 怎么用

新增一条跨层约束时，按顺序问三个问题：

1. **这条约束的两端各在哪一层？**（配置文件 / 应用运行时 / 托管层 / 数据库 / 对端服务）
2. **有没有哪一层同时读得到两端？** 没有 → 这条约束目前**无法强制**，别假装它成立。
3. **能读到两端的最低层是哪个？** 把校验放那儿，失败要 `exit 1` 并**打印修复命令**（而不是只报错——修复命令能省掉排查的人一轮翻文档）。

若三个问题的答案是「没有任何层读得到两端」，那只剩两条路：**改设计让两端落到同一层**，或**显式登记为无保证项**（写进部署就绪检查的「已知边界」，不要留在正文里假装它被守着）。

## 反例：不要把强制点放在「写下约束的那一层」

实例 1 的初版设计把三层一致性的校验写在**应用启动校验**里——因为约束是在设计文档的应用章节里写下的。这是最自然的直觉，也是错的：**约束写在哪儿，和谁能验它，是两件事。**
