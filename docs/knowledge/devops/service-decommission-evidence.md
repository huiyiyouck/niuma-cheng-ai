# 停服决策的证据标准：活跃连接数 0 不等于没人用

- 沉淀日期：2026-08-01
- 来源角色：DevOps
- 来源：v0.1 服务（`127.0.0.1:8100`）停机决策，运行 31 天后停止
- 适用范围：任何「看起来没人用了」的服务下线判断

## 结论（先看这条）

**「当前活跃连接数 0」对批处理型调用方而言是常态，不是无人使用的证据。**

判断一个服务能否停，要看的是**请求日志的构成**（总量 + 来源 + 时间分布），不是某一时刻的连接快照。

## 本次的具体情形

`8100` 上的 v0.1 服务运行 31 天，停机前核实：

| 检查项 | 结果 | 能否作为停机依据 |
|--------|------|----------------|
| `ss -tnp` 活跃连接 | **0** | ❌ **不能** —— 调用方 xiaobao 是定时批处理、日均才 15~30 条，绝大部分时间连接数本就是 0 |
| uvicorn 访问日志 `POST /v1/runs/news-l1` 总数 | **10 条**，且与 07-01 冒烟 + 07-04 联调记录**逐条吻合** | ✅ **可以** —— 说明该端口**从未承接过生产流量**，31 天只服务过联调 |
| 调用方 `journalctl -u news-api` 近 7 天 | 零命中 | ✅ 辅证 |
| 调用方配置 | ⚠️ **`AI_INTEGRATION_MODE=http`，且 `AI_HUB_BASE_URL` 未覆盖 → 默认值指向 8100** | ⚠️ **反证** —— 配置上仍存在依赖 |

**最终判断**：日志构成证明是「配置上的潜在依赖」而非活跃链路，据此停机；同时把配置事实主动知会对方并登记跨项目待跟进项。

## 停服前必查清单

1. **请求日志的构成**——总量、来源 IP、时间分布。总量小但**分布在整个周期**说明有稀疏真实流量；总量小且**集中在联调时段**说明从未投产。这两者的连接数快照完全一样。
2. **调用方的配置指向**——不只看它现在调不调，要看它**配置上指向哪儿**。配置里的依赖是「潜在的活跃依赖」，随时可能被触发。
3. **调用方的模式开关**——如本次的 `AI_INTEGRATION_MODE`。开关在 `http` 而实际没调，说明链路可能未启用；但**开关随时可能被打开**。
4. **该服务是否是某个预案的一环**——本次 HTTP 模式契约被标注为「灰度/回滚用」，停掉承载它的进程前必须确认**回滚路径仍有其他承载**（本次由 8102 承载，故回滚能力未受损）。

## 停机动作本身的标准

停机是可逆的，但**只有在恢复方法被记下来的前提下才可逆**。停之前留档：

- 完整 `cmdline`、`cwd`、启动时间、运行时长
- 代码版本（`git rev-parse HEAD`）——恢复时要起的是**同一个版本**
- 恢复命令原文
- **更推荐的替代路径**（本次：让调用方指向已 systemd 托管的 8102，比恢复一个 `nohup` 裸进程更稳）

停机后立即核验**三件事**：目标端口已释放、**其他服务不受影响**、托管服务状态正常。只验第一件是不够的——停错进程、连带杀掉同机其他服务是真实风险。

## 教训

Owner 给的判断是「没人使用」，方向正确；但**「没人使用」需要被翻译成可核验的证据**才能作为停机依据。执行方的价值不在于复述这个判断，而在于**找出它的盲区并据实报告**——本次的盲区就是调用方配置仍指向该端口，报告后风险从「未知」变成「已登记且有三条处置路径」。
